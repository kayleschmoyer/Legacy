# FLD-003 — Commissioner Settings has no roster-position reconfiguration control for football leagues

**Severity:** Medium
**Type:** Task
**Agent lens:** Senior QA Lead
**Platform:** Android Native
**File:** `apps/app/src/features/commissioner/CommissionerScreen.tsx`

## Description

The Commissioner Settings Tab Feature Story (LS-5416) lists "NFL roster requirements" among the expected commissioner controls, alongside Next Step, draft settings, waiver type, playoff format, LeagueScoringEditor, dues setup/status, audit log, and note control — all of which are present and wired in `CommissionerScreen.tsx`. `LeagueSettingsControl` (the general league-settings control rendered for all sports) exposes games-per-matchup, career filters, playoff format/multi-week, and salary cap — but nothing for roster position slot counts (QB/RB/WR/TE/K/DST/DL/LB/DB counts). `DraftSettingsControl` is explicitly gated `{!isFootball && ...}` (baseball-only draft pool/era settings), and there is no equivalent football-specific control rendered in its place for roster requirements. This is a post-creation-editing gap distinct from — but related to — the create-time roster-position gap already filed as LS-6151 (CLF-032, premium custom roster positions at creation).

## Steps to Reproduce

1. As a commissioner of an existing football league, open Commissioner Settings.
2. Look for any control to change roster position slot counts (e.g. add a second FLEX, add Superflex) after league creation.
3. None exists — `LeagueSettingsControl` has no roster-position fields, and the football branch (`!isFootball` guard) skips the one control (`DraftSettingsControl`) that might have been the natural home for it.

## Expected

A football-specific roster-requirements control in Commissioner Settings, symmetrical with the baseball-only `DraftSettingsControl` it currently excludes.

## Actual

No such control exists; roster positions set at league creation cannot be changed afterward via the Commissioner Settings tab on native.

## Recommendation

This is the natural implementation surface for LS-6151's premium custom-roster-positions gap — recommend linking this finding to LS-6151 rather than treating them as fully independent, and scoping the actual UI work through `/define` given it needs server-side validation of in-flight roster changes (e.g. what happens to already-drafted/rostered players when slot counts shrink).
