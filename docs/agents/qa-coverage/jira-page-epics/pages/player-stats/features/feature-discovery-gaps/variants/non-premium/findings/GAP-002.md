# GAP-002 — Missed feature: Blob export via createObjectURL + revokeObjectURL lifecycle

**Severity:** Medium
**Type:** Bug
**Agent lens:** Feature Discovery From Code
**Platform:** Web
**File:** `apps/web/src/pages/players/PlayerStatsPage.tsx:222`

## Description

`handleExport` in the route shell (`PlayerStatsRoute`) creates a `Blob`, calls
`URL.createObjectURL`, programmatically clicks a hidden `<a>` element to trigger the
browser download, and then calls `URL.revokeObjectURL`. In the original implementation
the revoke call was not wrapped in a `try/finally` block — if any step between
`createObjectURL` and the revoke (e.g., appending the link or the click itself) threw,
the URL was silently leaked and never revoked.

The `export-json` feature story (LS-5591) documents what is exported and when, but
it did not enumerate a `resource-cleanup` variant that would assert every export path
— including the error path and repeated concurrent exports — correctly releases the
object URL.

## Steps to Reproduce

1. Mock `URL.createObjectURL` / `URL.revokeObjectURL` with Jest spies.
2. Force `document.body.appendChild` (or the programmatic `.click()`) to throw.
3. Assert that `URL.revokeObjectURL` was still called (it was not in the original code).

## Expected

`URL.revokeObjectURL` is called on every export, including when an error occurs
between `createObjectURL` and the download link click. Each of 50 rapid repeated
exports cleans up its own object URL exactly once.

## Actual

`URL.revokeObjectURL` was only called in the happy path. Any exception between
`createObjectURL` and the revoke left the object URL alive — a memory leak that
accumulates with each failed export.

## Recommendation

Wrap the link append, click, and remove in a `try/finally` block so
`link.remove()` + `URL.revokeObjectURL(url)` always run, including on the error path.
Add a `resource-cleanup` variant to the `export-json` feature doc covering:

- Success-path revoke
- Error-path revoke (link click throws)
- Concurrent/repeated exports each clean up their own URL

## Resolution

Fixed in `apps/web/src/pages/players/PlayerStatsPage.tsx` — the link
`append` / `click` / `remove` sequence is now wrapped in `try/finally` so
`link.remove()` and `URL.revokeObjectURL(url)` run on every export, including the
error path. `document.body.removeChild` was also replaced with `link.remove()` (safe
whether or not `appendChild` succeeded).

New test suite added in `apps/web/src/pages/players/PlayerStatsRoute.spec.tsx`:

- **Success path** — `revokeObjectURL` called once after a normal export.
- **Error path** — `revokeObjectURL` still called when the link click throws.
- **50 repeated exports** — each created URL is revoked exactly once (no accumulation).

jsdom does not implement `URL.createObjectURL` / `URL.revokeObjectURL`, so the tests
install Jest spies. The shared `PlayerStatsPage` is mocked in the route spec; the mock
was extended to capture the `onExport` prop so the export callback can be driven
directly.
