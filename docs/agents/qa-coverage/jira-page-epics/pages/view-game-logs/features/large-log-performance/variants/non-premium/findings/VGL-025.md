# VGL-025 — Automation gap: no k6 perf scenario or render-time test for full-season game logs

**Severity:** Low
**Type:** Task
**Agent lens:** Automation Coverage Audit
**Platform:** All
**File:** `tests/performance/scenarios/game-logs.js`

## Description

No k6 performance scenario existed for the View Game Logs feature. The
`tests/performance/scenarios/` directory contained only
`baseline.js`, `draft-day.js`, and `stress.js`; no scenario covered
`POST /baseball-game-logs` under load.

An MLB player's full season spans up to 162 games. Fetching a full-season
log with no date filter is the most data-intensive read path the stats
endpoint receives and the most likely site of latency regressions under
concurrent load. Without an automated scenario, performance regressions in
the game-logs handler go undetected until production.

## Steps to Reproduce

1. Open `tests/performance/scenarios/`.
2. Observe: no scenario targets `POST /baseball-game-logs` with a
   full-season (no-date-filter) payload.

## Expected

A k6 scenario exists that:

- POSTs to `/baseball-game-logs` with no date filter, exercising the
  full-season (162-game) read path
- Runs a single-VU baseline (30 s) followed by a 10-VU load phase (1 min)
- Enforces p(95) response time ≤ 2 000 ms via a k6 threshold
- Tracks a custom `errors` Rate metric and enforces < 1 % error rate

## Actual

No such scenario existed; the automation gap meant performance regressions
in the game-logs stats handler were invisible to CI.

## Resolution

Created `tests/performance/scenarios/game-logs.js` (LS-7474). The scenario
implements a two-phase k6 run with the thresholds described above. Override
the target URL via `K6_STATS_API_URL` for staging / production runs.
