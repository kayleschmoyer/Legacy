# GAP-002 — Missed feature: Matchup Roster Editor panel undocumented as its own feature

**Severity:** Medium
**Type:** Bug
**Agent lens:** Feature Discovery From Code
**Platform:** All (web, mobile-web, android)
**File:** `apps/web/src/features/matchup/MatchupRosterEditor.tsx`

## Description

`MatchupDetailLayout` renders a `rosterEditor` slot (slot 7 of 9, after the matchup
information card and before `recapPanel`) wired on both platforms:
`apps/web/src/pages/matchup/MatchupDetailPage.tsx:237-249` — gated on `userTeamId != null
&& leagueIdNum != null`, matchup status `Scheduled`/`InProgress`, and the viewing user
owning one of the two teams (`matchup.team1Id === userTeamId || matchup.team2Id ===
userTeamId`) — and `apps/app/src/features/matchup/screens/MatchupDetailScreen.tsx:132-146`
(same guard via the derived `isUserInMatchup`).

Both wrap `MatchupRosterEditor` (web: `apps/web/src/features/matchup/MatchupRosterEditor.tsx`;
native: `apps/app/src/features/matchup/components/MatchupRosterEditor.tsx`), a
data-fetching wrapper around the shared presentational component
`MatchupRosterEditorView` (`lib/shared-components/src/features/roster/MatchupRosterEditorView.tsx`).
It:

- Fetches matchup players + league positions via GraphQL, filtered to the viewing
  user's team.
- Wires `onSwapPositions` / `onMoveToPosition` mutations (`useSwapMatchupPlayerPositions`,
  `useUpdateMatchupPlayerPosition`), each preceded by a pre-flight `MatchupStatus`
  re-fetch that discovers and locks editing if the matchup is no longer `Scheduled`
  (web: `MatchupRosterEditor.tsx:157-229`).
- Renders a locked (read-only) view once the matchup transitions to `InProgress` (native
  passes `locked={matchup.status === MatchupStatus.InProgress}` at
  `MatchupDetailScreen.tsx:143`; web discovers the lock server-side via the pre-flight
  check above).
- Already has hermetic Playwright E2E coverage
  (`apps/web-e2e/src/tests/matchup-roster-editor.spec.ts`) plus component specs
  (`apps/web/src/features/matchup/MatchupRosterEditor.spec.tsx`,
  `lib/shared-components/src/features/roster/MatchupRosterEditorView.spec.tsx`) — the
  feature is fully tested but has no QA inventory / feature-doc entry.

None of the four pre-existing feature docs (matchup-information-card LS-5352,
matchup-navigation-controls LS-5353, roster-comparison LS-5357, win-probability-panel
LS-5358) mention roster editing anywhere; it is a distinct, non-premium,
ownership-and-status-gated feature of the page with its own interaction model
(swap/move) separate from the read-only `roster-comparison` feature (LS-5357).

## Steps to Reproduce

1. As the owner of one of the two teams in a `Scheduled` or `InProgress` matchup, open
   `/baseball/league/:leagueId/matchups/:matchupId`.
2. Observe the roster editor rendered between the matchup information card and the
   (gated) AI Matchup Recap panel, allowing lineup position swaps/moves.
3. Open the same matchup as a non-owning user (or after it becomes `Completed`) and
   observe the slot renders nothing.

## Expected

A dedicated Feature Story enumerates the "Matchup Roster Editor": the
ownership + status (`Scheduled`/`InProgress`) gating, the swap/move interactions, the
pre-flight lock-discovery behavior, and its existing E2E/unit test coverage — the same
level of QA coverage as the sibling roster-comparison doc (LS-5357).

## Actual

No feature doc or Jira ticket owns this panel, despite it being fully covered by
existing E2E and unit tests.

## Recommendation

File a Feature Story for "Matchup Roster Editor" modeled on the sibling
roster-comparison doc (LS-5357), enumerating the ownership/status gates, the
swap/move mutation flow, the pre-flight lock-discovery behavior, and referencing the
existing test coverage (`matchup-roster-editor.spec.ts`,
`MatchupRosterEditor.spec.tsx`, `MatchupRosterEditorView.spec.tsx`).
