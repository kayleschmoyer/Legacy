# FPD-029 — No data source / provenance documented for injury data — when a user disputes a status, support has no audit trail

**Severity:** Medium
**Type:** Task
**Agent lens:** Observability / Data Accuracy
**Platform:** Web Desktop, Web Mobile, iOS, Android
**File:** `(no docs)`

## Description

When injury status ships on the Football Player Detail page, no data source or
provenance is documented for the displayed status. If a user disputes a
status — "this player is active, not Out" — support has no audit trail to trace
where the status came from, which provider reported it, or when it was fetched.

The recommendation is to document the source (e.g. an official NFL injury
report surfaced through a licensed redistributor) and to surface
`Source: NFL official injury report` on hover for trust.

## Steps to Reproduce

_no steps provided_

## Expected

Injury data has a documented source and provenance model, giving support an
audit trail to resolve disputes, and the displayed status surfaces its source
to the user for trust.

## Actual

No provenance was documented. The only `injury` value in the codebase is
placeholder data on the demo Draft `PlayerCard`
(`lib/shared-components/src/features/draft/PlayerCard.tsx`), with no recorded
source — so a disputed status could not be traced anywhere.

## Recommendation

Document the source (e.g. SportRadar, official NFL report, MFL feed) and surface
`Source: NFL official injury report` on hover for trust.

## Resolution

Documented the injury-data provenance model and audit-trail requirements in
`docs/architecture/injury-data-provenance.md` (LS-6253). The doc records the
current state (no live injury feed; football data
is sourced from Pro Football Reference, baseball from archived box scores),
specifies the four provenance fields any injury-status feature must capture at
ingestion (source/provider identifier, original report reference, fetch
timestamp, and a queryable audit trail), and captures the FPD-029 UX
requirement to surface `Source: <provider> injury report` on hover. Selecting a
provider and building the Injury Status & News UI remain follow-up work that
must satisfy these requirements when the feature ships.
