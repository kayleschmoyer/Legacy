# Skill: Cloud Agent Mode

Cloud implementation of the [ticket-to-merge spine](../workflow-overview/references/ticket-to-merge-spine.md). The spine owns the **ordering** (Steps 0–16, five gates, mandatory tracking-task graph) — nothing here restates it; this file binds each spine action to the tools your cloud platform actually has, and is the single home for cloud platform facts (quirks, auth, transition IDs, label mechanics).

Common to all cloud platforms: Linux, bash, `/` paths; no worktrees, no `twig`, no `acli`; work on a branch off `origin/main` in the repo root; pnpm 9.12.1 via corepack.

## Step 0: identify your platform

Three configurations hide behind "cloud agent". Identify yours **before** following any workflow — the validation binding differs and picking wrong wastes the session.

```
Is `mcp__legacy-sports-nx__nx_run_pc_chunk` present?
   (check the deferred-tools <system-reminder>, or run ToolSearch("select:nx_run_pc_chunk"))
│
├─ YES, and built-in Bash/Read/Edit are present
│     → CONNECTOR CC WEB (Claude Code on the web with custom remote connectors)
│
├─ YES, and there is no Claude Code shell (worktree_*/make_* tools instead of Bash)
│     → COPILOT CODING AGENT
│
└─ NO
      ├─ `mcp__Claude_Code_Remote__*` tools present (e.g. `create_trigger`, `list_repos`, `send_later`) alongside hosted `legacy-sports-{jira,github,ci}` connectors
      │     → CLAUDE CODE REMOTE (CCR) — see [below](#claude-code-remote-ccr)
      │
      └─ No custom MCP servers of any kind
            → DEFAULT (DEGRADED) CC WEB
```

Secondary confirmation for default CC web: `jira_*` tools absent, `Glob`/`Grep` may be absent (probe with `ToolSearch("select:Glob,Grep")`), no Docker socket, no `gh` CLI. Three diagnostic probes (LS-4358 + two reprobes) confirmed default CC web ignores project `.mcp.json` (stdio servers never load) and `.devcontainer/devcontainer.json` entirely.

## Validation binding (safety-critical — read before running anything)

The seven `pc-*` chunks in canonical order — `pc-db-prep` → `pc-typecheck` → `pc-format` → `pc-lint` → `pc-workflows` → `pc-test` → `pc-build` — are the only validation path in cloud. They are the same nine steps as `make pc`, and equivalent to it **only if all seven run in order** (LS-7906). The chunk list's source of truth is `PC_CHUNKS` in `tools/mcp/nx-server/src/tools/run-pc-chunk.ts` and the `pc-*` targets in the Makefile.

**`pc-test` and `scripts/*.ps1` changes (LS-8729)**: `pc-test`'s underlying `_PC_TEST_CMD` (`pnpm exec nx affected -t test --base=$NX_BASE`) never touches root-level `scripts/`, since it is not an Nx project. `classify-changes.js` sets `PC_HAS_PS1=1` whenever a changed file matches `scripts/**/*.ps1`; when that flag is set, `pc-test` additionally runs `pnpm run test:scripts:ps` if `pwsh` is on `PATH`, or prints an explicit `SKIPPED (pwsh not installed)` line otherwise — see [Quirk 11](#quirk-11-pwsh-is-not-preinstalled-pnpm-run-testscriptsps-fails-outright-ls-8729) for installing `pwsh` in this environment so the step actually runs instead of being skipped.

| Platform             | Binding (owner ruling 2026-07-02)                                                                                                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Copilot Coding Agent | `nx_run_pc_chunk({ chunk: "pc-db-prep" })` → … → `({ chunk: "pc-build" })` — **mandatory** wherever the tool exists (30-min runaway backstop, structured pass/fail)                                                                               |
| Connector CC web     | Same — `nx_run_pc_chunk` per chunk, **mandatory**                                                                                                                                                                                                 |
| Default CC web       | `nx_run_pc_chunk` does not exist here. Sanctioned path: Bash `make pc-<chunk>` with **`run_in_background: true`**, one chunk at a time, waiting for each background completion before starting the next. This is the only compliant degraded path |

Preconditions that hold on every platform:

- **Before any chunk**: the draft PR exists and the branch is pushed (spine [draft-PR-before-validation gate](../workflow-overview/references/ticket-to-merge-spine.md#critical-gates-preconditions)). A container reap mid-validation is then non-fatal.
- **Before `pc-db-prep`**: migrations applied where a DB exists (Copilot: `pnpm --prefix lib/db-client run db:status` → `db:up` against local Docker Postgres; default CC web has no DB — see [degraded mode](#default-cc-web-degraded-mode)).
- **Before `pc-format`**: commit all your changes so the working tree is clean. `pc-format` runs `prettier --write .` repo-wide; with a dirty tree it exits 1 ("You have other uncommitted changes alongside the format fixes"); with a clean tree it commits any formatter rewrites as a new `style: apply formatting` commit on top of your tip commit — never an amend of the tip, since the tip is always already pushed by this point (LS-8367; verified in the Makefile `_PC_FORMAT_RECIPE`).
- **After each chunk**: refresh the continuation checkpoint; on failure, fix and re-run that chunk before moving on.
- Monolithic `make pc` / `make_run(target: "pc")` never runs in cloud on any platform — it exceeds transport windows and gets the container reaped mid-run.

Why the degraded path is background-only: the repo hook `.agents/hooks/enforce-background.mjs` exit-2 blocks foreground `make pc-<chunk>` (and foreground `pnpm exec nx affected|run-many`) because they exceed the Bash tool's ~120s inline timeout. `run_in_background: true` satisfies the hook and survives long chunks; completion arrives as a notification — do not poll output files while waiting. The companion hook `.claude/hooks/guard-make-pc.sh` warns (never blocks) on monolithic `make pc`.

**Never wrap the command in `nohup ... &` when using `run_in_background: true` (LS-8951)**: `run_in_background: true` already backgrounds the command for you — the Bash tool tracks it directly and fires a completion notification when _it_ exits. Additionally wrapping it yourself, e.g. `nohup make pc-typecheck > /tmp/pc-typecheck.log 2>&1 & echo "started pid $!"`, hands the tool a wrapper shell instead of the real command: the wrapper forks the `nohup`'d process and its `echo` returns almost instantly, so the tool reports "completed (exit code 0)" for the wrapper while the actual `make pc-*` target keeps running detached, unobserved, for minutes more. This produced false-positive "verified complete" pc-chunks during LS-6137 (PR #6616) — recovery required a manual `until pgrep -f "make pc-..." ...; do sleep 5; done` wait loop. **Correct pattern**: pass the plain foreground command directly — `Bash({ command: "make pc-typecheck", run_in_background: true })`, no `nohup`, no trailing `&`, no `echo $!`. The harness handles detachment; the notification then reflects the real command's actual exit.

Two guardrails on the background wait (LS-8542, from the PR #6190 stall):

- **Refresh the `<!-- continuation-plan -->` checkpoint before ending any turn that waits on a background chunk.** If the completion notification is missed or never processed, the session stalls permanently in draft; the `/sweep-prs` stalled-agent net ([sweep.md Step 2b](../pr-lifecycle/references/sweep.md)) is what recovers it, and it resumes from that checkpoint.
- **This degraded path is cloud-only.** A _local_ session where `nx_run_pc_chunk`/`make_run` are missing has a **broken worktree** (usually a dead `node_modules` link — stdio MCP servers fail silently without `node_modules/.bin/tsx`), not a degraded environment. Repair it (`node scripts/modules-pool/link.mjs`, then restart the session) instead of adopting background-Bash validation — see [workflow-overview local nuances](../workflow-overview/SKILL.md#local-only-step-nuances).

### Known failure mode: phantom typecheck/lint errors on unrelated files (LS-8384)

**Symptom**: `pc-typecheck` / `pc-lint` / `pc-build` / `pc-test` fail in a long-lived persistent cloud container, reporting errors in files with **zero diff** against `origin/main` for the current branch. `make clean-cache` (nx reset) does not fix it — errors reproduce identically after. A fresh worktree (or fresh clone) on the exact same source tree passes with zero errors, and the repo's real CI is confirmed green on the same commit throughout.

**Root cause**: unlike the [missing-`tsx`](../mcp-first/references/diagnostics.md#recovery-missing-node_modules) failure mode (`node_modules` absent or its pooled symlink broken, causing stdio MCP servers to silently fail to connect), this is a **present-but-corrupted** `node_modules` in a long-lived container — one or more specific packages have a broken/partial install (e.g. a stray nested `node_modules/<subdep>/` with no `package.json`/`dist` for the top-level package itself). Confirmed instances: `@aws-sdk/client-cloudwatch` (LS-6064), `recharts` (LS-8668). The underlying cause of the drift itself (partial/interrupted installs, stale `.pnpm` store entries) is **not identified** — this section documents the symptom and workaround, not a fix for the drift.

**Diagnose**: before trusting a local `pc-*` failure on a file your branch didn't touch, run `git diff --stat origin/main -- <file>` — zero output confirms the failure is unrelated to your change. Per LS-5895, a local persistent-container `pc-*` run can also misreport its own affected-project scope (e.g. claiming 26-30 affected projects for a 2-file change); when local and CI disagree, **trust CI's `nx affected` result**, not the local rerun. (One confirmed cause of affected-scope bloat: a stale local `origin/main` ref — `git fetch origin main` and re-diff before concluding the base itself is fine.)

**Why `make clean-cache` doesn't fix it**: its automatic node_modules re-link only fires when `.git` is a **file** (a git-worktree checkout) — see the Makefile's `clean-cache` recipe. In a long-lived container's **main-repo** checkout (`.git` is a directory, which is how cloud sessions run — no worktrees), `make clean-cache` reduces to a bare `pnpm exec nx reset` with no node_modules health check at all, so a corrupted install is never caught or repaired by it.

**Recover**: never manually `rm -rf` a package under `node_modules` — if it happens to be a pool-managed symlink (`.modules-pool/<hash>/node_modules`, see [modules-pool RFC](../../../docs/rfcs/modules-pool/README.md)), deleting inside it mutates a shared immutable slot other sessions/worktrees on the same lockfile hash rely on — the exact corruption class the pool exists to prevent. Instead run `node scripts/modules-pool/link.mjs` (safe to run from the main-repo root too, not just a worktree): it health-checks the current install for precisely this signature (orphaned pnpm `_tmp_` dirs, packages missing `package.json`) and auto-quarantines + rebuilds an unhealthy slot. Use `--check` first to see findings with no filesystem changes, or `--rebuild` to force a rebuild even when the health check doesn't flag anything.

**Related but distinct variant — total project-graph failure, not per-file phantom errors (LS-8473)**: the corruption signature above is _present-but-partial_ (a package directory exists but is missing files), which nx tolerates well enough to still build a project graph and run `tsc`, just against the wrong module resolution. A **more broken** slot — `link.mjs --check` reports `slot not built` rather than listing specific unhealthy packages — fails earlier and louder: `nx` cannot process the project graph at all (e.g. `Cannot find module 'react-native/jest-preset'` while resolving `apps/app/jest.config.ts` for the `@nx/jest` plugin), so **every** `nx` target errors out, including `typecheck` for projects that have nothing to do with the missing module. This is easy to misdiagnose as ~hundreds of pre-existing source-level `tsc` errors if the failing command's output is skimmed rather than read — the actual error is a single project-graph-construction failure, not a list of per-file diagnostics. Same recovery as above (`node scripts/modules-pool/link.mjs --rebuild`); afterward, `tsc --noEmit` run directly (bypassing nx) is the fastest way to confirm a project is genuinely clean.

**Bounded diagnostic/repair tooling, no manual worktree+relink dance required (LS-8698)**: the recovery commands above target a **worktree's pool slot** (`--check`/`--rebuild`, keyed by lockfile hash under `.modules-pool/`). A CCR/cloud session's **main-repo checkout has no pool slot at all** — it's a plain `node_modules` populated by a raw `pnpm install`, so those flags don't apply there. `link.mjs` also exposes a standalone pair for exactly this case, needing no worktree, lockfile, or pool resolution: `node scripts/modules-pool/link.mjs --assess-path=<dir>` answers "is this `pc-typecheck`/`pc-lint`/`pc-build`/`pc-test` failure present on a fresh install" directly against any `node_modules` (exit 0 healthy / 1 unhealthy, with findings printed — the same orphaned-`_tmp_`/missing-`package.json`/missing-`.modules.yaml` signature as the pool check), and `--heal-path=<dir>` performs the targeted repair (strips just the corrupt entries so a subsequent `pnpm install` rebuilds them cleanly, instead of a full relink). Both are already wired into the session-start path: `.claude/cloud-setup.sh`'s `node_modules_healthy()` check (registered as a SessionStart hook, LS-8113) calls `--assess-path` before deciding whether to skip `pnpm install`, and falls back to `--heal-path` + reinstall when it isn't. `.github/copilot/hooks/mcp-bootstrap.mjs` — which runs earlier still, before the first stdio MCP server launch — has its own separate, dependency-free health check (`isNodeModulesHealthy()`) that now also checks for `.modules.yaml`, matching `assessSlot()`'s signature, so a drifted install is caught there too rather than only surfacing later as an opaque `nx` project-graph failure (corroborating incident: LS-9681, 2026-09-02).

## Copilot Coding Agent

**Bootstrap**: `.github/workflows/copilot-setup-steps.yml` runs before every task: Node 22 + pnpm + deps, local Docker Postgres (service container, `postgres:16` on 5432) with migrations applied, Agent Author GitHub App token exported as `GH_TOKEN`/`GITHUB_TOKEN`, and one short-lived Cognito machine-grant bearer minted per hosted MCP scope (`MCP_{JIRA,GITHUB,CI,DB}_BEARER`) from the `client_credentials` secret. The SigV4/OIDC Lambda-Function-URL path was retired in LS-5093 — **no AWS credentials exist or are needed anywhere in cloud**. The authoritative secret/variable list lives in the header comment of `copilot-setup-steps.yml`; the MCP config to paste into Settings → Copilot → Cloud agent lives in `.github/copilot/copilot-cloud-mcp-config.json` (paste only the `mcpServers` object).

**Servers available** (from `.github/copilot/copilot-cloud-mcp-config.json`): hosted `legacy-sports-{github,ci,jira,db-admin}` (API Gateway + Cognito bearer) and stdio `worktree`, `legacy-sports-nx`, `legacy-sports-make`. The `worktree` server runs an allow-listed subset — the `tools` array in that config is the authoritative list (as of 2026-07-21: `worktree_ping`/`_list`/`_set`/`_run`/`_job_status`/`_job_wait`/`_job_list`/`_guard`/`_commit`/`_rebase_continue`/`_stabilize`/`_push`/`_reset_to_remote` plus `auth_check_all`); everything else, including the twig-dependent `worktree_rebase`/`worktree_clean`/`worktree_remove_batch`, is excluded — route ad-hoc git (status/diff/log) through `worktree_run`. Like the ruleset, this file is **config, not necessarily live state**: `worktree_commit`/`worktree_reset_to_remote`/`auth_check_all` joined the allowlist 2026-07-03 and the `worktree_job_*` polling tools 2026-07-21 (LS-8559), so if a live session rejects them the pasted Settings JSON predates that — ask the owner to re-paste the `mcpServers` object. No `legacy-sports-aws`, no browser server by default, no built-in `mcp__github__*` or Atlassian plugin.

**Session preflight**: `auth_check_all` (worktree server) is available here — run it first per AGENTS.md. Individual probes: `github_auth_status()`, `ci_auth_status()`, `jira_auth_status()`, `nx_check_package_health()`, `db_query({ query: "SELECT 1" })`, `worktree_ping()`. If a hosted server is unreachable, check the bootstrap logs for the bearer-minting step and confirm the `copilot` environment secrets named in the workflow header are set.

## Connector CC web

Claude Code on the web where the hosted `legacy-sports-*` servers are attached as **custom remote MCP connectors** registered in claude.ai (epic LS-5089). Registration is owner-only and out-of-band (Org settings → Connectors); once registered, connectors auto-sync into local and CC-web sessions for that account — nothing is read from `.mcp.json` in either case. Onboarding: [docs/dev-process/mcp-connector-access.md](../../../docs/dev-process/mcp-connector-access.md).

- **Auth is OAuth** (MCP OAuth 2.0 spec, LS-5095), consented once per connector by the human in a browser. Claude Code does **not** auto-refresh MCP OAuth tokens mid-session ([claude-code#58607](https://github.com/anthropics/claude-code/issues/58607)): a mid-session 401 means the token expired — prompt the user to re-consent via `/mcp`; do not fall back to `gh`/`curl`.
- **Which connectors are attached varies by account** — trust the deferred-tools list over any static claim here. The hosted DB connector may display as `legacy-sports-db` rather than `legacy-sports-db-admin` (verified in a live 2026-07-02 connector session); identify servers by their tool names (`db_query`, `db_migrate`), not display names.
- **Tool routing**: built-in `mcp__github__*` (native GitHub connector, bot identity) is authoritative for every PR operation it covers — create PR, mark ready draft-flip, reply to review comments, request Copilot review, read PR/reviews. The hosted `legacy-sports-github` connector covers the gaps: `github_manage_labels` (no built-in equivalent), `github_get_review_threads` (only source of GraphQL thread node IDs), `github_resolve_threads` (batch resolve + bot-review recheck; a 403 on the recheck dispatch is non-fatal — threads still resolve and the recheck fires on the next push).
- `auth_check_all` lives in the **stdio** worktree server and is therefore absent in both CC-web modes. Fallback: verify each surface on first use (one Atlassian-plugin call, one `mcp__github__*` call, one hosted-connector call) instead of a single preflight.
- Validation: `nx_run_pc_chunk` per chunk (see [Validation binding](#validation-binding-safety-critical--read-before-running-anything)).

## Default CC web (degraded mode)

No custom MCP servers of any kind. Confirmed surface (LS-4358 + two reprobes): built-in `Read`/`Edit`/`Write`/`Bash`, built-in `mcp__github__*`, Atlassian plugin. `Glob`/`Grep` may be absent — probe with `ToolSearch("select:Glob,Grep")`; if absent, Bash `find`/`grep -r`/`ls -1` are the sanctioned fallback for file **discovery** (keep file **reads** on `Read`). No `gh` CLI, no `GH_TOKEN`/`GITHUB_TOKEN` in env, no Docker daemon (`/var/run/docker.sock` missing), no `twig`/`acli`. `node_modules` is populated by `.claude/cloud-setup.sh` (runs at cloud session setup and on session start per its header: deepens the shallow clone to establish an `origin/main` merge-base, runs `pnpm install` when `node_modules/.bin/tsx` is missing — LS-8113/LS-8209), so `pnpm exec nx|prettier|tsx` work.

Follow the spine with these bindings (also see the [spine step table](#spine-step-binding-by-platform)):

1. Ticket lookup: Atlassian plugin `searchJiraIssuesUsingJql({ cloudId: "<see Jira binding>", jql: "key = LS-####", maxResults: 1 })` — never `getJiraIssue` (returns wrong data, LS-3715).
2. Transition In Progress: `transitionJiraIssue({ ..., transition: { id: "21" } })` — object, not string; mind [Quirk 2](#quirk-2-atlassian-plugin-transitionjiraissuecreatejiraissue-reject-nested-object-parameters-on-cold-start).
3. Branch: `git fetch origin main && git checkout -b claude/ls-####-<desc> origin/main`.
4. Implement; commit specific files (never `git add .`); `git push -u origin HEAD` (push auth is provided by the CC-web sandbox). `.claude/cloud-setup.sh` proactively neutralizes a stale git-lfs pre-push hook stub when git-lfs is absent (LS-7773), so this should now be rare. **If `git push` is still blocked by git-lfs** (e.g. the SessionStart hook did not run, or the hook was manually recreated after setup): fall back to `mcp__github__push_files` to push via the GitHub API. After any API-based push the local branch is behind the remote — re-sync with `worktree_reset_to_remote()` where the worktree server is attached (Copilot; see the [mcp-first substitution table](../mcp-first/SKILL.md)); in degraded CC web (no worktree server) use Bash `git fetch origin <branch> && git reset --hard origin/<branch>`.
5. Draft PR via `mcp__github__create_pull_request({ ..., draft: true })`; checkpoint via `mcp__github__add_issue_comment` with a body starting `<!-- continuation-plan -->` ([format](../dev-process/artifacts/continuation-plan.md)). If the body was assembled in a scratch file, `Read` it back and inline the text — `body` is a literal JSON string, not shell-evaluated (see the [create-PR callout](../pr-lifecycle/references/create-pr.md#command)). **Hand-author the `jira-link` HTML-comment marker in this call's body** — despite recurring reports to the contrary, `create_pull_request`/`update_pull_request` do **not** strip it (confirmed, LS-8694: [full writeup in create-pr.md](../pr-lifecycle/references/create-pr.md#jira-link-check-repairs-the-marker-for-you-ls-9279)); those reports were the [documented read-path display stripping](../pr-lifecycle/references/create-pr.md#seeing-and-fixing-linkage-on-an-open-pr) misread as a write bug. Still also put the ticket key in the PR **title** regardless — Jira Link Check auto-repairs the marker from the title on the next CI run if it's ever missing or malformed for an unrelated reason, and degraded mode has no `legacy-sports-github` connector to fall back on for a manual fix.
6. Validate: Bash `make pc-<chunk>` with `run_in_background: true`, one chunk per call, canonical order, waiting for each completion notification. `pnpm exec nx affected -t <target> --base=origin/main` also requires `run_in_background: true` (same hook).
7. Self-review, then mark ready: `mcp__github__update_pull_request({ draft: false })`.
8. Jira → In Review: `transitionJiraIssue({ ..., transition: { id: "2" } })`.
9. Watch review events (surfaced natively — no polling). Cycle-1 clean → merge via `mcp__github__merge_pull_request({ mergeMethod: "squash" })` if loaded, else ask the user.

## Claude Code Remote (CCR)

A fourth configuration, distinct from the three in [Step 0](#step-0-identify-your-platform): the managed remote execution product described in this session's own system prompt ("Your current remote execution environment"), reached via a dedicated `mcp__Claude_Code_Remote__*` server (`create_session`, `create_trigger`, `list_repos`, `add_repo`, `send_later`, `subscribe_pr_activity`, etc.) — **not** the `ccd_session` server that hosted "chip dispatch" sessions use. Identify it by: `mcp__Claude_Code_Remote__*` tools present; `mcp__ccd_session__spawn_task` and `nx_run_pc_chunk` both absent (confirm with `ToolSearch`); hosted `legacy-sports-{jira,github,ci}` connectors and built-in `mcp__github__*` present (same as Connector CC web). Only the chip-dispatch gap below is verified for CCR — everything else in this file (spine bindings, validation, Jira transition IDs) is unconfirmed here. In particular, do **not** assume Connector CC web's `nx_run_pc_chunk` validation binding — that tool is absent by definition in CCR (see the Step 0 check above); until verified, the safer assumption is Default CC web's degraded validation path (Bash `make pc-<chunk>` in background, one chunk at a time). Verify each capability against the tools actually present in your session rather than assuming any platform's full binding, and update this section with what you find.

### AWS/Packer tools non-functional in CCR (LS-9537, LS-8736)

`legacy-sports-aws` connects normally in a CCR session — schemas load via `ToolSearch`, tool calls execute rather than timing out — but every `aws_*`/`packer_*` tool still fails, because the server implementation shells out to the `aws`/`terraform` CLI binaries and neither is installed on PATH in this environment. This is distinct from Copilot/CC-web, where no AWS credentials exist at all; here the server tries to run and simply can't find the binary.

As of LS-9537 this surfaces as an actionable error naming the missing binary and the CCR limitation, not the raw `spawn aws ENOENT` Node throws by default — but the underlying capability gap is real, not just a confusing error message. There is no in-session workaround: don't retry `aws_*`/`packer_*` calls expecting a different result, and don't burn time re-diagnosing "aws: not found" as a startup race (a server disconnect/reconnect does not change the outcome). Fall back to what the deploy/CI run itself reports (e.g. a Terraform apply output or `aws` invocation in the GitHub Actions log) for anything that would otherwise need direct AWS-side verification (EC2/AMI inspection, log tailing via `aws_logs_tail`, etc.). Full detail: [mcp-first § AWS Operations](../mcp-first/SKILL.md#aws-operations).

Baking the `aws`/`terraform` CLIs into the CCR base image, or migrating `aws-server`'s ~20 tool implementations off the CLI onto the AWS SDK for JS directly, are both CCR-platform/large-refactor changes outside a single ticket's reach — this section is the documented-fallback half of LS-8736, not the fix.

### Chip dispatch substitute (LS-8510)

[work-ticket leaf-mode step 4](../work-ticket/references/leaf-mode.md) requires spawning a chip via `mcp__ccd_session__spawn_task` whenever a follow-up ticket is filed mid-implementation. That tool does not exist in CCR sessions and `ToolSearch` cannot locate it (confirmed LS-8510) — a platform capability gap in this product surface, not a repo bug to route around.

**Current compliant behavior**: file the follow-up ticket and add a one-line note (description or `jira_add_comment`) that it needs manual pickup — do not stop the current ticket to work it. leaf-mode.md step 4 branches to this fallback for CCR sessions; it satisfies the "MANDATORY" contract without a dispatch primitive.

**VERIFIED substitute (LS-9597)**: `mcp__Claude_Code_Remote__create_session({ prompt, title, source_url })` spawns a real independent session in this environment. Confirmed end-to-end 2026-08-23: `session_01QxoS5F8SPKkL991oHP3sMX` was created from a CCR session, consumed its `prompt`, ran a turn, and reported back (`post_turn_summary`, `usage.output_tokens: 270`). `environment_id` is optional — it inherits the caller's environment; pass it only to target a different one.

**`source_url` is mandatory.** Omitting it produces a session that dies before its first turn while the call still returns success — see the failure mode below. This is the single reason the earlier chip fan-outs appeared to "never work".

Two caveats before relying on it. First, whether this satisfies [leaf-mode](../work-ticket/references/leaf-mode.md) step 4's dispatch contract is a separate decision — that file still branches CCR sessions to the file-a-ticket-and-note-it fallback, and changing that branch is its own change, not implied by this verification. Second, `create_session` can fail with `failed to create session: the service is temporarily unavailable — try again`, which is [VM allocation capacity](https://code.claude.com/docs/en/claude-code-on-the-web#session-creation-failed), not a caller error: it reproduces with any payload, in any environment, and with or without `source_url`. Retry rather than rewriting the call — see the bounded protocol below for how long.

### `create_session` outage: bounded retry protocol, not blind retry (LS-9639)

There is no `mcp__Claude_Code_Remote__*` health-check or status tool that distinguishes "transient blip, retry in 30s" from "down for hours, stop retrying" — the `the service is temporarily unavailable` string carries no error code, no `retryAfter`, no incident ID. That tool surface is the hosted CCR platform, not one of the 10 in-repo MCP servers this repo can patch (see [gaps.md](../mcp-first/references/gaps.md#phase-2-triage-quick-reference)), so the fix here is a bounded, documented protocol rather than a tool change.

Three independently observed outages set the bounds: 7 retries over ~2h (self-recovered), 5 retries over ~90min (self-recovered), 5 retries over ~15min (never recovered in-session). Recovery, when it happens, has taken tens of minutes to ~2 hours — never seconds.

**Do not blind-loop the retries in-context** — that violates the [never-poll rule](../mcp-first/references/waiting-and-wakeups.md#the-rule) the same way an in-context `ci_view_run` loop would. Use the same chained-one-shot mechanism as the [Periodic Wake Protocol](../mcp-first/references/waiting-and-wakeups.md#periodic-wake-protocol):

1. On first `create_session` failure, retry once immediately (covers true one-off blips).
2. Still failing → `send_later({ delay_minutes: 20, message: "retry create_session for <ticket/purpose>" })` and end the turn. Re-arm on each subsequent failure, same as the wake protocol's re-arm invariant — never more than one outstanding reminder.
3. **Cap at 6 retries (~2h elapsed, matching the longest observed self-recovery).** If still failing at the cap, stop — per AGENTS.md's chip-dispatch rule ("if unavailable, stop and inform the user") — do the work directly in the current session instead of dispatching a chip, and note the outage (duration, attempt count) in the ticket or PR so the next audit has data.
4. A success after a prior failure needs no special handling — just proceed; there is no lingering half-broken state to detect.

**Also available, confirmed but unnecessary**: `create_trigger({ name, prompt, create_new_session_on_fire: true, run_once_at: "<RFC3339>" })` spawns a fresh session once and then self-disables (`ended_reason: "run_once_fired"`). That self-disable is not an incidental observation — it is the documented contract for one-off schedules ([routines docs](https://code.claude.com/docs/en/routines#schedule-a-one-off-run): "After the routine fires, it auto-disables and the web UI marks it as **Ran**"). Structurally close to a one-shot `spawn_task`, but `create_session` is verified end-to-end and does not depend on a future firing time — prefer it.

### Trigger lifecycle: never call `delete_trigger` (LS-9648)

`delete_trigger` **cannot be auto-approved, in any session, by any configuration.** Its permission prompt offers only "Deny" / "Allow once" with no "don't ask again" — the signature of an MCP tool whose server sets `_meta["anthropic/requiresUserInteraction"]: true`. Per the [MCP docs](https://code.claude.com/docs/en/mcp#require-approval-for-a-specific-tool), such a tool prompts on every call "even in `acceptEdits`, `auto`, and `bypassPermissions` permission modes… Allow rules that match the tool don't skip the prompt either", and in `dontAsk` mode is **denied** instead. Adding it to `permissions.allow` in [`.claude/settings.json`](../../../.claude/settings.json), changing permission mode, and returning `"allow"` from a hook therefore all fail. Do not spend a ticket trying.

That is also a simpler explanation for the LS-8381 half of [Quirk 5](#quirk-5-askuserquestion-can-fail-outright-in-any-autonomous-session-not-just-webhook-subscribed-ones) than shared-plumbing failure: in an unattended session the by-design forced prompt has nowhere to land, so the call dies rather than prompting.

**The fix is to not call it.** A one-off trigger consumes itself; the other trigger types do not:

| Trigger type            | Self-consumes on fire?                | How to stop it from an agent session                   |
| ----------------------- | ------------------------------------- | ------------------------------------------------------ |
| `run_once_at` (one-off) | **Yes** — auto-disables, marked `Ran` | Nothing. Let it fire.                                  |
| Recurring schedule      | No — fires on its cadence forever     | `RemoteTrigger action: "update"`, `{ enabled: false }` |
| API (`/fire` endpoint)  | No — persists until revoked           | Same, or revoke the token on the web                   |
| GitHub event            | No — persists                         | Same                                                   |

A fired one-off is inert: it will not re-fire, and one-off runs do not count against the daily routine run cap. What remains is cosmetic clutter at [claude.ai/code/routines](https://claude.ai/code/routines), safe to bulk-clean by hand from a browser — where no agent permission prompt is in the loop. Unlike `delete_trigger`, the `update` path takes the ordinary permission route and **is** allowlistable as `mcp__<server>__update_trigger`.

One caveat when substituting a trigger for a wake-up: `create_new_session_on_fire: true` starts a **fresh** session carrying the trigger's saved prompt — it does not resume the current one, and that session starts cold. Write the prompt to stand alone, per [subagent-templates](../subagent-templates/SKILL.md).

### Known failure mode: `create_session` without `source_url` produces a dead session, reported as success (LS-9597)

**Symptom**: the call returns a session ID and `SESSION_STATUS_PENDING` — indistinguishable from success — and the session then does nothing at all. It never runs a turn, never pushes a branch, never reports back.

**Detection** (`get_session` / `list_sessions` on the spawned ID):

| Field                         | Dead session                                                                                  | Healthy session                  |
| ----------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------- |
| `session_context.sources`     | key absent                                                                                    | `[{git_repository: {url: ...}}]` |
| `updated_at - created_at`     | ~3 seconds                                                                                    | tens of seconds or more          |
| `usage` / `post_turn_summary` | absent                                                                                        | populated                        |
| `last_init_error`             | sometimes `{error_kind: "init_script", message: "Setup script failed", recoverable: "false"}` | absent                           |

Note the `last_init_error` is only _sometimes_ retained — 2 of the 29 known-bad sessions carried it, the other 27 showed nothing but the 3-second lifetime. **Absence of an error is not evidence the session is alive**; check `sources` and the lifetime instead.

**Mechanism**: the cloud environment's setup-script field invokes this repo's script by absolute path — `source "$HOME/legacy-sports/.claude/cloud-setup.sh"`. With no `source_url` no repo is cloned, so that path never exists and `source` fails immediately. The script is _sourced_, not executed, and sets `set -euo pipefail`, so the failure kills the setup shell rather than returning nonzero; the repo-root guard near the top of the script (`.git` + `package.json` present, else `exit 1`) would do the same for a partial checkout. Both guards are correct — the defect is that a missing parameter becomes an invisible death rather than a visible error.

**Fix**: pass `source_url` on every spawn. To make the failure legible when someone forgets, the environment's setup-script field can be guarded (environment config UI, not a repo file — see LS-9597):

```bash
if [ -f "$HOME/legacy-sports/.claude/cloud-setup.sh" ]; then
  source "$HOME/legacy-sports/.claude/cloud-setup.sh"
else
  echo "WARNING: no repo checkout at $HOME/legacy-sports — skipping cloud-setup.sh."
  echo "This session was very likely created without source_url and cannot do repo work."
fi
```

### Known failure mode: hosted `legacy-sports-github`/`legacy-sports-jira` OAuth expires mid-session on long-running watch-to-merge loops (LS-8924)

**Symptom**: partway through a long `/work-ticket` watch-to-merge loop — spanning CI retries, review cycles, and possibly multiple [container restarts](#known-failure-mode-container-restarts-silently-kill-in-flight-background-bash-jobs-no-resume-ls-8937) over real-world days — every `mcp__legacy-sports-github__*` and `mcp__legacy-sports-jira__*` call starts failing:

```
The following MCP servers require authentication before their tools can be used:
legacy-sports-github
legacy-sports-jira

This session is non-interactive, so Claude cannot run the OAuth flow here.
```

**Root cause**: the same OAuth token expiry as [Mid-Session 401 / Token Expiry (LS-4874)](../mcp-first/references/diagnostics.md#mid-session-401--token-expiry-ls-4874). That section's general recovery — stop, surface the re-consent prompt, wait for the user to `/mcp` — assumes a human is attending the session. A CCR watch-to-merge loop is deliberately unattended for the exact multi-hour-to-multi-day spans that make expiry likely, so waiting on a human response is not actionable: there is no one to answer within any useful window.

**CCR-specific recovery — do not stop and wait; fall back to the generic connectors and keep driving to merge:**

1. Note the auth failure once (PR comment or continuation-plan checkpoint), then switch to the generic equivalents for the rest of the PR lifecycle. If the PR itself has not been created yet, `mcp__github__create_pull_request` is fine for the `jira-link` marker too — despite recurring reports to the contrary it does not strip the hand-authored comment (LS-8694, [full writeup](../pr-lifecycle/references/create-pr.md#jira-link-check-repairs-the-marker-for-you-ls-9279)); still put the ticket key in the title as well, per the [CCR fallback](../pr-lifecycle/references/create-pr.md#ccr-fallback--hand-authoring-the-marker-no-jirakey-convenience):
   - `github_mark_pr_ready` → `mcp__github__update_pull_request({ draft: false })` **then** `mcp__github__issue_write({ method: "update", issue_number: N, labels: [...] })` adding `bot:ready-for-review` to the PR's **current** label set — read it first via `mcp__github__pull_request_read`, since `issue_write` replaces the whole label list (same caveat as the [Default CC web trigger-label fallback](#what-is-genuinely-unexecutable-in-degraded-mode-and-the-fallback-per-case)).
   - Re-triggering the Reviewer Bot after a fix-push (normally `github_manage_labels` re-add) → remove `bot:ready-for-review` then re-add it via two `issue_write` calls; re-adding an already-present label alone is a no-op and won't refire the `labeled` webhook.
   - `FIX:`/`JUSTIFY:` replies → `mcp__github__add_reply_to_pull_request_comment`; resolving threads → `mcp__github__resolve_review_thread` (needs GraphQL thread node IDs — same gap as [degraded CC web](#what-is-genuinely-unexecutable-in-degraded-mode-and-the-fallback-per-case) if no read path surfaces them in your session).
   - `jira_transition` → `mcp__Atlassian__transitionJiraIssue({ cloudId: "fb294606-6c8f-4b52-9a41-11fe45b77528", transition: { id } })` using the [static transition ID table](#discovering-transition-ids). The plugin path has no monotonic guard, so check the current status via `searchJiraIssuesUsingJql` before transitioning.
   - Filing/commenting on follow-up tickets → `mcp__Atlassian__createJiraIssue` / `mcp__Atlassian__addCommentToJiraIssue`.
2. Merging still works without the hosted connector: `mcp__github__merge_pull_request` (built-in) or ask the user if it isn't loaded.
3. **Do not retry the hosted-connector calls once this symptom appears** — there is no mid-session auto-refresh (see [Auth Model](../mcp-first/SKILL.md#auth-model)), so every retry just burns a tool call. Switch to the fallback on the first failure, not after several.

**Not fixable in this repo as a token-lifetime change** — OAuth TTL for hosted connectors is claude.ai connector-layer/platform configuration, outside `bkrupa/legacy-sports`'s reach (same class as [Quirk 6](#quirk-6-stop-hook-git-checksh-false-positives-unverified-on-genuinely-ssh-signed-commits-ls-8589)). ### Known failure mode: stale Nx project-graph cache blocks every `nx` invocation (LS-8936)

**Symptom**: any direct `nx` invocation — `node_modules/.bin/nx run <project>:<target>`, `pnpm exec nx run-many`, etc. (CCR has no `nx_run`/`nx_run_pc_chunk` MCP tools per the platform note above, so direct CLI is the only path) — fails before the target ever runs, with `NX   Failed to process project graph.` followed by a `Cannot find module '<something>'` from one of Nx's project-graph plugins (`@nx/jest`, `@nx/eslint`, `nx/js/dependencies-and-lockfile`). Three distinct signatures have been observed across separate CCR sessions, all with the same root cause:

- `Cannot find module 'react-native/jest-preset'` — `@nx/jest/plugin` resolving `apps/app/jest.config.ts`.
- `pnpm lockfile detected, but ".../node_modules/.modules.yaml" is missing` — `nx/js/dependencies-and-lockfile`.
- `Cannot find module '@typescript-eslint/type-utils'` — `@nx/eslint/plugin` resolving `eslint.config.mjs`.

Because Nx's project-graph plugins eagerly resolve config/module state for **every** project in the workspace before any target runs, a single stale entry anywhere breaks `nx run <any-project>:<target>` repo-wide, not just the project the missing module belongs to. This is easy to misdiagnose as a real dependency problem — the referenced module (`react-native`, `.modules.yaml`, `@typescript-eslint/type-utils`) may in fact be present and correctly installed on disk; the failure is a **stale `.nx/workspace-data` graph cache**, not (necessarily) a broken install. Confirmed directly: after hitting the `@typescript-eslint/type-utils` signature with the package fully present in `node_modules`, `pnpm install --frozen-lockfile` alone did **not** fix it, but `rm -rf .nx/cache .nx/workspace-data` did — the very next `nx run` succeeded against the same, unchanged `node_modules`.

**Root cause (unconfirmed but consistent with all observed evidence)**: the CCR container image bakes a pre-warmed `.nx/workspace-data` graph cache against the `node_modules` state at image-build time. If the container's `node_modules` is finalized or adjusted after that (e.g. a provisioning-time `pnpm install` step, or any other post-snapshot change), the cache references a `node_modules` layout that no longer matches disk — and whichever plugin happens to touch the drifted package first is the one that throws. This explains why the specific missing module differs session to session: it's whatever changed between image build and container boot, not a single fixed broken dependency. This is a distinct failure signature from the present-but-corrupted `node_modules` mode documented above under [phantom typecheck/lint errors on unrelated files (LS-8384)](#known-failure-mode-phantom-typechecklint-errors-on-unrelated-files-ls-8384) for local persistent containers — that one is fixed by `modules-pool/link.mjs` rebuilding the install; this one is fixed by rebuilding Nx's cache, not the install.

**Recover**: `rm -rf .nx/cache .nx/workspace-data` (both are gitignored, safe to delete, rebuilt automatically on the next `nx` invocation), then retry the `nx` command. Do this **first**, before spending a diagnostic pass on the specific missing module named in the error — the module is very likely a red herring. Only fall back to `make install` (preferred — see below) or raw-binary invocation (`tsc --noEmit`, `jest`, `eslint`, `prettier --check` directly, bypassing `nx` — the sanctioned CCR fallback given no `nx_run_pc_chunk` tool exists here) if the graph is still unbuildable after the cache clear.

**If the cache-clear alone doesn't resolve it, prefer `make install` over a bare `pnpm install --frozen-lockfile` (LS-9577).** A plain `pnpm install --frozen-lockfile` in a network-sandboxed CCR container commonly fails outright on puppeteer's postinstall Chrome download (`Failed to set up chrome vXXX.X.XXXX.XX! ... Set "PUPPETEER_SKIP_DOWNLOAD" env variable to skip download`), aborting the install before `node_modules/.modules.yaml` gets written — which reproduces the exact `.modules.yaml is missing` signature this section documents, now as a genuine half-install rather than a stale cache. `make install`'s non-Windows branch now sets `PUPPETEER_SKIP_DOWNLOAD=1 PUPPETEER_SKIP_CHROMIUM_DOWNLOAD=1` before calling `pnpm install --frozen-lockfile`, so the Chrome download no longer aborts the install; Chromium is pre-installed at `/opt/pw-browsers` in these containers, so skipping the download costs nothing. If invoking `pnpm install` directly for any reason, set those two env vars yourself.

**Self-heal shipped for the MCP path (LS-8936)**: on platforms where `mcp__legacy-sports-nx__nx_run`/`nx_run_pc_chunk` **are** available (Copilot, Connector CC web — not CCR), `runNx()` in `tools/mcp/nx-server/src/run-command.ts` now detects the `Failed to process project graph` signature, clears `.nx/cache`/`.nx/workspace-data` once, and retries automatically — no manual intervention needed there. CCR has no equivalent MCP tool to patch, so the manual recovery above is the durable guidance for this platform.

## Container timeout resilience

Cloud containers can be reaped mid-run — most often during validation. The spine's ordering already absorbs this: branch pushed → draft PR → checkpoint comment → **then** validate, so a reap during a `pc-*` chunk loses nothing. The gate that still holds: **all seven chunks green before mark-ready** — a draft PR existing earlier is inert (CI and the Reviewer Bot are gated on `draft == false`).

The spine's tracking-task graph (Step 1c) is what survives compaction: with the validation task `blockedBy` the draft-PR task, an agent that loses prose context cannot reorder the gates. See [Read first](../workflow-overview/references/ticket-to-merge-spine.md#read-first-why-ordering-breaks-and-what-actually-holds-it).

**Checkpoint**: where the `legacy-sports-dev-process` stdio server is loaded (local only — it is in no cloud configuration), use `continuation_post` / `continuation_status`. In every cloud mode, post/read the checkpoint as a PR comment whose first line is `<!-- continuation-plan -->` ([artifact format](../dev-process/artifacts/continuation-plan.md)). **Resuming after a reap**: fresh container reattaches to the branch, reads the most recent `<!-- continuation-plan -->` comment, and continues from "what's left" — never restart from zero. A stalled-mid-validation session is what [/recover-stall](../../../.claude/commands/recover-stall.md) recovers.

> Distinct from [Cloud-to-Local Teleport](#cloud-to-local-teleport) (capability gap); this section handles the time gap.

### Known failure mode: container restarts silently kill in-flight background Bash jobs, no resume (LS-8937)

**Symptom**: a long-running `run_in_background: true` Bash job (most often a `make pc-<chunk>` validation chunk, e.g. `pc-lint`) is in flight when the container restarts. The restart kills the job with no error, no partial-progress marker, and no proactive notification at restart time — the only signal is a reactive `<system-reminder>` ("The container was restarted... background tasks were running and are now stopped") delivered on the _next_ turn. If a `ScheduleWakeup` was already armed expecting the job to still be running, that wakeup fires and finds nothing — the wait was spent on a job that no longer exists.

**Root cause**: `run_in_background` Bash processes have no persistence or checkpoint/resume mechanism across a container restart; only the git working tree survives (confirmed safe — restarts do not lose committed or pushed work, verified via `git status`/`git log` after every restart). There is currently no proactive push at the moment of restart, only the reactive notification on next tool use.

**Guidance**:

- Keep `pc-*` chunk background jobs **short and checkpointed** — run one chunk at a time in the canonical order (never a monolithic `make pc`) so a restart mid-chunk only costs that one chunk's re-run, not the whole validation pass. This is already the mandated degraded-mode path (see [Validation binding](#validation-binding-safety-critical--read-before-running-anything)); the restart risk is another reason to never batch chunks into one background call.
- **After any restart notification, before assuming a job is still progressing**: always re-verify `git status` (confirm the working tree/branch state you expect) and re-tail or re-check the job's log/output immediately — do not trust a previously scheduled wakeup's assumption that the job is still running. Treat the notification as "the job is gone until proven otherwise," not "the job might still be fine."
- If the job was a `pc-*` validation chunk, just re-launch that one chunk in the background again — cheaper than discovering three restarts in via repeated full re-runs.
- Investigated but not pursued in LS-8937: proactive restart notification and background-job persistence/resume (the ticket's options a/b) both require platform/session-image changes outside this repository's reach — no in-repo hook, MCP tool, or script controls background-job lifecycle across a CCR container restart. This section (option c) is the documentation-only mitigation; if a persistence or proactive-notification primitive is ever added platform-side, update this entry to point to it instead.

## GitHub identity and auth

Two GitHub Apps split duties: **Agent Author** (App ID `3158619`) writes code, pushes, opens PRs; **Agent Reviewer** (App ID `3142924`) approves and merges (verified in `.github/actions/resolve-runner-label/action.yml`). The same app never both authors and approves.

| Platform         | GitHub auth                                                                                                                                  |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Copilot          | Agent Author app token minted by `copilot-setup-steps.yml`, exported as `GH_TOKEN`/`GITHUB_TOKEN` — bot-attributed authorship                |
| CC web (both)    | Built-in `mcp__github__*` via Claude's native GitHub connector — no token config, bot identity. Never route PR authorship through a user PAT |
| Hosted connector | `legacy-sports-github` Lambda holds its own credentials server-side (Secrets Manager); the client sends only the OAuth/Cognito bearer        |

### Mark-ready and the review trigger label

`bot:ready-for-review` is the review trigger label. Verified against `.github/workflows/review.yml`: the Reviewer fires on `opened`/`ready_for_review`, and re-fires on `synchronize` **only when `bot:ready-for-review` (or the bot-owned `merge-when-ready`) is present**. Consequences:

- `github_mark_pr_ready` (hosted server) flips draft **and** applies the label — one call, done.
- Built-in `mcp__github__update_pull_request({ draft: false })` flips the draft flag **only**. Follow it with `github_manage_labels({ prs: [N], add: ["bot:ready-for-review"] })` wherever that tool exists. Without the label, Cycle 1 fires but fix-pushes never re-trigger review — Cycle-1 mandates stall permanently.
- Degraded mode cannot apply the label — see the [degraded fallback table](#what-is-genuinely-unexecutable-in-degraded-mode-and-the-fallback-per-case).

## Known cloud-environment quirks

Environment behaviors that look like bugs but are not. Recognize the symptom and switch strategy without declaring yourself blocked.

### Quirk 1: `legacy-sports-jira` stdio server `fetch failed` (Claude Code on the web only)

**Symptom**: every `jira_*` call from a _stdio_ jira server returns `fetch failed`, while `jira_auth_status` misleadingly reports `{"configured": true}`. **Root cause**: the CC-web session proxy blocks HTTPS egress to `api.atlassian.com` (CONNECT 403); credentials load fine but outbound calls die. **Fix**: switch to the Atlassian plugin immediately (primary path on CC web — see [Jira binding](#jira-binding)). Does not apply to the hosted jira Lambda (its egress happens on AWS) — Copilot and connector sessions are unaffected.

### Quirk 2: Atlassian plugin `transitionJiraIssue`/`createJiraIssue` reject nested-object parameters on cold start

**Symptom**: `MCP error -32602 ... "expected": "object", "received": "string", "path": ["transition"]` (or `["additional_fields"]`) on a correctly-formed call. Cold-start only; `editJiraIssue`/`createIssueLink`/`addCommentToJiraIssue` accept the same shapes concurrently. **Fix**: retry once after any other successful plugin call (~30s of activity warms it). `createJiraIssue.additional_fields` can stay broken longer — avoid it (parent-setting alternatives in [Jira binding](#jira-binding)). If a transition still fails: hosted `jira_transition` where attached; otherwise ask the user to transition in the Jira UI. Distinct from the never-resolves mistake of passing `transition` as a string.

### Quirk 3: `ci_get_logs` returns step summaries instead of full log text in cloud sessions

**Symptom**: output begins `[Log download unavailable: ... results-receiver.actions.githubusercontent.com ... blocked ...]` followed by per-step ✓/✗ conclusions. **Root cause** (LS-3040): GitHub's log endpoint 302-redirects to a host the cloud proxy blocks; the server intentionally falls back to step conclusions. You can see _which_ step failed, not _why_. **Fixes**: `ci_view_run(runId)` returns a `url` the user can open; or get logs from a local session.

### Quirk 4: `ci_dispatch_workflow` returns 403 in cloud — AGENT_AUTHOR_APP lacks `actions:write`

**Symptom**: `Cannot dispatch workflow ...: the GitHub App token lacks actions:write permission (HTTP 403)` / `Resource not accessible by integration`. **Root cause**: the Agent Author installation has `contents:write` + `pull_requests:write` but not `actions:write`; the dispatch endpoint requires it — permissions gap, not auth failure. **Do not loop-retry.** Alternatives: (1) empty commit to re-trigger (`git commit --allow-empty -m "chore: trigger merge queue (LS-####)" && git push`, or `worktree_commit`+`worktree_push` on Copilot); (2) remove/re-add the triggering label; (3) wait — the merge queue retries on its own cycle. **Waiting for CI**: CI and review events surface natively in Claude Code — continue with other work; never sleep+poll. For non-PR `workflow_dispatch` runs (no push notification), use `ci_dispatch_workflow({ ..., waitForCompletion: true })` where the CI server is attached (see AGENTS.md).

### Quirk 5: `AskUserQuestion` can fail outright in any autonomous session, not just webhook-subscribed ones

**Symptom** (LS-8378, broadened by LS-8400): `AskUserQuestion` fails immediately with `Tool permission stream closed before response received` — not a timeout, the call never completes. First observed (LS-8378) in a session with an active `github-webhook-activity` PR subscription while PR events were arriving concurrently, and originally suspected as contention between the webhook event channel and the interactive prompt channel. LS-8400 reproduced the identical error text in a plain autonomous session with **no** webhook subscription active — twice in a row, mid-decision on a rejected-push force-vs-new-commit choice — ruling out webhook contention as the sole cause. The same error string also hit the unrelated `delete_trigger` MCP tool (LS-8381, a stdio tool call with no interactive channel at all) — but that half is weaker corroboration than it first appeared (LS-9648): `delete_trigger` is flagged `requiresUserInteraction` and forces a permission prompt on **every** call by design, so an unattended session fails it for that reason alone, without any plumbing bug. See [Trigger lifecycle](#trigger-lifecycle-never-call-delete_trigger-ls-9648). The `AskUserQuestion` reproductions still point to permission-prompt plumbing shared across tool types in the core harness — not something fixable from this repo (LS-8381 was closed `Won't Do` on that basis). Treat this as a known limitation of autonomous/background-driven sessions generally (webhook-subscribed PR watches, Routines, dispatched chips, and plain unattended sessions alike), not something to retry through. **Do not retry in a loop.** Fallback and full protocol: [drive.md "AskUserQuestion may be unavailable in autonomous sessions"](../pr-lifecycle/references/drive.md#askuserquestion-may-be-unavailable-in-autonomous-sessions) — proceed with documented reasoning (PR comment + Jira note), or escalate via the "Genuine human-only blocker" terminal state instead of a blocking prompt.

### Quirk 6: `stop-hook-git-check.sh` false-positives "Unverified" on genuinely SSH-signed commits (LS-8589)

**Symptom**: after `git commit --amend` (or any local rewrite that keeps `upstream..HEAD` non-empty), the Stop hook fires: "There are commit(s) on branch '...' that GitHub will show as Unverified (missing signature, or committer email is not noreply@anthropic.com)" — even though `git cat-file commit HEAD` shows a populated `gpgsig` block and GitHub does show the commit as Verified once pushed. `git log --format='%G?' -1` reports `N` for the flagged commit.

**Root cause**: the hook (`~/.claude/stop-hook-git-check.sh` — a CCR-platform file, **not** tracked in this repo; confirmed absent from `.claude/hooks/` and `.claude/settings.json`) treats `%G? == "N"` as "unsigned." In this image, `gpg.format` is `ssh`, `gpg.ssh.program` is `/tmp/code-sign` (a remote-signing helper), and `commit.gpgsign=true`, but `gpg.ssh.allowedSignersFile` is unset and the only local pubkey (`~/.ssh/commit_signing_key.pub`) is empty (0 bytes) and owned by a different user than the session UID. With no signers file, git has no key to verify against — reproduced directly (isolated throwaway repo, same global signing config): `git verify-commit` prints `error: gpg.ssh.allowedSignersFile needs to be configured and exist for ssh signature verification`, and `%G?` reports `N` even though the commit's raw object has a valid `gpgsig` header. `%G?==N` is therefore ambiguous here between "actually unsigned" and "signed but unverifiable locally" — the hook's own guardrail comment assumed the latter case reports `B`/`U`/`E`, which holds for `gpg.format=gpg` but not for `gpg.format=ssh` with no signers file.

**Not fixable in this repo**: the buggy script lives entirely outside `bkrupa/legacy-sports` (not mirrored under `.claude/hooks/`), so no PR here can change its detection logic — and an agent patching a security-verification hook's live file outside the repo boundary is correctly blocked by the environment's own safety classifier, not a restriction to route around. The other candidate fix — provisioning a real `gpg.ssh.allowedSignersFile` + non-empty pubkey in the session image — is also infra-only: `/tmp/code-sign` only implements `-Y sign` (confirmed via `--help`), it has no way to export its public key for a session to build a signers file itself. Both fixes require a change to CCR's session-image/platform provisioning, not to this codebase.

**Do not misdiagnose this as a real signing failure and do not bypass signing to silence it** — `--no-gpg-sign` is explicitly forbidden by AGENTS.md, and the commit is in fact validly signed. **Recognize and proceed**: `git cat-file commit HEAD | grep '^gpgsig'` — a populated block means the commit is genuinely signed and this is the known false positive; the warning stops on its own once the branch is pushed (`upstream..HEAD` becomes empty), not because anything about the signature changed.

### Quirk 7: `bkrupa.github.io` `CONNECT` blocked by the CCR egress proxy (cloud/remote sessions)

**Symptom**: `WebFetch(url: "https://bkrupa.github.io/...")` returns a bare `HTTP 403 Forbidden` with no body; an equivalent `curl -sSL` fails with `curl: (56) CONNECT tunnel failed, response 403`. `curl -sS "$HTTPS_PROXY/__agentproxy/status"` (or the CCR proxy status endpoint on other ports) shows a `recentRelayFailures` entry with `"kind": "connect_rejected"` and `"host": "bkrupa.github.io:443"`.

**Root cause**: `bkrupa.github.io` (the GitHub Pages host serving `bkrupa/legacy-sports-deploys`, used as a direct-URL fallback for Playwright reports — see [read-playwright-report](../read-playwright-report/SKILL.md)) is not on the session's outbound egress allowlist. Per the CCR proxy's own README (`/root/.ccr/README.md`): "403 / 407 from the proxy: The destination host is not allowed by your organization's egress policy for this session. Do not retry or route around it — report the blocked host." That allowlist is CCR platform/session-image configuration, not application config — confirmed by an exhaustive repo search (`terraform/`, `.github/`, `.claude/`, `docs/`) turning up no allowlist, proxy-CONNECT, or egress-policy file anywhere in `bkrupa/legacy-sports` (LS-8556).

**Not fixable in this repo**: same class as [Quirk 6](#quirk-6-stop-hook-git-checksh-false-positives-unverified-on-genuinely-ssh-signed-commits-ls-8589) — the policy that rejects the `CONNECT` lives entirely outside this repository's boundary, so no PR here can add a host to it.

**Fix**: report the blocked host to your session administrator or Anthropic support (per the README's own guidance) so `bkrupa.github.io` (or `*.github.io` broadly, since every GitHub Pages site shares that host) can be added to the org's egress allowlist. Until that lands, do not spend time retrying the direct `bkrupa.github.io` `WebFetch`/`curl` fallback in cloud/remote sessions — it 403s unconditionally. Use the primary paths instead: `ci_get_playwright_report` (MCP tool), `ci_get_playwright_test_result(source: "s3")` for nightly/integration runs, or a local session where the `gh` CLI fallback still works.

### Quirk 8: a wedged GitHub Actions check-suite rejects every rerun/cancel path — only a genuine new commit unsticks it (LS-9116)

**Symptom**: a CI Orchestrator run gets stuck with one or more jobs `queued` for 30+ minutes (observed: 110+ minutes) after an upstream GitHub Actions hiccup (e.g. "Service Unavailable" during `Resolve Runner Label`). Every rerun/cancel path fails or no-ops:

- `ci_rerun({ runId })` → `Streamable HTTP error: ... "message":"Service Unavailable"`
- `mcp__github__actions_run_trigger({ method: "rerun_failed_jobs" | "rerun_workflow_run" })` → `403 This workflow is already running` — persistently, not the transient race `postWithRetryOnAlreadyRunning` already retries through (`tools/mcp/ci-server/src/github-api.ts`)
- `mcp__github__actions_run_trigger({ method: "cancel_workflow_run" })` → reports success, but the run's overall `status` stays `"queued"` (never `"completed"`/`"cancelled"`) and the stuck jobs keep `queued` for another hour+

**Root cause**: GitHub's own state machine for the check-suite is wedged upstream of anything the REST API's rerun/cancel endpoints can reach — they all defer to the same "already running" guard that a genuinely wedged run never clears. There is no lower-level GitHub Actions API to force this: `DELETE /repos/{owner}/{repo}/actions/runs/{run_id}` explicitly requires the run to already be in a terminal state, so it cannot be used to reset an in-progress/queued run either. This was investigated for a `ci_force_reset_run`-style addition to `legacy-sports-ci` and no viable GitHub API path was found — **not implementable as an MCP tool** without GitHub exposing a force-reset endpoint that does not currently exist.

**Confirmed workaround**: push a **genuine new commit with real content** (e.g. resolving an unrelated merge conflict, or any other real diff) — this reliably breaks the wedge and produces a clean run. **Empty commits do not work** (same "already running" guard applies) and **closing/reopening the PR does not work either** (it triggers auxiliary workflows but not the CI Orchestrator run itself). If no real change is pending, use the empty-commit trick from [Quirk 4](#quirk-4-ci_dispatch_workflow-returns-403-in-cloud--agent_author_app-lacks-actionswrite) first since it is cheaper — but be prepared to fall back to a real commit if the run is genuinely wedged rather than just needing a nudge.

**Do not loop-retry** the rerun/cancel MCP calls once a run has been stuck 15+ minutes with a persistent "already running" 403 — that is the wedge signature, not a transient race worth retrying through.

### Quirk 9: Auto Mode's permission classifier can block a legitimate single-shot `ci_list_runs`/`send_later` call (LS-8931)

**Symptom**: a single, non-looping `mcp__legacy-sports-ci__ci_list_runs(...)` or `mcp__Claude_Code_Remote__send_later(...)` call is denied outright with `"Blocked by classifier"` — even though the call is exactly the ONE-SHOT pattern this repo's own skills recommend (Rule 11 in [pr-lifecycle/SKILL.md](../pr-lifecycle/SKILL.md#quick-commands); the `send_later` check-in fallback in [drive.md](../pr-lifecycle/references/drive.md#askuserquestion-may-be-unavailable-in-autonomous-sessions)), not the `sleep N && gh pr checks` polling anti-pattern the classifier is presumably meant to catch.

**Root cause**: Auto Mode's tool-call permission classifier lives in the core Claude Code harness (the product surface described by this session's own "## Auto Mode Active" system reminder), not in this repository — confirmed by an exhaustive repo search (`.claude/hooks/`, `.claude/settings.json`, `tools/mcp/`) turning up no classifier, heuristic, or blocklist referencing `ci_list_runs` or `send_later` anywhere in `bkrupa/legacy-sports`. Its heuristic appears to key on the tool name alone rather than call frequency, so it can flag the first and only invocation in a session the same way it would flag a tight retry loop.

**Not fixable in this repo**: same class as [Quirk 6](#quirk-6-stop-hook-git-checksh-false-positives-unverified-on-genuinely-ssh-signed-commits-ls-8589)/[Quirk 7](#quirk-7-bkrupagithubio-connect-blocked-by-the-ccr-egress-proxy-cloudremote-sessions) — no PR against this codebase can change harness-side classifier logic.

**Fix / workaround**: do not loop-retry an identical call that was blocked by the classifier — a retry with the same arguments will not change its verdict. Treat the denial as a capability gap for that call, not a task blocker: fall back to the next-best signal already documented for each tool (native push-event/webhook delivery in place of a `ci_list_runs` snapshot; pure webhook-driven PR watching in place of a `send_later` check-in — but the wake cadence and classification still come from [waiting-and-wakeups](../mcp-first/references/waiting-and-wakeups.md), which is wake-source-agnostic by design), and continue the ticket. If the block recurs often enough to be disruptive, report it to your session administrator so the classifier's allowlist/heuristic can be tuned — that tuning happens on the harness side, not via a change here.

### Quirk 10: `legacy-sports-ci-local` (stdio) tools 401 "Bad credentials" against the raw GitHub REST API in CCR sessions, even with `GH_TOKEN`/`GITHUB_TOKEN`/`AGENT_AUTHOR_APP_PRIVATE_KEY` all present (LS-8740)

**Symptom**: a `legacy-sports-ci-local` tool that hits the GitHub REST API through `tools/mcp/ci-server/src/github-api.ts`'s own `fetch()` calls (e.g. `ci_retry_runner_flake({ prNumber })`) fails with `GitHub API 401: {"message": "Bad credentials", ...}` — for the same repo, same PR, same moment where the **hosted** `legacy-sports-ci` server's equivalent tool (e.g. `ci_retry_failed({ runId })`) succeeds. `env | grep -iE 'GH_TOKEN|GITHUB_TOKEN|AGENT_AUTHOR_APP_PRIVATE_KEY'` in the same session shows all three credential sources present and non-empty — this is not the "no token configured" case `resolveToken()` already has a clear error for (see the `getToken()` error text in `github-api.ts`).

**Root cause**: per the CCR watch-to-merge guidance already documented in AGENTS.md, "the network proxy injects real GitHub credentials only for the pinned `gh`/GitHub-MCP operations" — `legacy-sports-ci-local` is a stdio server making its own direct `fetch()` calls to `api.github.com` from inside the CCR container, which is outside that pinned set. The hosted `legacy-sports-ci` server never hits this: its credentials live server-side in Secrets Manager and its calls originate from AWS, never touching the CCR session's local network proxy at all. `resolveToken()`'s existing self-heal chain (LS-8551: env token → GitHub App key → `gh` CLI, each validated/retried on 401) cannot route around this, because the underlying limitation is which _outbound request shape_ the proxy honors, not which credential _value_ is used — every source in the chain is subject to the same gap in a CCR session.

**Not fixable in this repo**: same class as [Quirk 6](#quirk-6-stop-hook-git-checksh-false-positives-unverified-on-genuinely-ssh-signed-commits-ls-8589)/[Quirk 7](#quirk-7-bkrupagithubio-connect-blocked-by-the-ccr-egress-proxy-cloudremote-sessions)/[Quirk 9](#quirk-9-auto-modes-permission-classifier-can-block-a-legitimate-single-shot-ci_list_runssend_later-call-ls-8931) — the proxy's credential-injection scope is CCR platform/session-image configuration, not application config; no PR against `bkrupa/legacy-sports` can widen what the proxy authenticates. As a partial mitigation (LS-8740), `github-api.ts`'s and `http-retry.ts`'s GitHub-API error formatting (`formatGithubApiError`, gated on `CLAUDE_CODE_REMOTE=true` and a bare 401 only) now appends this Quirk's diagnosis and fallback directly to the thrown error text, so the failure is self-diagnosing on the next occurrence instead of a bare "Bad credentials" the caller has to research from scratch.

**Fix / workaround**: in a CCR session, don't retry a `legacy-sports-ci-local` tool that 401s this way — it will not succeed no matter which credential source resolves. Fall back immediately to the hosted `legacy-sports-ci` server for the same operation (e.g. `mcp__legacy-sports-ci__ci_retry_failed({ runId })` in place of `ci_retry_runner_flake({ prNumber })` — parse the run ID from the PR's "CI: Runner Flake" bot comment or label first), or to a built-in `mcp__github__*` tool where no hosted equivalent exists. Report the fallback per the [Reporting Protocol](../mcp-first/references/diagnostics.md#reporting-protocol) so it lands in the MCP gap audit rather than being silently absorbed.

### Quirk 11: `pwsh` is not preinstalled — `pnpm run test:scripts:ps` fails outright (LS-8729)

**Symptom**: editing `scripts/*.ps1` or `scripts/lib/*.ps1` (e.g. `scripts/lib/jira-rollup.ps1`, `scripts/sync-jira-status.ps1`) and then running `pnpm run test:scripts:ps` fails with `pwsh: command not found`. Unlike Chromium (preinstalled for Playwright — see the top-level environment notes), the Claude Code Remote Ubuntu image ships no PowerShell runtime. `make pc` / `pc-test` do not surface this either way (see the [`PC_HAS_PS1`](#validation-binding-safety-critical--read-before-running-anything) note below) — a green pipeline gives **no signal** on PowerShell-script correctness unless `pwsh` is installed and run manually.

**Root cause**: PowerShell is not part of the base Ubuntu image and is not installed by any repo setup script (`node scripts/modules-pool/link.mjs` only links `node_modules`); it must be fetched from the upstream PowerShell release feed on demand.

**Fix — install `pwsh` for the session** (Microsoft's supported binary tarball; no root/apt required, works under the CCR egress proxy):

```bash
curl -sSL -o /tmp/pwsh.tar.gz "https://github.com/PowerShell/PowerShell/releases/download/v7.4.6/powershell-7.4.6-linux-x64.tar.gz"
mkdir -p /tmp/pwsh && tar -xzf /tmp/pwsh.tar.gz -C /tmp/pwsh
chmod +x /tmp/pwsh/pwsh
export PATH="/tmp/pwsh:$PATH"   # session-scoped only; repeat per fresh container
```

Then `pnpm run test:scripts:ps` (or `pwsh -NoProfile -File scripts/__tests__/run-ps-tests.ps1`) runs normally. This is a per-session workaround, not a persistent install — the tarball and PATH change do not survive a container restart. If the download itself 403s or times out, that is the egress proxy blocking `github.com` release assets for this session (see the proxy README pattern in [Quirk 7](#quirk-7-bkrupagithubio-connect-blocked-by-the-ccr-egress-proxy-cloudremote-sessions)) — report the blocked host rather than retrying in a loop; there is otherwise no PowerShell-capable fallback for local `.ps1` validation in this environment.
