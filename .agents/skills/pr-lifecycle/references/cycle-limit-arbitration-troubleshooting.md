# Troubleshooting cycle-limit arbitration on `legacy-sports-review-bot`

When the bot posts a comment that begins with:

> [!IMPORTANT]
> **Human arbitration needed — review cycle limit (N) exceeded.**

…and applies the `needs-human-arbitration` label, it has decided the PR has exhausted the review cycle budget (default `MAX_CYCLE = 3`). The comment is generated by `buildCycleLimitArbitrationComment` in `.github/scripts/reviewer/index.mjs`.

The cycle counter is derived from immutable PR review history: `cycle = count(bot reviews) + 1`. Several review categories are excluded — see `.github/scripts/reviewer/lib/cycle-counter.mjs` for the canonical list.

## Symptom: arbitration fires with no extractable findings

The arbitration comment ends with:

> _No findings could be extracted from the last bot review body._

…meaning the bot picked the most-recent non-excluded review and its body had no parsable issue titles. **In a healthy PR cycle this should never happen** — the bot only escalates when there is a real review with mandates to adjudicate.

### Diagnosis: bot thread-reply artifacts are inflating the cycle count (LS-4474)

GitHub auto-creates a `review` entity with `state=COMMENTED` and an empty body every time something replies to an inline review thread via `POST /pulls/{n}/comments/{id}/replies`. The bot does this in two places:

1. `postReviewThreadReply(..., FORMAT_ERROR_MESSAGE)` — when an author's `FIX:`/`JUSTIFY:` reply is malformed (e.g. has trailing text after `FIX: <sha>`).
2. Future in-thread bot responses.

Each such reply creates one empty-body `COMMENTED` review by the bot. Prior to LS-4474 the cycle counter treated these as full review cycles. A single legitimate Cycle 1 review + two format-error replies → 3 bot reviews → `cycle = 4` → false arbitration on what was actually still Cycle 1.

**LS-4474 fix:** `isThreadReplyArtifactReview` in `cycle-counter.mjs` now excludes empty-body `COMMENTED` bot reviews from the count. Verify the fix shipped by inspecting `.github/scripts/reviewer/lib/cycle-counter.mjs` for the `isThreadReplyArtifactReview` helper.

### Diagnosis: reset signal lost to concurrency cancellation (LS-4474)

The reviewer workflow has `concurrency.cancel-in-progress: true`. Sequence that used to break things:

1. Admin applies `bot:reset-cycle-counter` → Run A starts with `CYCLE_RESET_SENDER` set.
2. Run A enters the admin-reset branch, removes the `bot:reset-cycle-counter` label, then begins the LLM call.
3. Author/admin (re-)applies `bot:ready-for-review` → Run B starts and cancels Run A.
4. Run B sees no `bot:reset-cycle-counter` label (Run A removed it) and `CYCLE_RESET_SENDER=''` (its triggering event is `bot:ready-for-review`).
5. Run B re-computes cycle from history → still over `MAX_CYCLE` → arbitration.

**LS-4474 fix:** The admin-reset branch now **dismisses** the prior bot reviews via `PUT /repos/{owner}/{repo}/pulls/{n}/reviews/{id}/dismissals` before doing anything else. Dismissal state is server-side and survives cancellation; the cycle counter already excludes `DISMISSED` reviews, so the surviving run sees `cycle = 1` from review history alone.

## How to recognize this state in the wild

You're hitting one of the LS-4474 failure modes when **all** of these are true:

- The bot posted an arbitration comment.
- The number of `CHANGES_REQUESTED` bot reviews on the PR is `< MAX_CYCLE` (typically just 1).
- `gh api repos/{owner}/{repo}/pulls/<PR>/reviews | jq '.[] | select(.user.login=="legacy-sports-review-bot[bot]") | {state, body_len: (.body // "" | length)}'` shows multiple empty-body `COMMENTED` reviews from the bot.
- Inline review threads on the PR include format-error replies from the bot ("Your reply could not be parsed — expected `FIX: <sha>` …").

## How to unblock (post-fix)

If the fix has merged and you still see the symptom (e.g. a PR that hit this before the fix shipped), the standard unblock works:

1. Confirm with `gh pr view <PR> --json reviews` that the `CHANGES_REQUESTED` count is below `MAX_CYCLE`.
2. Apply `bot:reset-cycle-counter` as a maintainer.
3. **Wait for the bot to dismiss prior reviews and post the cycle-reset NOTE comment** before re-applying `bot:ready-for-review`. The reset run takes ~5-10 seconds. Re-bouncing the ready label too quickly will cancel the reset run mid-flight — though after LS-4474 the dismissals persist, so the next run still recovers to cycle=1.
4. Bot re-reviews from cycle 1.

If the bot persistently re-emits arbitration even with both fixes in place, escalate via `review-bot-override` (forces `bot-review` to `success`) and capture the workflow run log for a follow-up ticket. Useful query for the log:

```bash
gh run view <run-id> --log | grep -E "reviewer\].*(cycle|reset|exclude|Escalat|arbitrat)"
```

The reviewer's stdout always prints `[reviewer] Computed review cycle: N` and `[reviewer] Excluded N thread-reply artifact review(s) from cycle counter (LS-4474)` — these are the two lines that diagnose this state.
