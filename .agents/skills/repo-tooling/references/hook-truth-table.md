# Hook truth table

One home for what every Claude Code hook in this repo actually does — verified against the scripts themselves, not their prose descriptions (two Bash guards were previously misdocumented). Registration lives in `.claude/settings.json` under `hooks`; the scripts live in `.claude/hooks/` and `.agents/hooks/`.

Semantics: **BLOCKS** = exit 2, the tool call (or stop) is refused and the message is fed back to the agent. **WARNS** = exit 0, stdout is injected into agent context but the call proceeds.

> **The `pnpm` gate, in full** (`pnpmInstallGate`). The hazard is pnpm writing _through_ a worktree symlink:
> that rewrites the immutable pool slot every other worktree on the machine is linked to. The gate checks real
> filesystem state so the rule fires only there:
>
> | State of `node_modules`               | bare `pnpm install`                  | `add` / `remove` / `update` / `install --lockfile-only` |
> | ------------------------------------- | ------------------------------------ | ------------------------------------------------------- |
> | Symlink into a pool slot              | **BLOCKED**                          | **BLOCKED**                                             |
> | Absent, linked worktree (detached)    | **BLOCKED** — run `link.mjs` instead | allowed (LS-9828)                                       |
> | Real directory, or main-repo checkout | allowed (LS-8731)                    | allowed                                                 |
>
> The right-hand column is every command that rewrites `pnpm-lock.yaml` — which is what mints a _new_ slot
> instead of mutating the current one. The detached row is [install-packages.md](install-packages.md)'s
> procedure: remove the symlink, `pnpm add -w` (rewrites the lockfile → new slot hash), then `make install` to
> materialise and link the new slot. No `# risk-ok` marker is needed for it.
>
> Bare `pnpm install` stays blocked in the detached state because nothing about the dependency set is changing:
> a slot for this lockfile already exists, so linking beats reinstalling. Note the gate reads filesystem state,
> never flags — while the symlink is live, `--lockfile-only` is blocked along with everything else.

> **The `actions_list` call-shape rules, in full** (`actionsListFindings`, LS-10156/LS-9987). Unlike every other
> rule here, these guard a _correctness_ hazard rather than a destructive one. `mcp__github__actions_list` belongs
> to the officially-hosted GitHub MCP server (no `github` entry in this repo's `.mcp.json`, not vendored under
> `tools/mcp/`), and its schema has no top-level `workflow_id`/`branch` param and no `additionalProperties: false`
> — so the plausible-but-wrong shape is accepted, the filters are dropped, and the unscoped repo-wide run list
> (~40,000 runs here) comes back looking like a filtered answer. Verified side by side on this repo:
>
> | Call                                                                                        | Result                                                         |
> | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
> | `{ workflow_id: "check-migrations-applied.yml", branch: "X" }`                              | `total_count` 40000, unrelated workflows, `head_branch` `main` |
> | `{ resource_id: "check-migrations-applied.yml", workflow_runs_filter: { branch: "main" } }` | `total_count` 28, only that workflow on that branch            |
>
> | Rule                          | Fires when                                                                          |
> | ----------------------------- | ----------------------------------------------------------------------------------- |
> | `actions-list-phantom-params` | any top-level key outside the real schema — the message names each one's real home  |
> | `actions-list-unscoped-runs`  | `list_workflow_runs` with neither `resource_id` nor `workflow_runs_filter`          |
> | `actions-list-verbose-runs`   | `list_workflow_runs` with `perPage` > 5, **including the tool's own default of 30** |
>
> LS-10055 root-caused this and fixed it with documentation in
> [service-operations.md](../../mcp-first/references/service-operations.md); LS-10156 is the same call made again
> by a session that had not read it. Prose cannot reach a call an agent is about to make, which is why the rule
> lives here. The regression tests in `scripts/__tests__/guard-risky-tools.test.mjs` pin the `settings.json`
> matcher too — without that, dropping the matcher would disable the guard with every test still green.

## Present but not registered in `.claude/settings.json`

- `.claude/hooks/check-mcp-servers.sh` — invoked only from the end of `setup-worktree-symlink.sh` (never standalone); warns when `node_modules/.bin/tsx` is missing, which silently kills every stdio MCP server.
- `.claude/hooks/cleanup-orphaned-symlinks.sh` — the registered twins live under `.github/copilot/hooks/` and are wired via `.github/hooks/worktree-setup.json` (Copilot coding-agent sessions).
- `*.ps1` twins (`guard-main-repo.ps1`, `guard-bash-mcp-first.ps1`, `setup-worktree-symlink.ps1`, `cleanup-worktree-symlink.ps1`) — Windows PowerShell variants; `.claude/settings.json` registers the `.sh` forms (run via Git Bash on Windows).

## Git hooks (`.github/hooks/`, not Claude hooks)

Installed into `.git/hooks/` by `make setup-hooks` (which `make install` runs). A fresh cloud checkout that never ran `make install` has **no** git hooks — only `*.sample` files.

`pre-push` runs four checks: (1) reject tracked `package-lock.json`/`yarn.lock`; (2) reject 7-char conflict markers in tracked non-md files; (3) `terraform validate` when `terraform/` changed; (4) `nx format:write` — if formatting changed files and the tree was clean, it auto-amends the last commit and **aborts the push** (re-run `git push`); if the tree was dirty, it blocks the push. Bypass: `SKIP_PREPUSH_LINT=1 git push` (formatting only) or `git push --no-verify` (all checks, emergency only).

`pre-push` has **no** git-lfs dependency as of this ticket (LS-7795) — removed end-to-end in LS-8204 (2026-06-20); re-verified against the live 159-line hook and guarded against regression by `.github/checks/pre-push-no-hard-lfs-guard.sh`. Do not reintroduce an unconditional `command -v <optional-binary> || exit <nonzero>` guard based on stale assumptions about LFS.
