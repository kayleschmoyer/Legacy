# Reference: Ticket-to-Merge Spine (environment-neutral)

This is the **canonical ordering** for taking a ticket to merge. It is environment-neutral: both [workflow-overview](../SKILL.md) (local) and [cloud-agent-mode](../../cloud-agent-mode/SKILL.md) (cloud) implement this exact sequence. Each step names a **gate** (what must be true) and an **action** (what to do). The concrete **tool binding** — which MCP tool or shell command performs each action in your environment — lives in your environment's skill, not here. Read this file for the order and the gates; read your env skill for the tools.

> **Why this file exists.** The ordering used to be restated in full in both the local and cloud skills, and the two copies drifted — the cloud copy dropped the task-graph enforcement (below), so cloud agents ran validation before opening a draft PR. There is now **one** source of truth for the order. Do not re-state the sequence in an environment skill; link here instead.

> **Two "spines" exist; they are not competitors.** [dev-process/spine.md](../../dev-process/spine.md) is the **6-phase process spine** (Frame → Design → Implement → Verify → Document → Handoff): it decides _what work and artifacts_ a change needs (risk tier, RFC, test plan, postmortem) independent of tooling. This file is the **operational spine**: the concrete Step 0–16 runbook that executes dev-process Phases 3–6 for a standard ticket, with gates and per-environment tool bindings. They answer different questions — dev-process decides _whether and what_; this file decides _in what order, with which gates_. Ordering and gate questions are answered **only** here.

## Read first: why ordering breaks, and what actually holds it

**Prose ordering does not survive context compaction.** A future agent (or this agent after a `/compact`) holds a _gist_ of the workflow, not the literal numbered steps — and the gist of "validate, then open a PR" is a strong prior that overrides a buried "open the draft PR first" instruction. The numbered [sequence](#the-sequence) below reads like a checklist, but it is **reference prose**: nothing tracks which step you are on or refuses to start the next one early, so it is itself exactly the kind of buried instruction the gist overrides. Do not mistake a numbered list for an executed plan.

Defenses against this come in three tiers, weakest to strongest. **The common failure is mistaking the middle tier for the strongest** — calling the task graph "mechanical enforcement" when it is not.

1. **Prose (weakest).** The numbered sequence and the gates table. Survives only as a gist; the failure above is its failure. Necessary for first reads and for humans, insufficient as enforcement.
2. **Task graph (durable, but still agent-honored).** Before writing any code, create the workflow tracking tasks with `TaskCreate` and chain them with `TaskUpdate(addBlockedBy: [...])`:
   1. **Implement + commit**
   2. **Push + open draft PR + apply `agent-in-progress` + post continuation checkpoint** — `blockedBy` (1)
   3. **Migrations + validation (`make pc`)** — `blockedBy` (2)
   4. **Self-review green + mark ready + watch to merge** — `blockedBy` (3)

   Task (3) being `blockedBy` task (2) is the load-bearing edge: the durable checkpoint (pushed branch + draft PR) exists **before** the long validation, so a container kill mid-`make pc` is recoverable. This beats prose because it persists as explicit state across compaction rather than as a gist — but be honest about its limit: it is **agent-honored, not tool-enforced.** Nothing refuses to start a blocked task; "never start a blocked task, and never delete a dependency to unblock yourself" is still an instruction the agent must _choose_ to obey. A graph that was never created, or created without the edge, enforces nothing — and that, not a defiant agent, is the usual real-world failure (an agent ran `make pc` before opening the PR because no graph gated the `make pc` call).

3. **Tool-enforced gate (strongest, and the only true enforcement).** A `PreToolUse` hook that refuses the action regardless of the agent's intent — e.g. blocking `make pc` until a draft PR exists for the current branch. This is the only tier that holds when the gist, the graph, and the agent's judgment all fail, because it lives in the tool-call path rather than in the agent's head. Where such a hook exists it _is_ the enforcement; the tiers above are then advisory scaffolding around it. Where one does not yet exist for a given ordering, treat that ordering as **unenforced** — a known gap to close, not a rule you can assume holds.

Creating the task graph is **mandatory in every environment**, local and cloud alike — it is the floor, not the ceiling. It makes the ordering durable and reviewable; it does not make it unbreakable.

## Critical gates (preconditions)

These five preconditions hold regardless of environment. Each is phrased as "before X, Y must be true."

| Gate                               | Precondition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Draft PR before validation**     | Open the PR as a **draft** right after the first push, _before_ running `make pc`. A draft PR is inert (CI and review are gated on `draft == false`), so it triggers nothing — but the branch + PR + continuation checkpoint now survive a container kill during the longest step. This reorders the classic "`make pc` must pass before you open a PR" rule: the **draft** opens early as a durable substrate; the gate that still holds is the next one. The checkpoint's **recovery consumer** is the `/sweep-prs` stalled-agent net ([sweep.md Step 2b](../../pr-lifecycle/references/sweep.md)): a draft with a stale `agent-in-progress` claim gets a resume chip that continues from the `<!-- continuation-plan -->` comment — which is why that comment must be kept current (LS-8542).                                                                                                                           |
| **`make pc` before mark-ready**    | A PR may be **opened as draft** with validation never run, but it must **not be marked ready** until `make pc` is green. Marking ready — not creating the PR — is the validated gate.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **CI red ≠ blocked on mark-ready** | The mark-ready gate is `make pc` green (this PR's own diff, validated locally) plus self-review complete — it is **not** "every CI check on the PR is green." When a check is red for a reason **proven** unrelated to this PR's diff (a pre-existing base-branch break, flaky infra) — not merely suspected — mark ready anyway: (1) mark the PR ready and apply `bot:ready-for-review`, (2) post a PR comment stating the failure is pre-existing/unrelated with the evidence (the failing check, the log excerpt, why it predates this diff), (3) track the underlying issue via a linked ticket (and a fix PR, if you're the one fixing it — the LS-9127/#6805 → LS-9186 pattern this gate codifies), (4) rebase and re-validate once the blocker resolves. Leaving the PR in draft to wait it out is the failure this gate prevents — see [pr-lifecycle Critical Rule 7](../../pr-lifecycle/SKILL.md#critical-rules). |
| **Migrations before `make pc`**    | Run migration status + apply before validating, even if you think no migrations were added. `make pc` assumes the local DB schema is current.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **PR Ready before watch-to-merge** | Do not enter the watch-to-merge phase (Step 15 — handling CI, review-thread, and merge events) until the PR is **Ready**: `state: OPEN`, `isDraft: false`, **and** the `bot:ready-for-review` trigger label applied. A draft PR is inert — CI orchestration and Reviewer Bot are both gated on `draft == false` plus the trigger label — so CI and review events never fire, and "waiting for CI" on a draft waits for something that cannot arrive. If the PR is still draft you are **not** in the watch phase: go back to mark-ready (Step 14). A turn that ends idling on a draft is the failure this gate prevents.                                                                                                                                                                                                                                                                                                   |
| **Self-review before mark-ready**  | Do not mark the PR ready — and do not push to a Ready (non-draft) PR — without completing the self-review gate (mechanical pattern lint + the judgment-requiring review of every changed file). Draft-checkpoint pushes (Steps 8–9) legitimately precede it; Step 13 is where it runs. `make pc` passing is necessary but not sufficient. See [common-review-patterns.md](../../pr-lifecycle/references/common-review-patterns.md) and [self-review.md](../../pr-lifecycle/references/self-review.md).                                                                                                                                                                                                                                                                                                                                                                                                                     |

## The sequence

Numbers are the canonical step order. "Tool binding" always means: look up the concrete call in your environment skill's binding section.

0. **Epic check** — if the ticket is an Epic, do not implement it directly; defer to the `work-ticket` skill's Parent Dispatch Mode (enumerate To Do descendants, check blockers, batch-dispatch chips).
1. **Identify/create the ticket** — complex/ambiguous work runs `/define` first; well-understood work creates directly with `sprint: "current"`. Capture planning output in the `context`/`risk`/`planningNotes` fields.
   - **1b. Plan** — assess scope, read relevant code, identify constraints, classify risk ([planning reference](../../plan-ticket/references/planning.md)). Skip for trivial tasks.
   - **1c. Create the tracking-task graph** — the mandatory enforcement described in [Read first](#read-first-why-ordering-breaks-and-what-actually-holds-it) above. This happens _before_ code.
2. **Dependency/blocker check** — inspect "blocked-by" links. Blocker not In Review/Done → **STOP**. Blocker In Review → branch off its branch. Blocker Done or none → branch off `origin/main`. Always fetch before branching.
3. **Transition Jira to In Progress** — only after the blocker check passes. Move the ticket to the current sprint if it isn't already.
4. **Claim the ticket** — atomically validates blockers/status and transitions to In Progress. Resolve the assignee from the environment first. Read the returned `branchRecommendation` for the git base; handle `STOP` / `ALREADY_CLAIMED` per the tool's contract.
5. **Working tree ready** — be on the correct branch/worktree, dependencies available. (Local: ephemeral or sibling worktree + node_modules symlink. Cloud: branch off latest main in the repo root.)
6. **Implement** — write the change. Prefer the env's structured run tool over raw shell. Test any new/modified spec files locally before committing; scope pre-`make pc` test runs to the specs you touched (don't run full platform suites — `make pc` re-runs them). After writing the fix, also `Grep` for E2E spec files (`apps/web-e2e/src/`) that reference the changed route, component, or GraphQL operation — run them locally and update any that fail due to the fix. A spec asserting the old (broken) behavior is itself a bug; update it in the same PR.
7. **Commit** — include the ticket key (`type(scope): LS-#### msg`) for Jira linking. Do not pre-run the formatter; `make pc` handles formatter rewrites and auto-commits them.
8. **First push** — establish the durable remote branch (set upstream).
9. **Open the draft PR (durable checkpoint)** — title `LS-#### type(scope): msg`, `draft: true`. Apply `agent-in-progress` while still draft (closes the sweep race window). Post a continuation checkpoint recording what's left (migrations, `make pc`, self-review, mark ready, merge). **This is the [draft-PR-before-validation gate](#critical-gates-preconditions).** A resuming container reads the checkpoint and continues instead of restarting.
10. **Rebase onto parent** (if needed) and **post-rebase stabilize** before validating.
11. **Migrations** — status + apply ([migrations-before-`make pc` gate](#critical-gates-preconditions)).
12. **Validate** — run the seven `pc-*` chunks **in order**: `pc-db-prep` → `pc-typecheck` → `pc-format` → `pc-lint` → `pc-workflows` → `pc-test` → `pc-build` ([`make pc`-before-mark-ready gate](#critical-gates-preconditions)). Update the continuation checkpoint after each chunk; a container kill mid-validation is non-fatal because the draft PR and branch already exist. Overlap self-review reading with the run rather than idle-waiting. **If a chunk runs in the background and you must end your turn to wait for its completion notification, refresh the checkpoint comment first** — a missed or unprocessed notification permanently stalls the session (the PR #6190 / LS-8542 incident), and recovery then depends entirely on the sweep's stalled-agent net reading an up-to-date checkpoint. **Local shortcut**: `make_run({ target: "pc" })` runs all seven in one call — valid only in non-timeout-prone local sessions where the full runtime fits inside a single foreground call. Never use the shortcut in cloud sessions.
13. **Self-review** — the mandatory gate before considering the PR shippable: mechanical pattern lint, then read every changed file in full and check the judgment patterns; fix everything; produce a Self-Review Summary. Re-run `make pc` if you changed code. Run any mandated integration spec locally.
14. **Mark ready** — once `make pc` is green and self-review is done, refresh the checkpoint and mark the draft PR ready (this applies the bot trigger label). **Draft is a working state, not an ending state — never end a turn with the PR still in draft.** This includes when CI itself is still red for a proven pre-existing/unrelated reason — see the [CI-red-≠-blocked-on-mark-ready gate](#critical-gates-preconditions). Transition Jira to In Review.
15. **Watch to merge** — **Precondition ([PR-Ready-before-watch-to-merge gate](#critical-gates-preconditions)): the PR is Ready** — `state: OPEN`, `isDraft: false`, and `bot:ready-for-review` applied. If it is still draft you are not in this phase yet; return to Step 14 and mark ready. Waiting for CI/review on a draft waits for events that are gated on `draft == false` and never fire. Once Ready: PR events (CI, review threads, conflicts, merge) surface natively; handle each as it arrives, reply to review threads, drive until merged. Do not poll with sleep loops, and do not start unrelated work while the PR is open.
16. **After merge** — run the MCP gap audit (skip only below the minimum threshold), complete every tracking task, and clean up.
