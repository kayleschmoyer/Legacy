# MCP-First — Tool Surfaces & Server Enablement

Split out of [SKILL.md](../SKILL.md) (LS-9952) — which MCP servers exist (stdio, hosted OAuth connectors, platform built-ins, Copilot bearers), how they're enabled, and the environment-detection probes for each. ## Tool Surfaces

Four independent tool surfaces exist. A session can have any combination — **probe, don't assume** (see [Environment Detection](../SKILL.md#environment-detection)).

> **`worktree_baseline_setup` (LS-9744)**: performing an e2e-hold Phase A local-baseline-worktree comparison (build + test a fresh `origin/main` to compare against a PR branch) used to require manually chaining `git worktree add`, `scripts/modules-pool/link.mjs`, and `pnpm exec nx build web` before `nx_run_e2e_specs({ worktreePath })` was usable. `worktree_baseline_setup({ ref, cleanup? })` runs all three steps and returns a ready-to-use `worktreePath`; it's keyed by `ref` and persistent (repeat calls reuse/refresh the same worktree via `git checkout --detach`) rather than one-shot/self-cleaning like `worktree_run_on_ref` (LS-9636), since a baseline comparison typically needs several `nx_run_e2e_specs` calls against the same build. Pass `cleanup: true` as a follow-up call to remove the baseline worktree once done.

> **`worktree_stabilize` and the modules-pool slot (LS-10109)**: when a worktree's `node_modules` is a symlink into a shared `.modules-pool/<hash>/` slot, `worktree_stabilize` deliberately does **not** run `make install` — that would mutate deps other worktrees are running. It runs `node scripts/modules-pool/link.mjs` instead, which is idempotent, leaves the slot's contents untouched, and links any workspace package a rebase just introduced. Without that step a rebase picking up a brand-new `@legacy-sports/*` package left the slot with no link for it, and `pc-typecheck` failed with `TS2307: Cannot find module` on a file the branch never touched — a code-defect-looking failure with a one-command fix. The tool's own description stays terse (the worktree server sits at its [tool-definition budget](../../../../docs/mcp/tool-budget.json) ceiling), so this is the written home for the behaviour; at runtime the tool logs which branch it took.

> **`aws_terraform_output` from a worktree session (LS-5209)**: worktree checkouts never have `.terraform/` initialized (only the main checkout does), so a bare call would fail with "Backend initialization required". The tool now falls back automatically: on a not-initialized error it retries the same relative `chdir` (default `terraform/main`) against the main checkout, resolved via `git worktree list` (main checkout is always the first entry) or a `MAIN_REPO_PATH` env var override. No caller-side workaround needed; pass an explicit `chdir` only to target a non-default Terraform directory (e.g. `terraform/runners`).

> **`nx_run_test` with a multi-word `testNamePattern` / `testPathPatterns` (LS-10153)**: pass the phrase as-is — the tool quotes it for you. It used to reach Jest word-split, so `testNamePattern: "keeper entitlement gate"` narrowed to `-t keeper` and the trailing words joined the path-pattern set, widening the suite and reporting that wider run as the pattern's result. The split was nx's, not the tool's: the `nx:run-script` executor (the `test:all-files` / `test:watch` style targets inferred from package.json scripts) joins its `--` passthrough into one shell string via `__unparsed__.join(' ')` and re-splits it. `@nx/jest:jest` and `nx:run-commands` targets were never affected, so quoting is applied only where it is needed — and the executor lookup it costs is skipped entirely unless a pattern value actually contains whitespace.

> **Load order in native-worktree sessions (LS-2902)**: Claude Code worktree-spawned sessions may only connect the first few servers from `.mcp.json` at session start. Each server is independently available — a missing `worktree` server does **not** imply the others are missing. If a server is absent, probe with its sentinel tool (below) before falling back to shell. **If all stdio servers are missing** (deferred tools list has no `mcp__worktree__*` / `mcp__legacy-sports-make__*` entries), the root cause is almost always a missing `node_modules/.bin/tsx` — see [`references/diagnostics.md`](diagnostics.md).

> **DB server name — `legacy-sports-db` vs `legacy-sports-db-admin`**: both names refer to the **same** hosted Lambda. The infra name and Cognito scope are `db` (terraform `local.mcp_servers_map`, SSM `/legacy-sports-<env>/mcp/db/api-url`), and the live claude.ai connector exposes tools under `mcp__legacy-sports-db__*` (verified in a live connector session, 2026-07-02). > **Self-served tool reference (`GET /docs`, LS-9593)**: each of the five hosted servers exposes its own tool reference at `GET /docs`, behind the same Cognito bearer its other tools require, generated at build time and redeployed with the server. ### Surface 4 — Copilot Coding Agent (`.github/copilot/copilot-cloud-mcp-config.json`)

Copilot cannot participate in OAuth connector flows. The authoritative config is `.github/copilot/copilot-cloud-mcp-config.json` (named "the committed Copilot MCP config" by the `copilot-setup-steps.yml` header; its `mcpServers` object is pasted into Settings → Copilot → Cloud agent). It registers the hosted `legacy-sports-{github,ci,jira,db-admin}` servers as `type: "http"` entries with static `Authorization: Bearer $MCP_*_BEARER` headers — short-lived Cognito `client_credentials` tokens minted by `scripts/mcp-mint-copilot-bearers.mjs` in `copilot-setup-steps.yml` — plus stdio entries for `worktree` (allow-listed tool subset), `legacy-sports-nx`, and `legacy-sports-make`. No `legacy-sports-aws` or browser server by default (per the config's `_instructions`); server-set details are owned by [cloud-agent-mode](../../cloud-agent-mode/SKILL.md). (`.github/copilot/mcp.json` is an older Copilot agent-mode config — `servers` key, no tool allowlists, still listed in `tools/mcp/README.md` — not what the cloud coding agent runs; `.vscode/mcp.json` is the analogous config for VS Code IDE agents.)

## Server Enablement: `.mcp.json` vs `.claude/settings.json`

Two different files, two different jobs:

- **`.mcp.json`** _registers_ project-scope stdio servers (Surface 1). It contains **only** stdio-launched entries — the hosted servers were removed from it when Claude Code 2.1.100 began silently dropping project-scope HTTP entries (LS-4595, documented in the `scripts/mcp-auth.mjs` header) and moved to claude.ai connectors.
- **`.claude/settings.json#enabledMcpjsonServers`** _auto-approves_ servers from `.mcp.json` so sessions start them without a permission prompt. It is a name list, not a registration.

The two lists intentionally-or-not disagree (verified 2026-08-10):

| Name                                                              | In `.mcp.json` | In `enabledMcpjsonServers` | Effect                                                                                                                     |
| ----------------------------------------------------------------- | :------------: | :------------------------: | -------------------------------------------------------------------------------------------------------------------------- |
| `worktree`, `legacy-sports-make/nx/aws/browser/android`, `stripe` |       ✅       |             ✅             | Start without prompting                                                                                                    |
| `legacy-sports-ci-local`, `legacy-sports-dev-process`             |       ✅       |             ❌             | Registered but not pre-approved — Claude Code may prompt before connecting. Whether the omission is deliberate is **OPEN** |
| `legacy-sports-github/jira/ci/db-admin`                           |       ❌       |             ✅             | No-op entries — vestiges of the pre-connector era when these were HTTP entries in `.mcp.json`                              |

> The `local-git` stdio server (former home of `github_create_pr` / `github_rebase_pr`) was **removed** in LS-9294 (owner ruling 2026-08-10): it was registered but never enabled or approved, so its tools never actually loaded in sessions, while the skills still documented them as canonical — the hosted `github_open_pr` composite is the single create surface now. If you encounter a doc still routing to `github_create_pr`, treat it as stale and fix it.

Separately, `settings.json#permissions.allow` pre-approves _tool calls_ (e.g. `mcp__legacy-sports-github__*`) — that governs permission prompts, not server startup.

> **No stdio `legacy-sports-jira` entry — intentional, do not add one (LS-9370).** `.mcp.json` has never carried a stdio-launched `jira-server` entry alongside the hosted `legacy-sports-jira` connector, even though `tools/mcp/jira-server` exists as a buildable stdio server (it also backs the hosted Lambda deployment and the Copilot/CCR machine-bearer paths). Registering it as a second, always-local stdio source would put two independently-authenticated servers behind the same `jira_*` tool names in the same session — whichever one wins isn't predictable, and it duplicates the OAuth-vs-stdio-credential split the connector migration (LS-4595, see above) was meant to collapse into one path. The late-attach cost documented below is real, but the fix is re-probing for the hosted connector, not standing up a second registration surface for it.

### Hosted connectors absent at session start, attach later (local launcher-worktree, LS-9370)

Distinct from both the LS-9576 "never registers at all" case and a mid-session 401: in local launcher-worktree sessions, the hosted connectors (`legacy-sports-jira`, `-github`, `-ci`, `-db`/`-db-admin`, `-rollbar`) routinely report unavailable in the deferred-tools roster **at session start** — either silently absent, or with an explicit `Incompatible auth server: does not support dynamic client registration` / `CONNECTION_CLOSED` reason — and then connect successfully **later in the same session**, sometimes 60–90 minutes in (observed recurring: LS-9366, LS-9371, LS-9839/PR #7536, LS-9859/PR #7584). Two consequences, both costly if unhandled:

1. **The whole ticket lifecycle falls back to REST/`acli`/`gh` unnecessarily.** An agent that checks tool availability once at Step 0b and treats that as final for the session keeps using CLI/REST fallbacks for claim, transition, comment, and PR creation even after the real tools would have worked — `gh pr create` in particular skips the jira-link marker `github_open_pr` auto-inserts, which is its own documented footgun (see [PR Creation Routing](auth-and-routing.md#pr-creation-routing)).
2. **The late attach can use a different tool prefix than the configured server name.** Observed live (2026-09-03): the same tools attached under UUID-prefixed aliases (`mcp__<uuid>__jira_*`, `mcp__<uuid>__github_*`, …) rather than `mcp__legacy-sports-jira__*` / `mcp__legacy-sports-github__*`, while the configured names stayed in the failed-to-connect list for the rest of the session. Guidance like "use the `jira_*` tools from `legacy-sports-jira`" doesn't help locate these — they're only discoverable by the bare tool name.

**Sanctioned response — re-probe by bare tool name before each lifecycle step, not just once at Step 0b:**

- Do not treat the Step 0b (or any single) `ToolSearch`/connection-error result as final for the session's lifetime. Before each subsequent Jira- or GitHub-touching step (claim/transition, comment, PR create, PR ready, label management), re-run `ToolSearch` on the **bare** tool name you need (`select:jira_view`, `select:jira_transition`, `select:github_open_pr`, …) rather than a server-prefixed query — a UUID-aliased late attach matches the bare-name search but not a `legacy-sports-jira`-scoped one.
- If the re-probe finds the tool (under its configured name or a UUID alias), use it — switch off any REST/`acli`/`gh` fallback already in flight for the rest of the session.
- If the re-probe still finds nothing, proceed with the documented fallback for the failure shape you're seeing (`configured: false` → Step 0b's stop condition; `Incompatible auth server…` → [Auth per surface](auth-and-routing.md#auth-per-surface) row below; entirely absent for the session → the [LS-9576 substitution table](auth-and-routing.md#jira-github-hosted-servers-absent-in-ccr-ls-9576), which applies here too even though this failure mode isn't CCR-specific), and note in the MCP gap audit which lifecycle steps ran on the fallback so a late attach mid-lifecycle is visible in the record.
- This costs one extra `ToolSearch` call per lifecycle step against the alternative of running the entire claim → PR → merge path on REST/CLI fallbacks — cheap by comparison, and it's the only way to recover the real tools once they attach.

### A connected server that still cannot reach your filesystem (CCR, LS-8890)

A fourth failure shape, distinct from every case above: the server **connects
fine and answers**, but cannot read a file on the path you name. In CCR the
stdio/hosted server process runs in a different container and OS user than the
agent, so a transcript the agent can `ls` directly — `/root/.claude/projects/<slug>/`,
root-owned, mode `0700` — is invisible to it. `ci_audit_session_bash` is the
worked example: `findClaudeProjectsDir` probes an explicit `projectsDir`
override, `$CLAUDE_PROJECTS_DIR`, `$HOME`, `homedir()`, `%APPDATA%`, `/root`
and every `/home/*`, and in CCR **none of them can succeed**, because the
problem is a namespace boundary rather than a wrong path (LS-8867, LS-9268,
LS-9458 and LS-9538 each narrowed the search and each confirmed it).

**Recognise it by the shape, not the wording:** auth is fine, the tool returns
a normal error rather than a connection failure, and an explicit path override
the agent has verified from its own Bash tool still fails. That combination
means no parameter value will ever work — stop retrying path variations.

**Sanctioned response — move the process boundary, not the path.** Where the
work is pure computation over a file the agent _can_ read, run the same
implementation locally instead of shipping the file to the server:

```bash
make audit-session ARGS="--auditMode"
```

This is the identical `auditSessionBash` code executed in the agent's own
namespace, so the report matches the MCP tool's exactly. Prefer it over the
`transcriptContent` upload param, which also works but costs the whole
transcript (hundreds of KB) through the context window. Full routing:
[audit-workflow.md](audit-workflow.md#when-the-server-cannot-see-the-transcript-ccr-run-the-audit-locally).

When adding a tool that reads a caller-side path, assume this boundary exists:
make the failure name a recovery the caller can actually run, rather than
ending at "do it by hand" — that wording alone kept Phase 1 of the gap audit
un-run across eight CCR sessions.
