## Tool Routing Rules

### Tool-Use Rejections Are a Hard Stop (LS-8761)

A tool-use rejection — the harness/user declining a specific call ("The user doesn't want to proceed with this tool use... STOP what you are doing and wait for the user to [respond]") — is categorically different from a tool _returning_ an error or a `STOP`/`ALREADY_CLAIMED` result field (that's the tool running successfully and reporting a state). A rejection means the call never ran at all. Treat the **first** rejection as a hard stop: halt the current action, surface it to the user, and wait — never resubmit the identical call (same tool, same arguments) expecting a different outcome. Resubmitting an already-rejected call is not a retry, it's the same declined action asked again; nothing about the call's arguments changes between attempts, so nothing about the answer will either. If the call is part of a multi-step flow (e.g. a ticket claim), investigate why it might be wrong _before_ trying again with different arguments (or a different tool) — for a claim rejection, check `github_pr_dashboard` for an existing PR against the ticket key first, per [work-ticket leaf-mode Step 1](../../work-ticket/references/leaf-mode.md).

Observed failure mode (LS-8761): ~48 near-identical rejected `jira_transition(action=claim)` calls against an already-in-review ticket in a single session, before the agent finally stopped and found the existing open PR — the investigation that happened after the 48th rejection should have happened after the 1st.

### PR Creation Routing

**The routing decision — which creation tool per environment, plus the mandatory label sequence — has one home: [pr-lifecycle → PR-creation tool routing](../../pr-lifecycle/references/create-pr.md#pr-creation-tool-routing-one-home--link-here-do-not-restate).** This section holds only the tool-surface facts behind that table:

- `github_open_pr` — registered on the **hosted `legacy-sports-github` connector** only. Semantic one-shot: push branch → create draft → mark ready → apply `bot:ready-for-review`; `draft: true` stops after creation; in Lambda mode `head` is required and push is skipped (no local git checkout to push from) — `push: true` (the default) is therefore a no-op in that mode. As of LS-9290, if `push` wasn't explicitly set to `false` and the `head` branch doesn't already exist on the remote, the tool now fails fast with an actionable error telling the caller to push manually and retry with `push: false`, instead of silently proceeding to a PR-create call that fails with an opaque GitHub 422 (`{"field":"head","code":"invalid"}`). If the branch already exists remotely (e.g. pushed separately via `worktree_push` beforehand), the no-op is harmless and the call proceeds normally. When `jiraKey` is passed, the tool auto-inserts the jira-link marker in the body **and** (LS-8679) prepends the key to the title if it isn't already present anywhere in it — so passing a pre-prefixed title is no longer required to pass Jira Link Check. For an evidence-heavy body already written to disk, pass `bodyFile` (a file path) instead of `body` — cheaper than re-emitting the whole document as a tool argument on create and every subsequent edit; `github_edit_pr` takes the same `bodyFile` parameter for exactly that re-edit case. Both fields are mutually exclusive, `bodyFile` must resolve inside the repo (its contents become the public PR body), and it isn't supported in Lambda mode (LS-9581).
- `github_open_pr` unavailable → the routing home's built-in and `gh` rows apply; before any `gh pr create` fallback, diagnose and report first (see [diagnostics Reporting Protocol](diagnostics.md#reporting-protocol)) — `gh pr create` silently targets the shell's working directory.

> **`github_create_pr` no longer exists.** It lived on the `local-git` stdio server, which was removed in LS-9294 — the server was registered but never enabled, so the tool never loaded in sessions anyway. `github_open_pr` (hosted `legacy-sports-github`) is the single custom create surface; it carries the jira-link-marker auto-insert itself (shared `jira-link.js` module: `primary: none` + `no-jira` label fallback per LS-8298, self-healing marker per LS-9043). `github_rebase_pr` went with the server too — use `github_bulk_rebase({ prs: [N] })` for a single hosted rebase, or `worktree_rebase_onto_main` locally.

<a id="label-changes--always-additive-never-replace-semantics-ls-9715"></a>

### Label Change Routing — Always Additive, Never Replace-Semantics (LS-9715)

**`github_manage_labels`** (`add`/`remove`/`clearPattern`, `legacy-sports-github`) is the required primitive for every label change on a PR or issue. It calls GitHub's native additive REST endpoints directly — `POST /repos/{owner}/{repo}/issues/{n}/labels` to add, `DELETE /repos/{owner}/{repo}/issues/{n}/labels/{name}` to remove — and never reads the current label set and writes back a full replacement array. That makes it safe by construction: adding a label already present or removing one already absent is a no-op (404/422 on the delete side is swallowed; see `tools/mcp/github-server/src/tools/manage-labels.ts`), and a concurrent label change made by another actor (a CI bot, a sweep, a failure-cleanup job) between your call and theirs cannot be clobbered, because the call never resends anyone else's labels. It targets the `issues/{n}/labels` path, which GitHub resolves identically for issue and PR numbers, so it's safe to call with a PR number. Confirmed reachable in CCR sessions — its Lambda-hosted transport (`tools/mcp/github-server/src/lambda.ts`) registers the same tool set as the local/stdio server, authenticated via the Cognito bearer path from LS-8114/LS-9576.

**Never use `mcp__github__issue_write({ method: "update", labels: [...] })`** (or any other full-set-replace label call) to add or remove a single label. Its `labels` array **replaces the entire set** — adding one label means reading the current set and writing back the full union, and if a label was stripped by automation (e.g. the "Remove Merge Label on Failure" job removing `merge-when-ready`) in the window between your read and your write, your write silently re-applies it. Per the [Author Agent Contract](../../pr-lifecycle/references/author-agent-contract.md), an agent must never apply `merge-when-ready` or any other maintainer escape-hatch label — replace-semantics turns that into a live race, not just an ergonomics gap. If `github_manage_labels` is ever genuinely unreachable (retry `ToolSearch` once before assuming so), see the [CCR substitution table](#jira-github-hosted-servers-absent-in-ccr-ls-9576) below for the last-resort fallback and its guardrail.

<a id="issue_write-cannot-resolve-pr-numbers-ls-9692"></a>

### `issue_write` Cannot Resolve PR Numbers (LS-9692)

`mcp__github__issue_write({ method: "update", issue_number: <PR#>, ... })` fails **`Failed to find issues: failed to get issue ID: Could not resolve to an Issue with the number of <PR#>`** whenever `issue_number` is a pull request — reproduced applying `bot:ready-for-review` to a real, open PR (#7368), and again on the same number trying to set `state`/`state_reason` to close it. `update_pull_request` on the identical number succeeded immediately after, confirming the PR was real and reachable; only `issue_write`'s resolution step rejects it.

This reads as a repo-fixable resolver bug — GitHub's underlying REST/GraphQL API serves both issues and PRs off the same `issues/{n}` surface for labels and state, so nothing about the platform requires this restriction. It is not, however: `mcp__github__*` is a **hosted, platform-built-in tool surface** (see [Built-in GitHub Tools](service-operations.md#built-in-github-tools-claude-code-on-the-web)) — there is no `tools/mcp/` source in this repo for it, unlike `legacy-sports-github` (`tools/mcp/github-server/`), so the resolver cannot be patched from here. The fix that _is_ reachable from this repo is routing: never call `issue_write` with a PR number, for **any** field, not only `labels`. Concretely:

- Labels on a PR → `github_manage_labels` (additive, safe on PRs — see above; this was already the rule before LS-9692, for the separate reason of replace-semantics).
- Open/closed state on a PR → `mcp__github__update_pull_request({ owner, repo, pullNumber, state: "open" | "closed" })`. Its schema has no `state_reason` field — closing a PR as `not_planned`/`duplicate`/`completed` with a recorded reason is not currently possible through any available tool; closing via `state: "closed"` alone is the available substitute.
- No single tool sets both state and labels on a PR in one call — issue two calls (`github_manage_labels` then `update_pull_request`, or vice versa) rather than reaching for `issue_write` to try to do both at once.

If `issue_write` is ever called with a PR number and returns the "Could not resolve to an Issue" error, that is expected behavior for this known platform limitation, not a transient failure worth retrying against the same tool — retry via the routing above instead.

### Pre-flight Auth Check

<a id="auth_check_all"></a>

`auth_check_all` (read-only token-presence check for GitHub/Jira/AWS/CI) lives in the **`worktree` stdio server** (`tools/mcp/worktree-server/src/index.ts`). Availability follows Surface 1: present in local sessions and Copilot (`auth_check_all` is in the `worktree` server's `tools` allowlist in `.github/copilot/copilot-cloud-mcp-config.json`); **absent whenever stdio servers are absent** — most commonly degraded CC-web, but also observed recurring in local Windows launcher-worktree sessions where the stdio servers simply failed to start (LS-8774, LS-9743) — run [diagnostics](diagnostics.md) Check 1 to tell the two apart before assuming CC-web. When it is absent, AGENTS.md's pre-flight mandate is satisfied per-service instead: `github_auth_status`, `jira_auth_status`, `ci_auth_status`, `rollbar_auth_status` on the hosted connectors, `aws_sso_status` on the aws stdio server. If `allAuthenticated: false` (or any per-service check fails): surface the `hint` verbatim and **stop** — see [Auth Model](#auth-model).

> **Pass `sessionToolNames` for a real presence check, not just credentials (LS-9749).** `auth_check_all`'s process boundary means it can only see local credential/config presence — it has no way to observe whether the _hosted_ `legacy-sports-github`/`legacy-sports-jira`/`legacy-sports-ci-local` connectors actually registered in your session (that state lives in the Claude Code client, not this server). Credentials can look fully configured while the connector never appeared in your tool roster at all — the false-green this ticket reported. You, the caller, **do** know your own roster (the deferred-tools listing, or a `ToolSearch` result) — pass those tool names as `sessionToolNames` and the response cross-checks each hosted service against them, downgrading `ok` to `false` and setting `rosterAbsent: true` on any service whose credentials look present but whose tools are nowhere in your list. Omitting the param preserves the old credentials-only behavior (with the [`HOSTED_CONNECTOR_CAVEAT`](#auth-model) warning) — pass it whenever you can.

> **`auth_check_all` and the per-service `*_auth_status` tools check credentials, not connector enablement (LS-8695)** — a connector with `enabledInChat: false` for the current chat is invisible to both: its tools never load, so there is no auth call to make in the first place, and none of these checks would catch the gap in advance. A ticket that names a specific hosted connector in its own instructions (e.g. a `labels: rollbar` ticket that expects to call `rollbar_get_item`) is worth a one-shot `ListConnectors({ keywords: ["<server>"] })` preflight before investigation starts — cheap, and it turns a mid-task "tool silently absent" surprise into an upfront "ask the user to enable it" ask. This is a recommendation, not a hard gate; it is not wired into `/work-ticket` or leaf-mode routing.

The Jira sub-check (`checkJiraAuth` in `tools/mcp/worktree-server/src/auth-checks.ts`) recognizes four credential shapes, not just direct basic/OAuth env vars: `JIRA_EMAIL`+`JIRA_API_TOKEN` (basic), `JIRA_CLIENT_ID`+`JIRA_CLIENT_SECRET`+`JIRA_CLOUD_ID` (a jira-server run as a direct stdio process), `~/.netrc`, and — the case that matters in practice, since `legacy-sports-jira` is hosted and its own credentials never reach this process — `MCP_JIRA_URL` paired with either `MCP_MACHINE_CLIENT_ID`+`MCP_MACHINE_CLIENT_SECRET` (local/worktree sessions, mirrored by `scripts/mcp-auth.mjs`) or `MCP_JIRA_BEARER` (Copilot cloud). Before LS-8714 this last path wasn't checked at all, so `auth_check_all` reported `jira: { ok: false }` in sessions where `jira_auth_status` confirmed OAuth was working.

### spawn_task and Chips

`mcp__ccd_session__spawn_task` (chip dispatch — each chip is a real independent Claude Code session) is **not registered anywhere in this repo** — no `.mcp.json`, no `tools/mcp/` source. It is injected by the chip-dispatch launcher on the orchestrating machine; its installation/provenance is **OPEN** (not documented in-repo). Detect with `ToolSearch("select:mcp__ccd_session__spawn_task")`. When unavailable, the binding rule is AGENTS.md Tier-2: **stop and inform the user — never substitute `Agent` for chip dispatch on your own authority.** The work-subagent fallback template in [subagent-templates](../../subagent-templates/SKILL.md) exists for orchestrators the user has explicitly told to proceed without chips.

### twig

`twig` is an external branch/worktree-management CLI installed on local Windows dev machines — it is not a repo package (no install step in `package.json`/`Makefile`; install source **OPEN**, ask the user if it is missing). Repo integration points: `make pr` (`twig github pr create`), `twig worktree clean` (the only sanctioned worktree removal, AGENTS.md Tier-2), and the `worktree` MCP server, whose `worktree_rebase`/`worktree_remove` wrap twig internally. Detect with `Bash: twig --version`. Cloud environments have **no twig** (AGENTS.md Environment table). As of LS-9954, `worktree_rebase()` (no explicit `base`) detects a twig-binary-not-found failure (ENOENT / exit 127 / "not found") and falls back to `git rebase origin/main` automatically — passing `base: "origin/main"` explicitly is no longer required in twig-less CCR/cloud sessions, though it still works and remains the way to target a different base ref. See the rebase flow in [worktree-workflow](../../worktree-workflow/SKILL.md).

### Validation Routing

Owner ruling (2026-07-02) — the validation execution path is availability-routed:

1. **`nx_run_pc_chunk` present** → it is **mandatory** for every chunk (cloud and timeout-prone sessions; AGENTS.md Tier-2). One call per chunk, canonical order. Calls are transport-safe: a chunk still running at the ~45s in-call budget returns `{ status: "running", jobId }` — follow with `nx_job_wait({ jobId })` (≤55s per call; re-invoke while `status: "running"`), `nx_job_status` for a snapshot, or `nx_job_list` to recover handles after a session resume. Never re-run a chunk that handed back a jobId — re-invoking joins the in-flight job. Sole exception: a terminal `"internal timeout"` error or `orphaned` status may be re-run once (completed tasks stay Nx-cached; LS-8353). Full contract: [repo-tooling](../../repo-tooling/references/pc-pipeline.md#running-validation-per-environment).
   - `runNx()` (backing every `legacy-sports-nx` tool call) self-heals a stale Nx project-graph cache: on `Failed to process project graph` it clears `.nx/cache`/`.nx/workspace-data` once and retries automatically — no manual cache-clearing needed on platforms where `nx_run_pc_chunk` exists (LS-8936). On CCR, where this tool is absent, see the [stale project-graph cache failure mode](../../cloud-agent-mode/references/ccr-known-failures.md#known-failure-mode-stale-nx-project-graph-cache-blocks-every-nx-invocation-ls-8936) for the manual recovery.
   - `runNx()` also self-heals the distinct "pnpm install never finished" cause of the same `.modules.yaml is missing` message: if the cache-clear retry above fails identically, it runs `pnpm install --frozen-lockfile` once and retries again (LS-9863) — see the [second-tier self-heal write-up](../../cloud-agent-mode/references/ccr-known-failures.md#known-failure-mode-stale-nx-project-graph-cache-blocks-every-nx-invocation-ls-8936) for detail.
   - The nx MCP server's own `--import tsx` launch env (`TSX_TSCONFIG_PATH`, set in `.mcp.json` for `legacy-sports-nx`) no longer leaks into `nx_run_pc_chunk`'s spawned children (`make -> nx -> jest`): `runCommand` (`tools/mcp/nx-server/src/run-command.ts`) always sanitizes the child env via `buildChildEnv()` (`tools/mcp/nx-server/src/child-env.ts`) before spawning, regardless of whether the caller passes its own `env` override. Previously a jest suite that itself shelled out to `tsx` (e.g. `lib/db-client/src/scripts/tsx-workspace-resolution.spec.ts`) could inherit the nx server's own relative `TSX_TSCONFIG_PATH` and resolve it against the wrong cwd, producing a false `pc-test` failure unrelated to the code under test (LS-9681). `make-server` had the same class of leak (it never set an explicit `env` on `execFile`, so it always inherited `process.env` verbatim into spawned `make` children); fixed in LS-9806 with the same `buildChildEnv()` pattern (`tools/mcp/make-server/src/child-env.ts`, wired into `tools/mcp/make-server/src/run-command.ts`).
   - **Isolated Nx plugin-worker timeouts self-heal with one retry (LS-9282)**: under host/process contention (many concurrent `node` processes across parallel worktree/cloud sessions), an isolated Nx plugin worker's IPC handshake can time out — `Plugin Worker for <plugin> is exiting as it did not receive a load message within 10 seconds of connecting.` / `Failed to load N default Nx plugin(s) ... exited unexpectedly.` `nx_run_pc_chunk`, `nx_run`, and `nx_run_affected` all detect this signature (`tools/mcp/nx-server/src/plugin-worker-failure.ts`) and automatically retry the identical command once with `NX_ISOLATE_PLUGINS=false` in the child env (`tools/mcp/nx-server/src/plugin-worker-retry.ts`) before surfacing a failure — no manual `nx reset` or env-var workaround needed. A result with `pluginWorkerRetried: true` means this happened; its `hint` says whether the retry recovered or is still failing.
2. **`nx_run_pc_chunk` absent** (degraded CC-web: no custom stdio servers) → the sanctioned path is Bash `make pc-<chunk>` with **`run_in_background: true`**, one chunk at a time in the canonical order. `.agents/hooks/enforce-background.mjs` permits background runs and exit-2-blocks the same command foreground — foreground remains banned.
3. **Local non-timeout-prone sessions** → `make_run({ target: "pc" })` is fine.

Chunk order and the full per-platform decision tree are owned by AGENTS.md and [cloud-agent-mode](../../cloud-agent-mode/SKILL.md) — do not restate them here.

### Waiting on CI (no polling, no sleep)

- **PR-associated runs — arm the watch before idling (LS-8544)**: before ending any turn with the PR in a non-terminal state, arm the canonical watch monitor — `Monitor({ command: "bash <worktree-abs-path>/scripts/watch-pr.sh <PR#>", persistent: true, description: "PR #<N> watch" })` — then end the turn. The script path must be **absolute**: `Monitor` is not guaranteed to run with the worktree root as its cwd, and a bare relative `scripts/watch-pr.sh` exits 127 before the script runs a single line (LS-9045). The watch polls harness-side (zero tokens, ~90s cadence) and re-invokes the idle session only on actionable transitions: red required contexts, corroborated merge conflicts, new reviews, escalation labels, SKIPPED-pipeline stalls (`bot-review`/`CI Gate` are commit statuses that go _absent_, never red), and MERGED/CLOSED. It heartbeats `.claude/.pr-watch-armed-<PR#>` so the stop guard (`check-open-pr.sh`) permits idling. Push notifications remain an accelerant when they arrive but are **not load-bearing**: conflict transitions caused by main advancing are surfaced only as an API check run + label + comment and never wake an idle session (observed stuck PRs #6161/#6163). In-context polling remains banned — treat `ci_view_run`/`github_view_pr` as one-shot lookups; polling loops have burned 1–2M tokens per session. Arming precondition: the `Monitor` tool is available **and** `gh` is on PATH; otherwise fall back to the environment rules below. **Binding caveat**: a fix/chip session still on its auto-generated `claude/<name>` branch must never end its turn waiting on a PR event — re-arm `bot:ready-for-review`, report, stop (see [pr-lifecycle drive.md Step 4 + Gotchas](../../pr-lifecycle/references/drive.md#step-4-enter-worktree-local-only)).
- **Non-PR `workflow_dispatch` runs** (integration suite on `main`, nightlies): no PR → no push notification. Use `ci_dispatch_workflow({ ..., waitForCompletion: true })` — each call waits at most ~20s (bounded by this Lambda-hosted server's own 30s execution timeout, not the ~60s MCP transport timeout — LS-8429), and can be shorter still: the wait is clamped to the Lambda's _actual_ remaining execution time (minus a response-serialization margin), not a flat 20s, so a slow-starting invocation (cold start, GitHub App token latency) returns sooner rather than risking the transport-level "Service Unavailable" that a naive fixed ceiling produced (LS-8429 regression fix — see `tools/mcp/ci-server/src/lambda-budget.ts`). A fast run returns `{ status: "completed", conclusion, durationSeconds }` in one call; a longer run returns `{ status: "in_progress", runId, hint }` — continue with `ci_wait_run({ runId })`, which has the same bounded-wait contract: re-invoke it until `status: "completed"`. Never re-dispatch while a run is in progress.
- **Retriggering a GH-Actions-owned check with no `workflow_dispatch` trigger** (e.g. `jira-link-check.yml`, which only runs on `pull_request`) (LS-8366): `github_retrigger_check` refuses and points to `ci_dispatch_workflow` as a fallback, but that workflow will 422 ("Workflow does not have 'workflow_dispatch' trigger"). `ci_dispatch_workflow` now detects this and returns an error redirecting to the path that actually works: `ci_list_runs({ workflow, branch })` to find the failed run, then `ci_rerun({ runId })` (default `scope: "failed"`).
- **Environments without push notifications** (e.g. Copilot): prefer `waitForCompletion`. If you must wait on a condition in a Claude Code session, use the harness `Monitor` tool — for PR waiting always via `scripts/watch-pr.sh` invoked by **absolute** path as shown above (never a bare relative path — it exits 127, LS-9045 — and never an ad-hoc loop: the canonical script covers commit-status stalls, conflict corroboration, debounce, and loud death) — **`ScheduleWakeup` is not a CI-wait primitive** (it paces `/loop` only). Never `sleep N && gh run view` loops, and never `Bash(gh run watch ..., run_in_background: true)` — the watcher dies silently on session resume.
- **Session-resume caveat**: if a bounded wait was in-flight when the session was interrupted, only that one ≤20s call is lost — the run itself is unaffected. Re-find the run with `ci_list_runs({ workflow, branch, limit: 5 })`, then re-attach with `ci_wait_run({ runId })`. Do not re-dispatch.
- **Waiting on a remote ref change or deletion** (e.g. `main` advancing after a queue merge, a PR branch being deleted post-merge): never `git ls-remote origin <ref> | sleep 20` — use `github_await_ref({ ref, changedFrom?, deleted?, maxWaitSeconds? })` on `legacy-sports-github` instead. Same bounded-wait contract as `ci_wait_run`: each call polls for up to 55s and returns `{ status: "unchanged", hint }` (never an error) if the condition hasn't occurred yet — re-invoke per the hint. `{ status: "changed" | "deleted" }` on success.
- **`ci_rerun` "already running" 403 vs. trailing cleanup jobs** (LS-9647): GitHub's `rerun-failed-jobs`/`rerun` endpoints gate on the run's overall status, not any individual job's — they keep 403ing "This workflow is already running" while trailing jobs (`Summarize & Report`, `Remove Merge Label on Failure`, etc.) are still queued, even after every substantive build/test/E2E job has finished. `ci_rerun` retries this race internally for a few seconds, but a short in-Lambda retry can't wait out a slow-scheduling cleanup job. If `ci_rerun` returns `{ status: "not_yet_reschedulable", hint }` instead of a normal success/error, that is the signal: call `ci_wait_run({ runId })` (re-invoking per its own hint) until it returns `status: "completed"` — that field only flips once every job on the run, cleanup included, is done — then retry `ci_rerun`. Do not loop calling `ci_rerun` itself or blind-poll `ci_view_run`/`actions_list` job lists in the meantime.

<a id="installation-vs-user-rate-limit-ls-9570"></a>

### Installation rate limit vs. `gh api rate_limit` (LS-9570)

`gh api rate_limit` reports the **CLI's own user/PAT token** bucket. Workflow steps authenticate as the **GitHub App installation token** minted from `secrets.AGENT_AUTHOR_APP_PRIVATE_KEY` (`actions/create-github-app-token`, app id 3158619) — a **completely separate budget**. These two buckets can be in opposite states at the same time: a healthy `gh api rate_limit` result does **not** mean CI's own API calls aren't rate limited, and does not answer "is CI rate limited?" at all. Running `gh api rate_limit`, seeing a healthy number, and concluding a workflow's 403s were a transient blip is the exact wrong-decision failure mode this gap produces (observed on PR #7232 / LS-9528 — a ~90-minute stall on what was purely an installation-token rate limit).

Use `ci_installation_rate_limit` (`legacy-sports-ci`/`legacy-sports-ci-local`) instead — it always mints a fresh installation token via `AGENT_AUTHOR_APP_PRIVATE_KEY` and queries `GET /rate_limit` with it directly, bypassing `GH_TOKEN`/`GITHUB_TOKEN` env precedence, so the result is guaranteed to be the installation bucket regardless of what other credentials the session has. (`ci_auth_status`'s own `rateLimit` field is not a substitute for this — it reflects whichever token source `getToken()` actually resolved, which may not be the installation token.)

A CI step that computes a verdict but can't post it — GitHub App API calls failing with `API rate limit exceeded for installation`, or a gate/status step logging its computed result and then silently withholding the actual `POST`/status update — is a **rate-limit signature, not a real verdict**. See [pr-lifecycle troubleshooting](../../pr-lifecycle/references/ci-checks-reference.md#withholding--could-not-post-status-is-a-rate-limit-signature-not-a-verdict-ls-9570) for the failure pattern and remedy.

<a id="deploys-repo-credentials-gap-ls-8788"></a>

### Deploys-repo credentials gap: diagnose, don't re-derive (LS-8788)

`ci_get_playwright_report`/`ci_get_playwright_test_result` read the private `bkrupa/legacy-sports-deploys` repo via `getDeploysToken()`, which tries `PREVIEW_APP_PRIVATE_KEY`/`PREVIEW_APP_ID` first, then the agent-author App's own installation on that repo, before falling back to the main (deploys-repo-blind) token. In CCR/cloud sessions neither of the first two tiers is currently provisioned, so every fetch 404s with a credentials-gap message. Call `ci_installation_rate_limit`'s sibling tool **`ci_deploys_repo_auth_status`** (`legacy-sports-ci`/`legacy-sports-ci-local`) to check which tier is configured/failing and why, in one call — instead of re-triggering a real report fetch and re-deriving the same diagnosis from a 404, which is what caused this gap to be independently rediscovered and re-ticketed four times. Full root cause and remedy: [read-playwright-report](../../read-playwright-report/references/credentials-gap.md).

## Auth Model

This section absorbed the former `credentials` skill (2026-07-02). One rule dominates everything below:

> **Tier-1 (AGENTS.md Safety): never run auth-generation commands.** `aws sso login`, `gh auth login`, `acli auth login`, OAuth device flows, and credential-provisioning scripts (`node scripts/mcp-auth.mjs`, `make e2e-auth`) are **user-only** actions. On any auth/expired-token error: stop, surface the `hint` verbatim, prompt the user. Falling back to `gh`/`acli`/raw `curl` does not work around a missing token — it masks the failure and pollutes the MCP gap audit.

### `legacy-sports-jira` / `legacy-sports-github` entirely absent in a local (non-CCR) worktree session (LS-9749)

Same symptom as the LS-9576 row above — `ToolSearch` for `jira_view`/`jira_auth_status`/`github_pr_dashboard`/`github_open_pr` returns nothing, not an error, and `auth_check_all` reports `ok: true` for both anyway (a false green; see the roster-cross-check fix below) — but observed in a **local worktree launcher session**, not CCR. Filed separately because the topology is different enough that "CCR-only" would have been the wrong prior for anyone hitting it locally; comment on LS-9749 also reports the identical symptom recurring in a CCR session, so this is one underlying gap wearing two topology labels, not two gaps.

**Root cause (investigated for LS-9749): not a repo-side config bug.** `legacy-sports-jira`, `legacy-sports-github`, `legacy-sports-db`, and `legacy-sports-rollbar` are never launched as local stdio processes — they are absent from `.mcp.json` entirely, unlike `worktree`/`legacy-sports-make`/`legacy-sports-nx`/etc. They exist only as claude.ai custom OAuth connectors ("Track B" — see [`docs/dev-process/mcp-connector-access.md`](../../../../docs/dev-process/mcp-connector-access.md)), auto-synced into a session's tool roster based on (a) whether an Org Owner registered the connector at all, and (b) whether _this user_ has completed per-user OAuth consent for it. `.github/copilot/hooks/mcp-bootstrap.mjs` — the wrapper every `.mcp.json` entry launches through — has no jira/github-specific or session-type-specific branching (its only fork is `isLocalWorktree` vs. cloud, purely for `node_modules`/symlink repair on the servers that _are_ locally launched); it cannot be the site of a "worktree launcher omits jira/github" bug because those two servers never pass through it. **Conclusion: there is no local-worktree-specific server-omission logic to fix in this repo.** Absence for a given local session is fully explained by the same per-user-consent/connector-registration state (or a claude.ai-side connector-layer outage) as any other hosted-connector gap — not by session type, and not fixable by editing `.mcp.json`, `mcp-bootstrap.mjs`, or any worktree-launcher script. If you land here again convinced it's a config bug, first prove the servers were ever registered as local processes anywhere in the repo (`grep -n 'legacy-sports-jira\|legacy-sports-github' .mcp.json`) — they aren't, so that path is a dead end.

**Fallback**: use the exact same [CCR substitution table](#jira-github-hosted-servers-absent-in-ccr-ls-9576) above — the recovery tools and lost guardrails don't depend on why the connector is missing, only on the fact that it is. Retry `ToolSearch` once after a few seconds first (connectors can be slow to attach, not just absent — see [tool-surfaces.md hosted connector late-attach](tool-surfaces.md#hosted-connector-late-attach-ls-9370)); if still absent, use the substitution table and note in the PR/Jira ticket which topology (local vs. CCR) you hit it in, for pattern-tracking across recurrences.

**Don't trust `auth_check_all`'s green here** — its presence-only check reports `ok: true` from local credential/env presence regardless of whether the hosted server ever registered (this is the false-green LS-9749 also flagged). Pass `sessionToolNames` (the tool names from your own session's deferred-tools listing) to `auth_check_all` to get an explicit `rosterAbsent: true` flag and a downgraded `ok: false` instead of a silent green when the connector's tools are nowhere in your roster.

<a id="legacy-sports-ci-local-write-path-auth-gap-ls-9234"></a>

### `legacy-sports-ci-local` write-path auth gap (LS-9234, proxy fix LS-9288)

`legacy-sports-ci-local`'s token resolution (`tools/mcp/ci-server/src/github-api.ts`, shared with the hosted `legacy-sports-ci` connector) tries, in order: `GH_TOKEN`/`GITHUB_TOKEN` env → a GitHub App installation token minted from `AGENT_AUTHOR_APP_PRIVATE_KEY` → `gh auth token` CLI. Read-only tools (`ci_view_run`, `ci_get_logs`, `ci_list_runs`, …) and write tools (`ci_rerun`, `ci_cancel_run`, `ci_dispatch_workflow`) go through the **same** resolution — there is no read/write credential split by design. A CCR (Claude Code Remote) session that has none of those three sources set fails **every** `ci_*` tool call identically, not just write-path ones; if a session appeared to have only read tools working, that was other tools (e.g. `ci_audit_session_bash`) not needing a GitHub token at all, not a deliberate split.

**Update (LS-9288):** a recurrence (LS-9288, reported against `ci_list_runs`/`ci_view_run_jobs`) turned out to have all three env sources genuinely configured, yet still fail — the gap was not the env being unset. `github-server/src/index.ts` (backing `legacy-sports-github`) sets a global undici `ProxyAgent` dispatcher from `HTTPS_PROXY`/`GLOBAL_AGENT_HTTPS_PROXY` so its own direct `fetch()` calls route through the CCR session's local egress proxy — the proxy is what actually swaps the session's placeholder `GH_TOKEN` for a real GitHub credential; a raw `fetch()` that bypasses it gets a 401 with the placeholder value. `ci-server/src/index.ts` never had this dispatcher mirrored in, so **every** `ci_*` tool's `fetch()` (shared `github-api.ts`) bypassed the proxy and 401'd, exhausting `resolveToken()`'s fallbacks down to the "no token available" error even with a fully-configured environment. LS-9288 mirrored the same dispatcher setup into `ci-server/src/index.ts`, so this class of failure should no longer reproduce when the env is actually configured — if the error above still occurs after this fix, treat it as the "genuinely unset" case (see the "Fixing the gap itself" paragraph below), not a repeat of the proxy gap.

If a `ci_*` call on this server fails with `No GitHub token available for the legacy-sports-ci-local server`, do **not** attempt to provision a token yourself (Tier-1 rule above) — use the built-in `mcp__github__*` tools instead, which authenticate independently via the platform's own token:

| Failed `legacy-sports-ci-local` tool          | Built-in substitute                                                                                                                                                                                                                                                   |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci_rerun` (failed jobs)                      | `mcp__github__actions_run_trigger({ method: "rerun_failed_jobs", owner, repo, run_id })`                                                                                                                                                                              |
| `ci_rerun` (full run)                         | `mcp__github__actions_run_trigger({ method: "rerun_workflow_run", owner, repo, run_id })`                                                                                                                                                                             |
| `ci_cancel_run`                               | `mcp__github__actions_run_trigger({ method: "cancel_workflow_run", owner, repo, run_id })`                                                                                                                                                                            |
| `ci_dispatch_workflow`                        | `mcp__github__actions_run_trigger({ method: "run_workflow", owner, repo, workflow_id, ref })`                                                                                                                                                                         |
| `ci_view_run` / `ci_list_runs` (read-only)    | `mcp__github__actions_list` / `mcp__github__actions_get` — save output to a temp file and extract fields with `jq`/`python3` rather than reading the full JSON inline; payloads run large (~400 KB at `per_page=15`)                                                  |
| `ci_get_playwright_test_result(source: "s3")` | No direct substitute for the structured pass/fail/flaky report (it needs the same run-id→commit-SHA GitHub API lookup as `ci_view_run`, so it fails identically) — use `mcp__legacy-sports-github__get_job_logs` to pull the failing job's raw logs instead (LS-8887) |

The error message thrown by `resolveToken()` names these substitutes directly (LS-9234, LS-8887) so an agent doesn't have to rediscover them. This does not fix the underlying credential gap — it is a documented fallback. Fixing the gap itself means getting `AGENT_AUTHOR_APP_PRIVATE_KEY` or `GH_TOKEN` set in the CCR environment's settings, which is a user action (Settings → Environment), not something an agent session can do for itself.

### Retired model — do not resurrect

Older docs (the pre-2026-07 `credentials` skill, anything mentioning `MCP_AUTH_TOKEN`) described per-session ~8 h Cognito ID tokens baked into `.mcp.json` URL-server headers, with 401 recovery = "run `node scripts/mcp-auth.mjs`, restart". That flow was **removed** (LS-5094; `scripts/mcp-auth.mjs` now purges the stale `MCP_AUTH_TOKEN*` keys on every run — LS-5219). The script itself still exists but is now the **user-run Track A provisioner** (machine credential + API URLs, needs AWS access) — an agent must never run it, and it is never the answer to a mid-session 401 in a connector session.
