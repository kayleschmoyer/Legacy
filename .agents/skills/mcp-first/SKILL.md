# Skill: MCP-First

> **MCP-first principle**: the shell commands shown in AGENTS.md (Workflow, Commands sections) are **fallbacks** for when MCP servers are unavailable. When MCP tools are available, always prefer them.

## Tool Surfaces

Four independent tool surfaces exist. A session can have any combination — **probe, don't assume** (see [Environment Detection](#environment-detection)).

### Surface 1 — stdio servers (`.mcp.json`)

Registered in the repo-root `.mcp.json`, launched per-session as local processes via `node .github/copilot/hooks/mcp-bootstrap.mjs node --import tsx tools/mcp/<name>-server/src/index.ts`. They need a working `node_modules/.bin/tsx` (see [diagnostics](references/diagnostics.md)). Registration order in `.mcp.json` (matters — see load-order note below):

| `.mcp.json` key             | Tool prefix                        | Purpose                                                                                                                                    |
| --------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `local-git`                 | `mcp__local-git__`                 | `github_create_pr` (create-only PR, jira-link marker) and `github_rebase_pr` — see [PR Creation Routing](#pr-creation-routing)             |
| `worktree`                  | `mcp__worktree__`                  | Worktree lifecycle: status/commit/push/rebase/stash/reset/reflog…, plus `auth_check_all` and `worktree_ping`                               |
| `legacy-sports-make`        | `mcp__legacy-sports-make__`        | Whitelisted Makefile targets: `make_run`, `make_run_wait`, `make_run_status`, `make_worktree_create`, `make_wt_setup`, `validate_pr`       |
| `legacy-sports-nx`          | `mcp__legacy-sports-nx__`          | Nx discovery + execution: `nx_run`, `nx_run_affected`, `nx_run_pc_chunk`, `nx_run_e2e_specs`, `nx_show_project(s)`, `nx_dep_graph`         |
| `legacy-sports-ci-local`    | `mcp__legacy-sports-ci-local__`    | Session audit tools (`ci_audit_session_bash`, `ci_find_session`, `ci_session_stats`) — stdio twin of the ci-server code, reads local files |
| `legacy-sports-aws`         | `mcp__legacy-sports-aws__`         | CloudWatch tailing/filtering, API Gateway inspectors, `aws_sso_status`, `secret_sync_to_github`                                            |
| `legacy-sports-browser`     | `mcp__legacy-sports-browser__`     | Dev server lifecycle, headless screenshots, GitHub image upload                                                                            |
| `legacy-sports-dev-process` | `mcp__legacy-sports-dev-process__` | RFC, ADR, test-plan, repro, continuation-plan, postmortem artifact management                                                              |
| `stripe`                    | `mcp__stripe__`                    | Official `@stripe/mcp` (npx); needs `STRIPE_SECRET_KEY` in env. Use for `lambdas/stripe-webhook`, `lambdas/apple-iap`, billing code        |

> **Load order in native-worktree sessions (LS-2902)**: Claude Code worktree-spawned sessions may only connect the first few servers from `.mcp.json` at session start. Each server is independently available — a missing `worktree` server does **not** imply the others are missing. If a server is absent, probe with its sentinel tool (below) before falling back to shell. **If all stdio servers are missing** (deferred tools list has no `mcp__worktree__*` / `mcp__legacy-sports-make__*` entries), the root cause is almost always a missing `node_modules/.bin/tsx` — see [`references/diagnostics.md`](references/diagnostics.md).

### Surface 2 — hosted OAuth connectors (claude.ai)

The same `tools/mcp/*-server` code deployed to AWS Lambda behind API Gateway, reached over HTTPS. In Claude Code sessions (local **and** web) they connect as **custom remote connectors registered in claude.ai** — they are **not** entries in `.mcp.json`. Five hosted servers exist (Cognito scopes `mcp/{github,jira,ci,db,rollbar}` — see `terraform/main/lambda-mcp-api-gateway.tf`, `aws_cognito_resource_server.mcp`):

| Hosted server           | Tool prefix (live sessions)    | Purpose                                                                                                                                                                                                                                              |
| ----------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `legacy-sports-github`  | `mcp__legacy-sports-github__`  | Full PR/review lifecycle incl. `github_open_pr`, `github_pr_diagnose`, `github_finish_fix_round`, bulk tools                                                                                                                                         |
| `legacy-sports-jira`    | `mcp__legacy-sports-jira__`    | Ticket CRUD, transitions, blocker checks, batch/bulk variants                                                                                                                                                                                        |
| `legacy-sports-ci`      | `mcp__legacy-sports-ci__`      | CI run triage: logs, reruns, dispatch, Playwright reports. ⚠ Playwright report fetches 404 in hosted/cloud sessions — deploys-repo credentials gap, not a missing report; see [read-playwright-report](../read-playwright-report/SKILL.md) (LS-8546) |
| `legacy-sports-db`      | `mcp__legacy-sports-db__`      | `db_query` / `db_migration_status` / `db_migrate` against the dev RDS (no SSM tunnel). `db_migrate` is async (LS-8563): returns `{ jobId, status: "running" }` — poll `db_migration_status({ jobId })` every ~5s until `terminal: true`              |
| `legacy-sports-rollbar` | `mcp__legacy-sports-rollbar__` | Rollbar item triage (`rollbar_list_items`, `rollbar_get_item`, `rollbar_list_occurrences`, `rollbar_get_occurrence` — returns full untruncated `data.body`), `rollbar_top_active_items`, + `rollbar_set_status` (write)                              |

<a id="db-server-name"></a>

> **DB server name — `legacy-sports-db` vs `legacy-sports-db-admin`**: both names refer to the **same** hosted Lambda. The infra name and Cognito scope are `db` (terraform `local.mcp_servers_map`, SSM `/legacy-sports-<env>/mcp/db/api-url`), and the live claude.ai connector exposes tools under `mcp__legacy-sports-db__*` (verified in a live connector session, 2026-07-02). Repo-side artifacts predate that registration and use the alias `legacy-sports-db-admin`: the source dir `tools/mcp/db-admin-server/`, `.github/copilot/copilot-cloud-mcp-config.json` (and the older `.github/copilot/mcp.json`), `.vscode/mcp.json`, and `.claude/settings.json` (AGENTS.md names both since 2026-07-02). The tool **names** (`db_query`, …) are identical either way — call them under whatever prefix your session exposes. (Consequence of the alias: the `.claude/settings.json` allow-list entry `mcp__legacy-sports-db-admin__*` does not match the connector prefix.)

**Auth**: per-user OAuth ("Track B") in Claude Code; Cognito machine bearers ("Track A") on Copilot. See [Auth Model](#auth-model).

### Surface 3 — platform built-ins

- **Harness tools** (always present in Claude Code): `Bash`, `Grep`, `Glob`, `Read`, `ToolSearch`, and `Monitor` (the wait-on-condition tool; it replaced the removed `ScheduleWakeup` — any doc still citing `ScheduleWakeup` is stale).
- **`mcp__github__*` built-ins** (Claude Code on the web): GitHub tools authenticated via the platform's own token. See [Built-in GitHub Tools](#built-in-github-tools-claude-code-on-the-web). **Not available on Copilot Coding Agent.**
- **Atlassian plugin** (`mcp__claude_ai_Atlassian__*`): Jira + Confluence via OAuth 2.1, cloud ID `fb294606-6c8f-4b52-9a41-11fe45b77528`, site `bkrupa.atlassian.net` (verified default in `tools/mcp/jira-server/src/netrc.ts` `JIRA_SITE_URL_DEFAULT`). Fallback when `legacy-sports-jira` is unavailable — see [Jira Operations](#jira-operations).

### Surface 4 — Copilot Coding Agent (`.github/copilot/copilot-cloud-mcp-config.json`)

Copilot cannot participate in OAuth connector flows. The authoritative config is `.github/copilot/copilot-cloud-mcp-config.json` (named "the committed Copilot MCP config" by the `copilot-setup-steps.yml` header; its `mcpServers` object is pasted into Settings → Copilot → Cloud agent). It registers the hosted `legacy-sports-{github,ci,jira,db-admin}` servers as `type: "http"` entries with static `Authorization: Bearer $MCP_*_BEARER` headers — short-lived Cognito `client_credentials` tokens minted by `scripts/mcp-mint-copilot-bearers.mjs` in `copilot-setup-steps.yml` — plus stdio entries for `worktree` (allow-listed tool subset), `legacy-sports-nx`, and `legacy-sports-make`. No `legacy-sports-aws` or browser server by default (per the config's `_instructions`); server-set details are owned by [cloud-agent-mode](../cloud-agent-mode/SKILL.md). (`.github/copilot/mcp.json` is an older Copilot agent-mode config — `servers` key, no tool allowlists, still listed in `tools/mcp/README.md` — not what the cloud coding agent runs; `.vscode/mcp.json` is the analogous config for VS Code IDE agents.)

## Environment Detection

Never assert which environment you are in from prose — probe the actual tool surface with `ToolSearch` and route accordingly:

| Probe (`ToolSearch` query)            | Present means                                            | Absent means                                                                                  |
| ------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `select:worktree_ping`                | stdio servers running (local, or cloud with working tsx) | no stdio servers → run [diagnostics](references/diagnostics.md) Check 1 first                 |
| `select:github_auth_status`           | hosted `legacy-sports-github` connector connected        | connector not consented/registered → [Auth Model](#auth-model)                                |
| `select:nx_run_pc_chunk`              | pc-chunk validation via MCP is **mandatory**             | degraded session → background-Bash chunk path (see [Validation Routing](#validation-routing)) |
| `select:mcp__github__get_me`          | CC-web built-in GitHub tools available                   | not on this platform (e.g. Copilot)                                                           |
| `select:mcp__ccd_session__spawn_task` | chip dispatch available                                  | chips unavailable → see [spawn_task](#spawn_task-and-chips)                                   |

## Server Enablement: `.mcp.json` vs `.claude/settings.json`

Two different files, two different jobs:

- **`.mcp.json`** _registers_ project-scope stdio servers (Surface 1). It contains **only** stdio-launched entries — the hosted servers were removed from it when Claude Code 2.1.100 began silently dropping project-scope HTTP entries (LS-4595, documented in the `scripts/mcp-auth.mjs` header) and moved to claude.ai connectors.
- **`.claude/settings.json#enabledMcpjsonServers`** _auto-approves_ servers from `.mcp.json` so sessions start them without a permission prompt. It is a name list, not a registration.

The two lists intentionally-or-not disagree (verified 2026-07-02):

| Name                                                               | In `.mcp.json` | In `enabledMcpjsonServers` | Effect                                                                                                                     |
| ------------------------------------------------------------------ | :------------: | :------------------------: | -------------------------------------------------------------------------------------------------------------------------- |
| `worktree`, `legacy-sports-make/nx/aws/browser`, `stripe`          |       ✅       |             ✅             | Start without prompting                                                                                                    |
| `local-git`, `legacy-sports-ci-local`, `legacy-sports-dev-process` |       ✅       |             ❌             | Registered but not pre-approved — Claude Code may prompt before connecting. Whether the omission is deliberate is **OPEN** |
| `legacy-sports-github/jira/ci/db-admin`                            |       ❌       |             ✅             | No-op entries — vestiges of the pre-connector era when these were HTTP entries in `.mcp.json`                              |

Separately, `settings.json#permissions.allow` pre-approves _tool calls_ (e.g. `mcp__legacy-sports-github__*`) — that governs permission prompts, not server startup.

## Tool Routing Rules

### PR Creation Routing

**The routing decision — which creation tool per environment, plus the mandatory label sequence — has one home: [pr-lifecycle → PR-creation tool routing](../pr-lifecycle/SKILL.md#pr-creation-tool-routing-one-home--link-here-do-not-restate).** This section holds only the tool-surface facts behind that table:

- `github_open_pr` — registered on the **hosted `legacy-sports-github` connector** only. Semantic one-shot: push branch → create draft → mark ready → apply `bot:ready-for-review`; `draft: true` stops after creation; in Lambda mode `head` is required and push is skipped.
- `github_create_pr` — registered on the **`local-git` stdio server** only (`mcp__local-git__`); create-only, auto-prepends the `<!-- jira-link -->` marker. When no Jira key is provided or derivable from the title, the marker falls back to `primary: none` and the tool applies the `no-jira` label automatically (LS-8298 — Jira Link Check requires that label for `primary: none`); the result surfaces `noJiraLabelApplied`. **Timeout recovery (LS-8213)**: on a transport timeout the tool reconciles by branch lookup and returns `{ success: true, number, url, note }` if the PR was created server-side — do not retry blindly.
- Neither custom surface available → the routing home's built-in and `gh` rows apply; before any `gh pr create` fallback, diagnose and report first (see [diagnostics Reporting Protocol](references/diagnostics.md#reporting-protocol)) — `gh pr create` silently targets the shell's working directory.

`github_create_pr` and `github_open_pr` share the same underlying implementation family (`tools/mcp/github-server/src/tools/create-pr.ts` / `open-pr.ts`; `local-git` imports `createPR` from there) — they are not competing conventions, just different surfaces.

### Pre-flight Auth Check

<a id="auth_check_all"></a>

`auth_check_all` (read-only token-presence check for GitHub/Jira/AWS/CI) lives in the **`worktree` stdio server** (`tools/mcp/worktree-server/src/index.ts`). Availability follows Surface 1: present in local sessions and Copilot (`auth_check_all` is in the `worktree` server's `tools` allowlist in `.github/copilot/copilot-cloud-mcp-config.json`); **absent whenever stdio servers are absent** (degraded CC-web). When it is absent, AGENTS.md's pre-flight mandate is satisfied per-service instead: `github_auth_status`, `jira_auth_status`, `ci_auth_status`, `rollbar_auth_status` on the hosted connectors, `aws_sso_status` on the aws stdio server. If `allAuthenticated: false` (or any per-service check fails): surface the `hint` verbatim and **stop** — see [Auth Model](#auth-model).

### spawn_task and Chips

`mcp__ccd_session__spawn_task` (chip dispatch — each chip is a real independent Claude Code session) is **not registered anywhere in this repo** — no `.mcp.json`, no `tools/mcp/` source. It is injected by the chip-dispatch launcher on the orchestrating machine; its installation/provenance is **OPEN** (not documented in-repo). Detect with `ToolSearch("select:mcp__ccd_session__spawn_task")`. When unavailable, the binding rule is AGENTS.md Tier-2: **stop and inform the user — never substitute `Agent` for chip dispatch on your own authority.** The work-subagent fallback template in [subagent-templates](../subagent-templates/SKILL.md) exists for orchestrators the user has explicitly told to proceed without chips.

### twig

`twig` is an external branch/worktree-management CLI installed on local Windows dev machines — it is not a repo package (no install step in `package.json`/`Makefile`; install source **OPEN**, ask the user if it is missing). Repo integration points: `make pr` (`twig github pr create`), `twig worktree clean` (the only sanctioned worktree removal, AGENTS.md Tier-2), and the `worktree` MCP server, whose `worktree_rebase`/`worktree_remove` wrap twig internally. Detect with `Bash: twig --version`. Cloud environments have **no twig** (AGENTS.md Environment table) — the cloud worktree-server config excludes twig-dependent tools; use `worktree_rebase(base: "origin/main")` semantics or the rebase flow in [worktree-workflow](../worktree-workflow/SKILL.md).

### Validation Routing

Owner ruling (2026-07-02) — the validation execution path is availability-routed:

1. **`nx_run_pc_chunk` present** → it is **mandatory** for every chunk (cloud and timeout-prone sessions; AGENTS.md Tier-2). One call per chunk, canonical order. Calls are transport-safe: a chunk still running at the ~45s in-call budget returns `{ status: "running", jobId }` — follow with `nx_job_wait({ jobId })` (≤55s per call; re-invoke while `status: "running"`), `nx_job_status` for a snapshot, or `nx_job_list` to recover handles after a session resume. Never re-run a chunk that handed back a jobId — re-invoking joins the in-flight job. Sole exception: a terminal `"internal timeout"` error or `orphaned` status may be re-run once (completed tasks stay Nx-cached; LS-8353). Full contract: [repo-tooling](../repo-tooling/SKILL.md#running-validation-per-environment).
2. **`nx_run_pc_chunk` absent** (degraded CC-web: no custom stdio servers) → the sanctioned path is Bash `make pc-<chunk>` with **`run_in_background: true`**, one chunk at a time in the canonical order. `.agents/hooks/enforce-background.mjs` permits background runs and exit-2-blocks the same command foreground — foreground remains banned.
3. **Local non-timeout-prone sessions** → `make_run({ target: "pc" })` is fine.

Chunk order and the full per-platform decision tree are owned by AGENTS.md and [cloud-agent-mode](../cloud-agent-mode/SKILL.md) — do not restate them here.

### Waiting on CI (no polling, no sleep)

- **PR-associated runs — arm the watch before idling (LS-8544)**: before ending any turn with the PR in a non-terminal state, arm the canonical watch monitor — `Monitor({ command: "bash <worktree>/scripts/watch-pr.sh <PR#>", persistent: true, description: "PR #<N> watch" })` — then end the turn. The watch polls harness-side (zero tokens, ~90s cadence) and re-invokes the idle session only on actionable transitions: red required contexts, corroborated merge conflicts, new reviews, escalation labels, SKIPPED-pipeline stalls (`bot-review`/`CI Gate` are commit statuses that go _absent_, never red), and MERGED/CLOSED. It heartbeats `.claude/.pr-watch-armed-<PR#>` so the stop guard (`check-open-pr.sh`) permits idling. Push notifications remain an accelerant when they arrive but are **not load-bearing**: conflict transitions caused by main advancing are surfaced only as an API check run + label + comment and never wake an idle session (observed stuck PRs #6161/#6163). In-context polling remains banned — treat `ci_view_run`/`github_view_pr` as one-shot lookups; polling loops have burned 1–2M tokens per session. Arming precondition: the `Monitor` tool is available **and** `gh` is on PATH; otherwise fall back to the environment rules below. **Binding caveat**: a fix/chip session still on its auto-generated `claude/<name>` branch must never end its turn waiting on a PR event — re-arm `bot:ready-for-review`, report, stop (see [pr-lifecycle drive.md Step 4 + Gotchas](../pr-lifecycle/references/drive.md#step-4-enter-worktree-local-only)).
- **Non-PR `workflow_dispatch` runs** (integration suite on `main`, nightlies): no PR → no push notification. Use `ci_dispatch_workflow({ ..., waitForCompletion: true })` — each call waits at most ~55s (transport-safe). A fast run returns `{ status: "completed", conclusion, durationSeconds }` in one call; a longer run returns `{ status: "in_progress", runId, hint }` — continue with `ci_wait_run({ runId })`, which has the same bounded-wait contract: re-invoke it until `status: "completed"`. Never re-dispatch while a run is in progress.
- **Environments without push notifications** (e.g. Copilot): prefer `waitForCompletion`. If you must wait on a condition in a Claude Code session, use the harness `Monitor` tool — for PR waiting always via `scripts/watch-pr.sh` (never an ad-hoc loop: the canonical script covers commit-status stalls, conflict corroboration, debounce, and loud death) — **`ScheduleWakeup` no longer exists**. Never `sleep N && gh run view` loops, and never `Bash(gh run watch ..., run_in_background: true)` — the watcher dies silently on session resume.
- **Session-resume caveat**: if a bounded wait was in-flight when the session was interrupted, only that one ≤55s call is lost — the run itself is unaffected. Re-find the run with `ci_list_runs({ workflow, branch, limit: 5 })`, then re-attach with `ci_wait_run({ runId })`. Do not re-dispatch.

## Auth Model

This section absorbed the former `credentials` skill (2026-07-02). One rule dominates everything below:

> **Tier-1 (AGENTS.md Safety): never run auth-generation commands.** `aws sso login`, `gh auth login`, `acli auth login`, OAuth device flows, and credential-provisioning scripts (`node scripts/mcp-auth.mjs`, `make e2e-auth`) are **user-only** actions. On any auth/expired-token error: stop, surface the `hint` verbatim, prompt the user. Falling back to `gh`/`acli`/raw `curl` does not work around a missing token — it masks the failure and pollutes the MCP gap audit.

### Auth per surface

| Surface                         | Credential                                                                                                                                                                                                 | Failure symptom → recovery                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Hosted connectors (Claude Code) | Per-user OAuth via claude.ai custom connectors ("Track B") — setup home: [`docs/dev-process/mcp-connector-access.md`](../../../docs/dev-process/mcp-connector-access.md)                                   | Mid-session HTTP 401 (often surfaced as `ZodError: expected string, received undefined`) → **`/mcp` re-consent is the ONLY recovery** (Claude Code does not auto-refresh MCP OAuth tokens — upstream [claude-code#58607](https://github.com/anthropics/claude-code/issues/58607)). No retry, no CLI fallback. Full protocol: [diagnostics — Mid-Session 401](references/diagnostics.md#mid-session-401--token-expiry-ls-4874). |
| Hosted servers (Copilot)        | Cognito `client_credentials` machine bearers ("Track A"), minted in `copilot-setup-steps.yml`                                                                                                              | Bearer expiry inside one job is not agent-recoverable — report and stop.                                                                                                                                                                                                                                                                                                                                                       |
| stdio servers                   | Read env at spawn: `.env.local` symlinked into worktrees, plus `settings.json#env`. Examples: `STRIPE_SECRET_KEY` (stripe), AWS SSO session (aws server), `ROLLBAR_READ_ACCESS_TOKEN` (rollbar stdio mode) | Servers read credentials **at startup** — after the user refreshes anything, the session must restart; mid-session env edits never propagate to already-spawned transports.                                                                                                                                                                                                                                                    |
| CC-web GitHub built-ins         | Platform-managed token                                                                                                                                                                                     | Not agent-recoverable; report.                                                                                                                                                                                                                                                                                                                                                                                                 |
| Web-e2e live-backend JWT        | `make e2e-auth` caches at `~/.legacy-sports/e2e-token.json` — **human-only interactive handshake** (AGENTS.md Environment)                                                                                 | `nx_run_e2e_specs` integration mode warns when stale → ask the user to run `make e2e-auth`.                                                                                                                                                                                                                                                                                                                                    |

### Retired model — do not resurrect

Older docs (the pre-2026-07 `credentials` skill, anything mentioning `MCP_AUTH_TOKEN`) described per-session ~8 h Cognito ID tokens baked into `.mcp.json` URL-server headers, with 401 recovery = "run `node scripts/mcp-auth.mjs`, restart". That flow was **removed** (LS-5094; `scripts/mcp-auth.mjs` now purges the stale `MCP_AUTH_TOKEN*` keys on every run — LS-5219). The script itself still exists but is now the **user-run Track A provisioner** (machine credential + API URLs, needs AWS access) — an agent must never run it, and it is never the answer to a mid-session 401 in a connector session.

## Tool-First Concrete Substitutions

These are the specific built-in tool substitutions agents should reach for automatically instead of the Bash equivalents:

| Shell command                                                                                  | Built-in tool replacement                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `grep -r "pattern" dir/`                                                                       | `Grep(pattern: "pattern", path: "dir", output_mode: "content")`                                                                                                                                                                                                                                                                                                                                                                                  |
| `grep -rn "pattern" dir/`                                                                      | `Grep(pattern: "pattern", path: "dir", output_mode: "content")` — `-n` is implicit: line numbers are always included in content mode; `-r` (recursive) is also the default behaviour                                                                                                                                                                                                                                                             |
| `grep -rl "pattern" dir/`                                                                      | `Grep(pattern: "pattern", path: "dir", output_mode: "files_with_matches")`                                                                                                                                                                                                                                                                                                                                                                       |
| `grep -rl "pattern" dir/ --include="*.ts"`                                                     | `Grep(pattern: "pattern", path: "dir", glob: "**/*.ts", output_mode: "files_with_matches")`                                                                                                                                                                                                                                                                                                                                                      |
| `grep -n "pattern" file`                                                                       | `Grep(pattern: "pattern", path: "file", output_mode: "content")` — line numbers are included by default in content mode; works for single files as well as directories                                                                                                                                                                                                                                                                           |
| `grep -i "pattern" file`                                                                       | `Grep(pattern: "pattern", path: "file", "-i": true, output_mode: "content")` — case-insensitive flag maps directly to the `-i` parameter                                                                                                                                                                                                                                                                                                         |
| `grep -rni "pattern" dir/`                                                                     | `Grep(pattern: "pattern", path: "dir", "-i": true, output_mode: "content")` — combine recursive + line numbers + case-insensitive; `-r`/`-n` are implicit, only `-i` needs an explicit parameter                                                                                                                                                                                                                                                 |
| `cat file`                                                                                     | `Read(file_path: "...")`                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `head -N file`                                                                                 | `Read(file_path: "...", limit: N)`                                                                                                                                                                                                                                                                                                                                                                                                               |

**Heavy targets are transport-safe by default (LS-8558, LS-8559).** Cloud Claude Code sessions enforce a ~60s MCP transport timeout on every tool call. `make_run` (and the job-backed nx tools `nx_run`, `nx_run_affected`, `nx_run_e2e_specs`, `nx_install_package`), plus `worktree_run` / `worktree_run_all` on the worktree server, now always run the underlying process as a background job with a ~45s bounded wait: fast targets return their result in one call, and anything slower returns `{ status: "running", jobId }` instead of blocking into the transport timeout. Never re-invoke the tool while its job runs — poll instead:

```
make_run({ target: "build-all" })   // fast → full result; slow → { jobId, status: "running" }
make_run_wait({ jobId })            // blocks ≤55s; re-call if it returns status: "running"
make_run_status({ jobId })          // non-blocking snapshot (status + log tail)
// nx tools poll with nx_job_wait({ jobId }) / nx_job_status({ jobId }) instead
// git-heavy github tools poll with github_job_wait({ jobId }) / github_job_status({ jobId }) instead
// worktree tools poll with worktree_job_wait({ jobId }) / worktree_job_status({ jobId });
// worktree_job_list recovers job handles after a server restart. worktree_run keeps its
// 120s process cap — long-running work still belongs in nx_run_pc_chunk / make_run / nx_run.
```

`make_run_wait` returns the full structured result (with `steps[]` for multi-step targets like `pre-commit`/`full-check`) once the job reaches `done`/`failed`; `nx_job_wait` likewise returns the originating tool's structured result (e.g. the playwright report for `nx_run_e2e_specs`). `runInBackground: true` still exists to skip the initial bounded wait and return the jobId immediately. (Validation routing is unchanged — see [Validation Routing](#validation-routing).)

The same contract covers the git-heavy github tools (LS-8562): `github_rebase_pr` (stdio `local-git` server), `github_bulk_rebase`, and `github_open_pr`'s push phase each run under a ~45s sync budget and may return `{ jobId, status: "running" }` — poll with `github_job_wait` / `github_job_status` **on the same server that returned the jobId** (job registries are per-process). `github_bulk_rebase` reports per-PR progress in `logTail`. These jobs are in-process and do not survive an MCP server restart — if a jobId is lost, verify the outcome (`github_view_pr`, `worktree_status`) instead of re-running. Only the stdio deployments are affected — the Lambda deployment has no `git` binary on its PATH, so `rebasePR`/`bulkRebase` route to a git-free GitHub API merge-style update there instead (`PUT /pulls/{number}/update-branch`) rather than the sync-budget/job path; this produces a merge commit, not a linear rebase (LS-7753).

The aws-server long-runners follow the same contract (LS-8560): `packer_build` always runs the build (including `packer init`) in the background with a 45s initial wait, returning either the finished result or `{ status: "running", buildId }`; `packer_build_wait` is capped at 55s per call and returns a non-error running snapshot with a re-arm hint; `aws_ssm_run_command` polls ≤55s per call and re-arms via `aws_ssm_run_command({ instanceId, commandId })` — never re-send the command while it is in progress.

The nx, make, and packer job runners share one engine — `@legacy-sports/mcp-jobs` in `lib/mcp-jobs` (LS-8564) — so make/packer jobs now also survive an MCP server restart (metadata persists on disk; a restarted server can still answer `make_run_status` / `packer_build_status` for jobs it did not spawn, reporting `orphaned` when the result was never recorded), and internal timeouts kill the whole process tree, not just the direct child. Internal timeouts are also success-aware for opted-in jobs (LS-8320): `nx_run_pc_chunk` gives the heavy full-monorepo chunks (`pc-lint`, `pc-test`) a longer process timeout than the other five, and if the timeout still fires after the chunk's nx success line is already in the log, the job is finalized as **passed** with `recoveredFromTimeout: true` (surfaced by `nx_run_pc_chunk` / `nx_job_wait` / `nx_job_status`) instead of the false `Process killed after Nms (internal timeout)` failure.

**`make_run` output is compact by default.** The `output` field omits prettier per-file listings (collapsed to `[Formatting: N files checked, M changed]`) and truncates each step body to 20 lines with a `[N more lines — run step directly for full output]` note. Pass `verbose: true` only when you genuinely need the full raw output for debugging.

> **If you find yourself writing `make <target>` in a Bash tool call during a local session, treat this as a signal that the `legacy-sports-make` MCP server is not connected.** Check server connectivity rather than falling back silently — raw `make pc` will fail with `nx: not found` or similar PATH errors when `node_modules/.bin` is not in `$PATH`. Using `make_run` via MCP avoids this PATH resolution problem entirely. If `make pc` fails with `ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL Command "nx" not found`, the `node_modules` symlink is broken or missing — repair it with `worktree_install_recover()` (MCP-first), **not** `node scripts/modules-pool/link.mjs` via Bash. After recovery, restart the session so the MCP servers reconnect.

## Git Operations in Worktrees

Use `worktree_rebase_onto_main` instead of the fetch → rebase → push chain when syncing a branch with `main` (handles merge conflicts gracefully and pushes with `--force-with-lease`). Use `worktree_commit` instead of `git add`/`git commit` via Bash — it handles staging and committing in one operation, refuses to stage likely credential/secret files (e.g., `.env`, `credentials.*`, `*.pem`, `*.key`), and supports `amend: true` to fix commit messages before push (pass `message` to replace, omit it to keep the existing message with `--no-edit`); add `resetAuthor: true` to also reset the commit author (e.g. after setting `git config user.email` in a cloud session). Use `worktree_checkout_file` instead of `git checkout [HEAD] -- <file>` to restore files to HEAD (discarding both staged and unstaged changes). Use `worktree_push` (supports `setUpstream`) instead of `git push`, `worktree_rebase` (pass `disableRerere: true` if a stale rr-cache entry is causing conflict markers to be silently committed) instead of `git fetch origin && git rebase origin/main` (or `git fetch && twig rebase`), `worktree_rebase_continue` instead of `GIT_EDITOR=true git -C ... rebase --continue` (the tool suppresses the editor prompt internally — `GIT_EDITOR=true` is unnecessary), `worktree_fetch` instead of `git fetch origin`, `worktree_stash`/`worktree_stash_pop` instead of `git stash`/`git stash pop`, `worktree_unstage` instead of `git reset HEAD -- <files>`, `worktree_rm` instead of `git rm` or deleting files, `worktree_is_tracked` instead of `git ls-files`, and `worktree_check_ignore` instead of `git check-ignore`. Use `worktree_run` only as the **catch-all for git commands that have no dedicated tool** (e.g., `git merge-base`, `git cherry-pick`, `git tag`, `git add <file>` after manually resolving a merge conflict). These tools auto-resolve the worktree directory, refuse dangerous operations (pushing `main`, pushing during rebase), and require no manual `cd` or `-C` flags. Never use `git -C $wt <command>` via Bash when `worktree_run` can handle it.

**`worktree_run` shell on Windows**: uses Git Bash (`bash.exe` from Git for Windows) when available, falling back to `cmd.exe`. When Git Bash is used, common Unix shell idioms and utilities such as `&&`, `|`, `head`, and `grep` are available. When it falls back to `cmd.exe`, only cmd built-ins and operators like `&&` and `|` are supported — do not rely on Unix utilities (`head`, `grep`, etc.). Avoid PowerShell-specific syntax in `worktree_run` commands.

## File Size & Line Count

Use `worktree_file_info({ paths: [...] })` instead of `wc -l file1 file2 ...` via Bash to get byte sizes and, when available, line counts and approximate token counts for one or more files in a single round-trip. For files larger than 10MB, the tool returns only `bytes` (no `lines` or `approxTokens`); if `approxTokens` is omitted, fall back to `bytes` (dividing by 4 gives a rough token estimate) to decide whether `Read` will fit within its 10k-token limit or whether `offset`/`limit` chunking is needed. Accepts both relative paths (resolved against the worktree root) and absolute paths within the worktree root.

**Merge-conflict verdicts union three signals**: `github_pr_why_blocked`, `github_pr_diagnose`, `github_pr_dashboard`, and `github_pr_scan` classify a PR as conflicting when ANY of GraphQL `mergeable: CONFLICTING`, the `CI: Conflicts` label, or a failing required "No Merge Conflicts" check fires (shared helper: `tools/mcp/github-server/src/conflict-signals.ts`). The label/check come from a deterministic `git merge` test and stay reliable while `mergeable` is `UNKNOWN`/stale after a base push — so a `MERGE_CONFLICT` verdict means rebase even if `mergeable` reads `MERGEABLE`. The dashboard's JSON rows expose this as `hasConflictSignal`; `CI_FAILING` verdicts carry a "conflicts cannot be ruled out yet" note while `mergeable` is `UNKNOWN`.

**PR number parameter names**: most `legacy-sports-github` tools use `number` (integer) for the PR number, **not** `prNumber`. Passing `prNumber` where `number` is expected causes an `Invalid input: received NaN` validation error. The tools `github_view_pr`, `github_merge_pr`, `github_get_review_threads`, `github_get_check_runs`, `github_mark_pr_ready`, `github_pr_why_blocked` (both LS-8214), and `github_manage_labels` accept `prNumber` as an alias — but `github_request_review` uses `prs` (array; also accepts `prNumber` as single-item alias). When in doubt, pass `number: N` for single-PR tools and `prs: [N]` for multi-PR tools. Remaining single-name tools are tracked in LS-8678.

**GitHub auth-aware routing**: call `github_auth_status` at the start of any GitHub workflow. If `configured: true`, use our custom GitHub MCP tools. If `configured: false`, **stop and prompt the user** — do not silently fall back. Tell them their GitHub credentials are missing or expired, and direct them to set `GH_TOKEN`/`GITHUB_TOKEN`, run `gh auth login`, or configure `AGENT_AUTHOR_APP_PRIVATE_KEY` (see [cloud-agent-mode](../cloud-agent-mode/SKILL.md)). Only fall back to `gh` CLI after the user confirms their `gh` auth is working or explicitly asks you to try the CLI fallback. **In Lambda**: the `fallback` field in the `configured: false` response contains a Lambda-specific diagnosis (key missing vs. exchange failed); for operator remediation steps see `docs/dev-process/mcp-github-lambda-ops.md`.

## CI Operations

Use `ci_list_runs`, `ci_view_run`, `ci_get_logs`, `ci_search_logs`, `ci_rerun`, `ci_rerun_failed_jobs`, `ci_retry_failed`, `ci_cancel_run`, and `ci_cancel_runs` instead of `gh run` commands via Bash. `ci_list_runs` accepts `limit` up to 100 (default 10). These tools parse and structure log output for agent consumption. When the triage path is "this run failed → rerun the failed jobs", prefer the semantic one-shot `ci_retry_failed({ runId })` — it returns the failed-job list and an error-pattern snippet from the original logs in the same call. Use `ci_cancel_run({ runId })` to kill a stale-SHA or no-longer-needed run instead of leaving it running — e.g. serializing expensive live-backend integration dispatches so a fresh run never races a stale one on the same branch (LS-7878); use `ci_cancel_runs({ workflow, branch })` to cancel every in-flight run of a workflow on a branch in one call.

**`ci_get_logs` transient 502/503/504 errors**: the log-blob fetch path retries automatically (3 attempts, exponential backoff) as of LS-8218. If `ci_get_logs` still fails after retries, use `get_job_logs` via `legacy-sports-github` as a fallback (see table below).

**`ci_rerun` / `ci_rerun_failed_jobs` / `ci_retry_failed` "already running" 403**: GitHub's workflow-run status (what the rerun endpoints gate on) can lag the per-job status `ci_view_run_jobs` reports, so a rerun can be rejected with a 403 "already running"/"already in progress" even after all jobs look complete. As of LS-8284 this is retried automatically (up to 3 attempts, ~10s/~20s backoff) instead of surfacing the error — no empty-commit workaround needed. If the tool still errors, the message states how many attempts were made; other 403s (e.g. permissions) still fail immediately, unchanged.

**`ci_get_logs` on a job that never started (LS-7910)**: a job that failed before any step executed (runner provisioning failure, hosted-runner billing/spending limit, or a GitHub Actions incident) has no log blob. `ci_get_logs` detects this and returns "Job failed before any step executed -- no logs exist..." instead of a raw Azure Blob Storage 404 — treat that message as the terminal signal (check the run/job conclusion and runner status) rather than retrying the log fetch.

**`ci_get_logs` / `ci_search_logs` on large `workflow_dispatch` runs (LS-8255)**: log fetches are capped at 10 jobs per call with a 20 s deadline. If the response includes `skippedJobs`, narrow scope using `jobName` or `jobId` to fetch specific job logs. Timeout errors include an actionable hint with the same guidance.

`ci_get_logs` enforces `maxChars` and `truncateLineLength` as **hard caps** on the serialized response — always pass `maxChars` when individual log lines may be multi-KB (e.g. `maxChars: 80000, truncateLineLength: 300`) to prevent context overflow. When truncation occurs the response ends with `... [truncated at N chars]`.

**`ci_search_logs` (LS-8390)**: also accepts `maxChars` (default 50000) and `truncateLineLength` (applied to the matched line and every before/after context line, default 500/200) — pass these when `contextBefore`/`contextAfter` are non-trivial and log lines may be long, since per-match context can overflow the token limit in aggregate even when `limitMatches` bounds the match count. When the char cap forces trailing matches to be dropped, the response carries `charTruncated: true` and an adjusted `returnedMatches`.

**`ci_search_logs` zero-scope results (LS-8301)**: `failedOnly` defaults to `true`, so a run whose only relevant job actually succeeded (e.g. a successful merge-queue job) can be filtered out of scope entirely — the response still returns `totalMatches: 0`, but check `jobsSearched`/`jobsTotal` and a `scopeNote` field before concluding the pattern is genuinely absent. A `scopeNote` present means 0 jobs were searched; retry with `failedOnly: false` to search successful-job logs too. Separately, `|` in `pattern` is matched as a **literal** character unless `isRegex: true` is also set — alternation (`a|b|c`) silently does not work otherwise, a second way to get a false "0 matches".

When acting on **several runs at once** (unblocking or re-validating multiple PRs), prefer the batch variants over a per-run loop: `ci_rerun_batch({ runIds: [...] })` reruns up to 50 runs and `ci_view_run_batch({ runIds: [...] })` inspects up to 50, each returning the shared partial-failure shape `{ success, total, succeeded, failed }` so one run erroring never fails the whole call. The single-run tools remain for one-off use. (`ci_get_logs` already accepts `runIds` for batch log fetches.)

## Jira Operations

**Auth-aware routing and fallback order**: call `jira_auth_status` before any Jira operation when the `legacy-sports-jira` tools are exposed. If `configured: true`, use `jira_*` MCP tools. If `configured: false` or they fail, use the Atlassian plugin. Fallback chain: `jira_*` MCP tools → Atlassian plugin (`mcp__claude_ai_Atlassian__*`) → `acli` CLI (last resort, local-only).

**When `jira_*` tools are absent from the session** (the `legacy-sports-jira` hosted connector is not connected — availability is per-session consent, see [Auth Model](#auth-model)): do NOT fall back to `acli`. Use the Atlassian plugin directly: `mcp__claude_ai_Atlassian__transitionJiraIssue`, `mcp__claude_ai_Atlassian__getJiraIssue`, etc. (cloud ID `fb294606-6c8f-4b52-9a41-11fe45b77528`). `acli` is only for local sessions where both the connector and the Atlassian plugin are confirmed unavailable.

**Description fields accept Markdown**: `description`, `context`, `risk`, and `planningNotes` params on `jira_create_ticket`, `jira_bulk_create_tickets`, and `jira_edit_ticket` all parse Markdown to ADF before sending to Jira. Bullet lists (`-`/`*`/`+`), numbered lists, fenced code blocks, ATX headings, **bold**, _italic_, and `inline code` all render correctly in the Jira UI. Plain text is unchanged — no migration needed for existing calls.

**`jira_create_ticket` hints on an invalid Story parent**: a `Bug`/`Task` cannot parent to a `Story` — only an Epic can (see [plan-ticket's Hierarchy section](../plan-ticket/references/create.md#hierarchy)). If this 400s (`"Please select valid parent issue"`), the error response includes a `hint` field naming the epic-parent + `jira_link_issues(..., linkType: "Relates")` workaround (LS-8481) — read it instead of retrying blind.

Use `jira_list_children` instead of `searchJiraIssuesUsingJql` with `parent = LS-####` to list children of an epic or story. Raw JQL returns verbose markdown-formatted output that can overflow the MCP context limit (~192K chars for 50 results); `jira_list_children` returns compact structured JSON with pagination support. Pass `paginate: true` to fetch **all** children in a single call — the tool paginates internally and returns `{ parent, total, children: [{key, summary, status}], truncated? }` (hard-capped at 500 items; `truncated: true` when the cap is hit). Use `paginate: true` whenever the parent is an epic or bucket with potentially 100+ children to avoid manual `pageToken` threading.

For any other JQL query, use `jira_search` instead of `searchJiraIssuesUsingJql`. The Atlassian plugin's tool returns ~3.8 KB per issue (~190 KB for 50 results) due to metadata envelope overhead (expand URLs, self links, avatar URLs, statusCategory objects) even when minimal fields are requested. Use `compact: true` for large result sets to get `{ issues: [{key, summary, status}], nextPageToken? }` (~2 KB for 50 issues). When the response includes `nextPageToken`, pass it as `pageToken` to fetch the next page.

**Batch variants (call once instead of N times in a loop)**: when operating on multiple tickets, prefer the `*_batch` / `bulk_*` tools over looping the single-item tool. Each accepts an array (max 50) and isolates per-item failures so one bad input never fails the whole call. Two distinct response shapes are in use today:

- **Operation-style** `{ total, succeeded, failed }` — used by tools that perform writes or where per-item identity is naturally a list: `jira_transition({ keys: [...] })` (multi-key status change; `jira_bulk_transition` is a deprecated alias), `jira_bulk_create_tickets`, `jira_bulk_edit` (summary/description/type/sprint/parent across N tickets), `jira_bulk_link_issues` (N issue links; same inward/outward contract as `jira_link_issues`), and `jira_bulk_list_children` (children of N parents in one call — returns the first page per parent; a parent's `nextPageToken`, when present, signals truncation, so page that parent with single-item `jira_list_children`).
- **Read-style** `{ <items>: { [key]: ... }, missing: [key, ...] }` — used by reads where the natural answer is a key→record map: `jira_view({ keys: [...] })` returns `{ tickets: { [key]: ticket }, missing: [key, ...] }`. Pass `include: ['comments']` or `include: ['transitions']` to fetch sub-resources in the same call (replaces the former `jira_get_comments` / `jira_get_transitions` tools).

Single-item tools are retained for one-off use.

**Claim mode assignee resolution (LS-7891, precedence fixed in LS-8302)** — applies to `jira_transition({ ..., action: "claim" })`, the deprecated `jira_claim_ticket` alias, and `jira_start_work`: on a successful claim the ticket is assigned using the first available of: `assignee` email param → `JIRA_ASSIGNEE_ACCOUNT_ID` env var (pre-resolved accountId, no lookup call) → `JIRA_ASSIGNEE_EMAIL` env var (resolved via `/rest/api/3/user/search`) → `GET /rest/api/3/myself`. ACCOUNT_ID is checked before EMAIL because on the **hosted Lambda** only the accountId path works — the service account's client-credentials token lacks the `read:jira-user` scope required by `/myself` and `/user/search`, so email-based resolution always 401s there (the claim still succeeds; assignment fails with a non-fatal warning). Prior to LS-8302, EMAIL was checked before ACCOUNT_ID, which made the accountId fallback unreachable dead code whenever both env vars were configured (the deployed state). The Lambda's accountId comes from the `jira_assignee_account_id` terraform variable. Email-based resolution works in local basic-auth sessions.

**LS-3810 caveat — `transitionJiraIssue` response body bug**: the Atlassian plugin's `transitionJiraIssue` response body returns data for a different issue — the returned `key`/`id` will not match the requested issue key (sometimes off-by-one in the key sequence). The transition itself succeeds, but always re-verify: call `searchJiraIssuesUsingJql(cloudId: "fb294606-6c8f-4b52-9a41-11fe45b77528", jql: "key = LS-XXXX", maxResults: 1, fields: ["status"])`, confirm `issues[0].key` matches the requested key, and check `issues[0].fields.status.name` to confirm the transition. The custom `jira_transition` MCP tool is not affected by this bug.

**LS-3715 — `getJiraIssue` returns parent epic's children instead of the requested issue**: the Atlassian plugin's `getJiraIssue` tool returns the parent epic's children list instead of the requested single issue. **Never use `mcp__*__getJiraIssue` to fetch a single ticket.** Use `searchJiraIssuesUsingJql(cloudId: "fb294606-6c8f-4b52-9a41-11fe45b77528", jql: "key = LS-XXXX", maxResults: 1)` instead, or the custom `jira_view` MCP tool (unaffected by this bug).

**LS-3771 — `transitionJiraIssue`/`createJiraIssue` cold-start encoding bug**: both Atlassian plugin tools reject nested object parameters (`transition: { id }` and `additional_fields`) with "expected object, received string" during a cold-start window. **Mitigation for transitions**: retry once after any other successful plugin call; if that still fails — in a local session fall through to `acli jira workitem transition --key LS-#### --status "<Status>" --yes`; in a cloud session use `jira_transition` from the custom MCP server if available, otherwise transition manually in the Jira UI. **Mitigation for creates with parent**: use `jira_create_ticket({ summary: "...", parent: "LS-####" })` (custom server, unaffected) when available. If the custom server is unavailable, create the ticket without parent then set it via `editJiraIssue({ cloudId: "fb294606-6c8f-4b52-9a41-11fe45b77528", issueIdOrKey: "LS-CHILD", fields: { parent: { key: "LS-PARENT" } } })`.

## AWS Operations

Use `aws_logs_tail` instead of `aws logs tail` via Bash, and `aws_sso_status` to check credentials before any AWS operation. If `aws_sso_status` returns expired or unconfigured, **stop immediately and prompt the user to run `aws sso login`** — do not retry the failing command. See `.agents/skills/infrastructure/references/aws-sso-login.md` for the exact prompt pattern.

`aws_logs_tail` defaults to markdown (extracted `### Errors` from `ERROR`/`WARN`/`Exception`/`Error:` lines + their stack frames, followed by a `### Recent` code-block with the last 50 lines). Pass `format: 'json'` only when you need the structured payload (e.g. piping into another tool). Pass `functions: string[]` (1-10) for batch mode — per-function blocks fetched concurrently (cap 5). For historical incident forensics, pass `startTime` + `endTime` (ISO-8601, e.g. `2025-06-01T00:00:00Z`) to pin an exact absolute window instead of the rolling `since` lookback; `maxLines` cap still applies.

For searching arbitrary log groups (including `/aws/apigateway/...` access logs) or scoping to a precise time window, use `aws_logs_filter` instead. It accepts any `logGroup` (leading-slash names handled natively — no `MSYS_NO_PATHCONV` needed), an optional `filterPattern`, and `startTime`/`endTime` as epoch milliseconds. Output is hard-capped at 50 events or 20 000 chars (`truncated: true` when hit).
