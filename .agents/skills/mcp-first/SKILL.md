## Tool Surfaces

Four independent tool surfaces exist. A session can have any combination — **probe, don't assume** (see [Environment Detection](#environment-detection)).

> **`aws_terraform_output` from a worktree session (LS-5209)**: worktree checkouts never have `.terraform/` initialized (only the main checkout does), so a bare call would fail with "Backend initialization required". The tool now falls back automatically: on a not-initialized error it retries the same relative `chdir` (default `terraform/main`) against the main checkout, resolved via `git worktree list` (main checkout is always the first entry) or a `MAIN_REPO_PATH` env var override. No caller-side workaround needed; pass an explicit `chdir` only to target a non-default Terraform directory (e.g. `terraform/runners`).

> **Load order in native-worktree sessions (LS-2902)**: Claude Code worktree-spawned sessions may only connect the first few servers from `.mcp.json` at session start. Each server is independently available — a missing `worktree` server does **not** imply the others are missing. If a server is absent, probe with its sentinel tool (below) before falling back to shell. **If all stdio servers are missing** (deferred tools list has no `mcp__worktree__*` / `mcp__legacy-sports-make__*` entries), the root cause is almost always a missing `node_modules/.bin/tsx` — see [`references/diagnostics.md`](references/diagnostics.md).

> **DB server name — `legacy-sports-db` vs `legacy-sports-db-admin`**: both names refer to the **same** hosted Lambda. The infra name and Cognito scope are `db` (terraform `local.mcp_servers_map`, SSM `/legacy-sports-<env>/mcp/db/api-url`), and the live claude.ai connector exposes tools under `mcp__legacy-sports-db__*` (verified in a live connector session, 2026-07-02). Repo-side artifacts predate that registration and use the alias `legacy-sports-db-admin`: the source dir `tools/mcp/db-admin-server/`, `.github/copilot/copilot-cloud-mcp-config.json` (and the older `.github/copilot/mcp.json`), `.vscode/mcp.json`, and `.claude/settings.json` (AGENTS.md names both since 2026-07-02). **Auth**: per-user OAuth ("Track B") in Claude Code; Cognito machine bearers ("Track A") on Copilot. See [Auth Model](#auth-model).

> **Self-served tool reference (`GET /docs`, LS-9593)**: each of the five hosted servers exposes its own tool reference at `GET /docs`, behind the same Cognito bearer its other tools require, generated at build time and redeployed with the server. For a no-token offline copy covering all eleven servers (stdio + hosted), see `docs/mcp/api-reference.html`.

### Surface 3 — platform built-ins

- **Harness tools** (always present in Claude Code): `Bash`, `Grep`, `Glob`, `Read`, `ToolSearch`, and `Monitor` (the wait-on-condition tool). `ScheduleWakeup` still exists but is scoped to `/loop` dynamic pacing — it is **not** a PR/CI wait primitive; use `Monitor` or the [Periodic Wake Protocol](references/waiting-and-wakeups.md#periodic-wake-protocol) for those (verified 2026-09-03).
- **`mcp__github__*` built-ins** (Claude Code on the web): GitHub tools authenticated via the platform's own token. See [Built-in GitHub Tools](#built-in-github-tools-claude-code-on-the-web). **Not available on Copilot Coding Agent.**
- **Atlassian plugin** (`mcp__claude_ai_Atlassian__*`): Jira + Confluence via OAuth 2.1, cloud ID `fb294606-6c8f-4b52-9a41-11fe45b77528`, site `bkrupa.atlassian.net` (verified default in `tools/mcp/jira-server/src/netrc.ts` `JIRA_SITE_URL_DEFAULT`). Fallback when `legacy-sports-jira` is unavailable — see [Jira Operations](#jira-operations).

### Surface 4 — Copilot Coding Agent (`.github/copilot/copilot-cloud-mcp-config.json`)

Copilot cannot participate in OAuth connector flows. The authoritative config is `.github/copilot/copilot-cloud-mcp-config.json` (named "the committed Copilot MCP config" by the `copilot-setup-steps.yml` header; its `mcpServers` object is pasted into Settings → Copilot → Cloud agent). It registers the hosted `legacy-sports-{github,ci,jira,db-admin}` servers as `type: "http"` entries with static `Authorization: Bearer $MCP_*_BEARER` headers — short-lived Cognito `client_credentials` tokens minted by `scripts/mcp-mint-copilot-bearers.mjs` in `copilot-setup-steps.yml` — plus stdio entries for `worktree` (allow-listed tool subset), `legacy-sports-nx`, and `legacy-sports-make`. No `legacy-sports-aws` or browser server by default (per the config's `_instructions`); server-set details are owned by [cloud-agent-mode](../cloud-agent-mode/SKILL.md). (`.github/copilot/mcp.json` is an older Copilot agent-mode config — `servers` key, no tool allowlists, still listed in `tools/mcp/README.md` — not what the cloud coding agent runs; `.vscode/mcp.json` is the analogous config for VS Code IDE agents.)

## Server Enablement: `.mcp.json` vs `.claude/settings.json`

Two different files, two different jobs:

- **`.mcp.json`** _registers_ project-scope stdio servers (Surface 1). It contains **only** stdio-launched entries — the hosted servers were removed from it when Claude Code 2.1.100 began silently dropping project-scope HTTP entries (LS-4595, documented in the `scripts/mcp-auth.mjs` header) and moved to claude.ai connectors.
- **`.claude/settings.json#enabledMcpjsonServers`** _auto-approves_ servers from `.mcp.json` so sessions start them without a permission prompt. It is a name list, not a registration.

The two lists intentionally-or-not disagree (verified 2026-08-10):

| Name                                                              | In `.mcp.json` | In `enabledMcpjsonServers` | Effect                                                                                                                     |
| ----------------------------------------------------------------- | :------------: | :------------------------: | -------------------------------------------------------------------------------------------------------------------------- |
| `worktree`, `legacy-sports-make/nx/aws/browser/android`, `stripe` |       ✅       |             ✅             | Start without prompting                                                                                                    |
| `legacy-sports-ci-local`, `legacy-sports-dev-process`             |       ✅       |             ❌             | Registered but not pre-approved — Claude Code may prompt before connecting. Whether the omission is deliberate is **OPEN** |
| `legacy-sports-github/jira/ci/db-admin`                           |       ❌       |             ✅             | No-op entries — vestiges of the pre-connector era when these were HTTP entries in `.mcp.json`                              |

> The `local-git` stdio server (former home of `github_create_pr` / `github_rebase_pr`) was **removed** in LS-9294 (owner ruling 2026-08-10): it was registered but never enabled or approved, so its tools never actually loaded in sessions, while the skills still documented them as canonical — the hosted `github_open_pr` composite is the single create surface now. If you encounter a doc still routing to `github_create_pr`, treat it as stale and fix it.

Separately, `settings.json#permissions.allow` pre-approves _tool calls_ (e.g. `mcp__legacy-sports-github__*`) — that governs permission prompts, not server startup.

> **No stdio `legacy-sports-jira` entry — intentional, do not add one (LS-9370).** `.mcp.json` has never carried a stdio-launched `jira-server` entry alongside the hosted `legacy-sports-jira` connector, even though `tools/mcp/jira-server` exists as a buildable stdio server (it also backs the hosted Lambda deployment and the Copilot/CCR machine-bearer paths). Registering it as a second, always-local stdio source would put two independently-authenticated servers behind the same `jira_*` tool names in the same session — whichever one wins isn't predictable, and it duplicates the OAuth-vs-stdio-credential split the connector migration (LS-4595, see above) was meant to collapse into one path. The late-attach cost documented below is real, but the fix is re-probing for the hosted connector, not standing up a second registration surface for it.

### Hosted connectors absent at session start, attach later (local launcher-worktree, LS-9370)

Distinct from both the LS-9576 "never registers at all" case and a mid-session 401: in local launcher-worktree sessions, the hosted connectors (`legacy-sports-jira`, `-github`, `-ci`, `-db`/`-db-admin`, `-rollbar`) routinely report unavailable in the deferred-tools roster **at session start** — either silently absent, or with an explicit `Incompatible auth server: does not support dynamic client registration` / `CONNECTION_CLOSED` reason — and then connect successfully **later in the same session**, sometimes 60–90 minutes in (observed recurring: LS-9366, LS-9371, LS-9839/PR #7536, LS-9859/PR #7584). Two consequences, both costly if unhandled:

1. **The whole ticket lifecycle falls back to REST/`acli`/`gh` unnecessarily.** An agent that checks tool availability once at Step 0b and treats that as final for the session keeps using CLI/REST fallbacks for claim, transition, comment, and PR creation even after the real tools would have worked — `gh pr create` in particular skips the jira-link marker `github_open_pr` auto-inserts, which is its own documented footgun (see [PR Creation Routing](#pr-creation-routing)).
2. **The late attach can use a different tool prefix than the configured server name.** Observed live (2026-09-03): the same tools attached under UUID-prefixed aliases (`mcp__<uuid>__jira_*`, `mcp__<uuid>__github_*`, …) rather than `mcp__legacy-sports-jira__*` / `mcp__legacy-sports-github__*`, while the configured names stayed in the failed-to-connect list for the rest of the session. Guidance like "use the `jira_*` tools from `legacy-sports-jira`" doesn't help locate these — they're only discoverable by the bare tool name.

**Sanctioned response — re-probe by bare tool name before each lifecycle step, not just once at Step 0b:**

- Do not treat the Step 0b (or any single) `ToolSearch`/connection-error result as final for the session's lifetime. Before each subsequent Jira- or GitHub-touching step (claim/transition, comment, PR create, PR ready, label management), re-run `ToolSearch` on the **bare** tool name you need (`select:jira_view`, `select:jira_transition`, `select:github_open_pr`, …) rather than a server-prefixed query — a UUID-aliased late attach matches the bare-name search but not a `legacy-sports-jira`-scoped one.
- If the re-probe finds the tool (under its configured name or a UUID alias), use it — switch off any REST/`acli`/`gh` fallback already in flight for the rest of the session.
- If the re-probe still finds nothing, proceed with the documented fallback for the failure shape you're seeing (`configured: false` → Step 0b's stop condition; `Incompatible auth server…` → [Auth per surface](#auth-per-surface) row below; entirely absent for the session → the [LS-9576 substitution table](#jira-github-hosted-servers-absent-in-ccr-ls-9576), which applies here too even though this failure mode isn't CCR-specific), and note in the MCP gap audit which lifecycle steps ran on the fallback so a late attach mid-lifecycle is visible in the record.
- This costs one extra `ToolSearch` call per lifecycle step against the alternative of running the entire claim → PR → merge path on REST/CLI fallbacks — cheap by comparison, and it's the only way to recover the real tools once they attach.

## Tool Routing Rules

### Tool-Use Rejections Are a Hard Stop (LS-8761)

A tool-use rejection — the harness/user declining a specific call ("The user doesn't want to proceed with this tool use... STOP what you are doing and wait for the user to [respond]") — is categorically different from a tool _returning_ an error or a `STOP`/`ALREADY_CLAIMED` result field (that's the tool running successfully and reporting a state). A rejection means the call never ran at all. Treat the **first** rejection as a hard stop: halt the current action, surface it to the user, and wait — never resubmit the identical call (same tool, same arguments) expecting a different outcome. Resubmitting an already-rejected call is not a retry, it's the same declined action asked again; nothing about the call's arguments changes between attempts, so nothing about the answer will either. If the call is part of a multi-step flow (e.g. a ticket claim), investigate why it might be wrong _before_ trying again with different arguments (or a different tool) — for a claim rejection, check `github_pr_dashboard` for an existing PR against the ticket key first, per [work-ticket leaf-mode Step 1](../work-ticket/references/leaf-mode.md).

Observed failure mode (LS-8761): ~48 near-identical rejected `jira_transition(action=claim)` calls against an already-in-review ticket in a single session, before the agent finally stopped and found the existing open PR — the investigation that happened after the 48th rejection should have happened after the 1st.

### PR Creation Routing

**The routing decision — which creation tool per environment, plus the mandatory label sequence — has one home: [pr-lifecycle → PR-creation tool routing](../pr-lifecycle/SKILL.md#pr-creation-tool-routing-one-home--link-here-do-not-restate).** This section holds only the tool-surface facts behind that table:

- `github_open_pr` — registered on the **hosted `legacy-sports-github` connector** only. Semantic one-shot: push branch → create draft → mark ready → apply `bot:ready-for-review`; `draft: true` stops after creation; in Lambda mode `head` is required and push is skipped. When `jiraKey` is passed, the tool auto-inserts the jira-link marker in the body **and** (LS-8679) prepends the key to the title if it isn't already present anywhere in it — so passing a pre-prefixed title is no longer required to pass Jira Link Check. For an evidence-heavy body already written to disk, pass `bodyFile` (a file path) instead of `body` — cheaper than re-emitting the whole document as a tool argument on create and every subsequent edit; `github_edit_pr` takes the same `bodyFile` parameter for exactly that re-edit case. Both fields are mutually exclusive, `bodyFile` must resolve inside the repo (its contents become the public PR body), and it isn't supported in Lambda mode (LS-9581).
- `github_open_pr` unavailable → the routing home's built-in and `gh` rows apply; before any `gh pr create` fallback, diagnose and report first (see [diagnostics Reporting Protocol](references/diagnostics.md#reporting-protocol)) — `gh pr create` silently targets the shell's working directory.

> **`github_create_pr` no longer exists.** It lived on the `local-git` stdio server, which was removed in LS-9294 — the server was registered but never enabled, so the tool never loaded in sessions anyway. `github_open_pr` (hosted `legacy-sports-github`) is the single custom create surface; it carries the jira-link-marker auto-insert itself (shared `jira-link.js` module: `primary: none` + `no-jira` label fallback per LS-8298, self-healing marker per LS-9043). `github_rebase_pr` went with the server too — use `github_bulk_rebase({ numbers: [N] })` for a single hosted rebase, or `worktree_rebase_onto_main` locally.

### Pre-flight Auth Check

<a id="auth_check_all"></a>

`auth_check_all` (read-only token-presence check for GitHub/Jira/AWS/CI) lives in the **`worktree` stdio server** (`tools/mcp/worktree-server/src/index.ts`). Availability follows Surface 1: present in local sessions and Copilot (`auth_check_all` is in the `worktree` server's `tools` allowlist in `.github/copilot/copilot-cloud-mcp-config.json`); **absent whenever stdio servers are absent** (degraded CC-web). When it is absent, AGENTS.md's pre-flight mandate is satisfied per-service instead: `github_auth_status`, `jira_auth_status`, `ci_auth_status`, `rollbar_auth_status` on the hosted connectors, `aws_sso_status` on the aws stdio server. If `allAuthenticated: false` (or any per-service check fails): surface the `hint` verbatim and **stop** — see [Auth Model](#auth-model).

> **`auth_check_all` and the per-service `*_auth_status` tools check credentials, not connector enablement (LS-8695)** — a connector with `enabledInChat: false` for the current chat is invisible to both: its tools never load, so there is no auth call to make in the first place, and none of these checks would catch the gap in advance. A ticket that names a specific hosted connector in its own instructions (e.g. a `labels: rollbar` ticket that expects to call `rollbar_get_item`) is worth a one-shot `ListConnectors({ keywords: ["<server>"] })` preflight before investigation starts — cheap, and it turns a mid-task "tool silently absent" surprise into an upfront "ask the user to enable it" ask. This is a recommendation, not a hard gate; it is not wired into `/work-ticket` or leaf-mode routing.

The Jira sub-check (`checkJiraAuth` in `tools/mcp/worktree-server/src/auth-checks.ts`) recognizes four credential shapes, not just direct basic/OAuth env vars: `JIRA_EMAIL`+`JIRA_API_TOKEN` (basic), `JIRA_CLIENT_ID`+`JIRA_CLIENT_SECRET`+`JIRA_CLOUD_ID` (a jira-server run as a direct stdio process), `~/.netrc`, and — the case that matters in practice, since `legacy-sports-jira` is hosted and its own credentials never reach this process — `MCP_JIRA_URL` paired with either `MCP_MACHINE_CLIENT_ID`+`MCP_MACHINE_CLIENT_SECRET` (local/worktree sessions, mirrored by `scripts/mcp-auth.mjs`) or `MCP_JIRA_BEARER` (Copilot cloud). Before LS-8714 this last path wasn't checked at all, so `auth_check_all` reported `jira: { ok: false }` in sessions where `jira_auth_status` confirmed OAuth was working.

### Validation Routing

Owner ruling (2026-07-02) — the validation execution path is availability-routed:

1. **`nx_run_pc_chunk` present** → it is **mandatory** for every chunk (cloud and timeout-prone sessions; AGENTS.md Tier-2). One call per chunk, canonical order. Calls are transport-safe: a chunk still running at the ~45s in-call budget returns `{ status: "running", jobId }` — follow with `nx_job_wait({ jobId })` (≤55s per call; re-invoke while `status: "running"`), `nx_job_status` for a snapshot, or `nx_job_list` to recover handles after a session resume. Never re-run a chunk that handed back a jobId — re-invoking joins the in-flight job. Sole exception: a terminal `"internal timeout"` error or `orphaned` status may be re-run once (completed tasks stay Nx-cached; LS-8353). Full contract: [repo-tooling](../repo-tooling/SKILL.md#running-validation-per-environment).
   - `runNx()` (backing every `legacy-sports-nx` tool call) self-heals a stale Nx project-graph cache: on `Failed to process project graph` it clears `.nx/cache`/`.nx/workspace-data` once and retries automatically — no manual cache-clearing needed on platforms where `nx_run_pc_chunk` exists (LS-8936). On CCR, where this tool is absent, see the [stale project-graph cache failure mode](../cloud-agent-mode/SKILL.md#known-failure-mode-stale-nx-project-graph-cache-blocks-every-nx-invocation-ls-8936) for the manual recovery.
   - The nx MCP server's own `--import tsx` launch env (`TSX_TSCONFIG_PATH`, set in `.mcp.json` for `legacy-sports-nx`) no longer leaks into `nx_run_pc_chunk`'s spawned children (`make -> nx -> jest`): `runCommand` (`tools/mcp/nx-server/src/run-command.ts`) always sanitizes the child env via `buildChildEnv()` (`tools/mcp/nx-server/src/child-env.ts`) before spawning, regardless of whether the caller passes its own `env` override. Previously a jest suite that itself shelled out to `tsx` (e.g. `lib/db-client/src/scripts/tsx-workspace-resolution.spec.ts`) could inherit the nx server's own relative `TSX_TSCONFIG_PATH` and resolve it against the wrong cwd, producing a false `pc-test` failure unrelated to the code under test (LS-9681). `make-server` had the same class of leak (it never set an explicit `env` on `execFile`, so it always inherited `process.env` verbatim into spawned `make` children); fixed in LS-9806 with the same `buildChildEnv()` pattern (`tools/mcp/make-server/src/child-env.ts`, wired into `tools/mcp/make-server/src/run-command.ts`).
2. **`nx_run_pc_chunk` absent** (degraded CC-web: no custom stdio servers) → the sanctioned path is Bash `make pc-<chunk>` with **`run_in_background: true`**, one chunk at a time in the canonical order. `.agents/hooks/enforce-background.mjs` permits background runs and exit-2-blocks the same command foreground — foreground remains banned.
3. **Local non-timeout-prone sessions** → `make_run({ target: "pc" })` is fine.

Chunk order and the full per-platform decision tree are owned by AGENTS.md and [cloud-agent-mode](../cloud-agent-mode/SKILL.md) — do not restate them here.

### Waiting on CI (no polling, no sleep)

- **PR-associated runs — arm the watch before idling (LS-8544)**: before ending any turn with the PR in a non-terminal state, arm the canonical watch monitor — `Monitor({ command: "bash <worktree-abs-path>/scripts/watch-pr.sh <PR#>", persistent: true, description: "PR #<N> watch" })` — then end the turn. The script path must be **absolute**: `Monitor` is not guaranteed to run with the worktree root as its cwd, and a bare relative `scripts/watch-pr.sh` exits 127 before the script runs a single line (LS-9045). The watch polls harness-side (zero tokens, ~90s cadence) and re-invokes the idle session only on actionable transitions: red required contexts, corroborated merge conflicts, new reviews, escalation labels, SKIPPED-pipeline stalls (`bot-review`/`CI Gate` are commit statuses that go _absent_, never red), and MERGED/CLOSED. It heartbeats `.claude/.pr-watch-armed-<PR#>` so the stop guard (`check-open-pr.sh`) permits idling. Push notifications remain an accelerant when they arrive but are **not load-bearing**: conflict transitions caused by main advancing are surfaced only as an API check run + label + comment and never wake an idle session (observed stuck PRs #6161/#6163). In-context polling remains banned — treat `ci_view_run`/`github_view_pr` as one-shot lookups; polling loops have burned 1–2M tokens per session. Arming precondition: the `Monitor` tool is available **and** `gh` is on PATH; otherwise fall back to the environment rules below. **Binding caveat**: a fix/chip session still on its auto-generated `claude/<name>` branch must never end its turn waiting on a PR event — re-arm `bot:ready-for-review`, report, stop (see [pr-lifecycle drive.md Step 4 + Gotchas](../pr-lifecycle/references/drive.md#step-4-enter-worktree-local-only)).
- **Non-PR `workflow_dispatch` runs** (integration suite on `main`, nightlies): no PR → no push notification. Use `ci_dispatch_workflow({ ..., waitForCompletion: true })` — each call waits at most ~20s (bounded by this Lambda-hosted server's own 30s execution timeout, not the ~60s MCP transport timeout — LS-8429). A fast run returns `{ status: "completed", conclusion, durationSeconds }` in one call; a longer run returns `{ status: "in_progress", runId, hint }` — continue with `ci_wait_run({ runId })`, which has the same bounded-wait contract: re-invoke it until `status: "completed"`. Never re-dispatch while a run is in progress.
- **Retriggering a GH-Actions-owned check with no `workflow_dispatch` trigger** (e.g. `jira-link-check.yml`, which only runs on `pull_request`) (LS-8366): `github_retrigger_check` refuses and points to `ci_dispatch_workflow` as a fallback, but that workflow will 422 ("Workflow does not have 'workflow_dispatch' trigger"). `ci_dispatch_workflow` now detects this and returns an error redirecting to the path that actually works: `ci_list_runs({ workflow, branch })` to find the failed run, then `ci_rerun({ runId })` (default `scope: "failed"`).
- **Environments without push notifications** (e.g. Copilot): prefer `waitForCompletion`. If you must wait on a condition in a Claude Code session, use the harness `Monitor` tool — for PR waiting always via `scripts/watch-pr.sh` invoked by **absolute** path as shown above (never a bare relative path — it exits 127, LS-9045 — and never an ad-hoc loop: the canonical script covers commit-status stalls, conflict corroboration, debounce, and loud death) — **`ScheduleWakeup` is not a CI-wait primitive** (it paces `/loop` only). Never `sleep N && gh run view` loops, and never `Bash(gh run watch ..., run_in_background: true)` — the watcher dies silently on session resume.
- **Session-resume caveat**: if a bounded wait was in-flight when the session was interrupted, only that one ≤20s call is lost — the run itself is unaffected. Re-find the run with `ci_list_runs({ workflow, branch, limit: 5 })`, then re-attach with `ci_wait_run({ runId })`. Do not re-dispatch.
- **Waiting on a remote ref change or deletion** (e.g. `main` advancing after a queue merge, a PR branch being deleted post-merge): never `git ls-remote origin <ref> | sleep 20` — use `github_await_ref({ ref, changedFrom?, deleted?, maxWaitSeconds? })` on `legacy-sports-github` instead. Same bounded-wait contract as `ci_wait_run`: each call polls for up to 55s and returns `{ status: "unchanged", hint }` (never an error) if the condition hasn't occurred yet — re-invoke per the hint. `{ status: "changed" | "deleted" }` on success.
- **`ci_rerun` "already running" 403 vs. trailing cleanup jobs** (LS-9647): GitHub's `rerun-failed-jobs`/`rerun` endpoints gate on the run's overall status, not any individual job's — they keep 403ing "This workflow is already running" while trailing jobs (`Summarize & Report`, `Remove Merge Label on Failure`, etc.) are still queued, even after every substantive build/test/E2E job has finished. `ci_rerun` retries this race internally for a few seconds, but a short in-Lambda retry can't wait out a slow-scheduling cleanup job. If `ci_rerun` returns `{ status: "not_yet_reschedulable", hint }` instead of a normal success/error, that is the signal: call `ci_wait_run({ runId })` (re-invoking per its own hint) until it returns `status: "completed"` — that field only flips once every job on the run, cleanup included, is done — then retry `ci_rerun`. Do not loop calling `ci_rerun` itself or blind-poll `ci_view_run`/`actions_list` job lists in the meantime.

<a id="installation-vs-user-rate-limit-ls-9570"></a>

### Installation rate limit vs. `gh api rate_limit` (LS-9570)

`gh api rate_limit` reports the **CLI's own user/PAT token** bucket. Workflow steps authenticate as the **GitHub App installation token** minted from `secrets.AGENT_AUTHOR_APP_PRIVATE_KEY` (`actions/create-github-app-token`, app id 3158619) — a **completely separate budget**. These two buckets can be in opposite states at the same time: a healthy `gh api rate_limit` result does **not** mean CI's own API calls aren't rate limited, and does not answer "is CI rate limited?" at all. Running `gh api rate_limit`, seeing a healthy number, and concluding a workflow's 403s were a transient blip is the exact wrong-decision failure mode this gap produces (observed on PR #7232 / LS-9528 — a ~90-minute stall on what was purely an installation-token rate limit).

Use `ci_installation_rate_limit` (`legacy-sports-ci`/`legacy-sports-ci-local`) instead — it always mints a fresh installation token via `AGENT_AUTHOR_APP_PRIVATE_KEY` and queries `GET /rate_limit` with it directly, bypassing `GH_TOKEN`/`GITHUB_TOKEN` env precedence, so the result is guaranteed to be the installation bucket regardless of what other credentials the session has. (`ci_auth_status`'s own `rateLimit` field is not a substitute for this — it reflects whichever token source `getToken()` actually resolved, which may not be the installation token.)

A CI step that computes a verdict but can't post it — GitHub App API calls failing with `API rate limit exceeded for installation`, or a gate/status step logging its computed result and then silently withholding the actual `POST`/status update — is a **rate-limit signature, not a real verdict**. See [pr-lifecycle troubleshooting](../pr-lifecycle/SKILL.md#withholding--could-not-post-status-is-a-rate-limit-signature-not-a-verdict-ls-9570) for the failure pattern and remedy.

## Auth Model

This section absorbed the former `credentials` skill (2026-07-02). One rule dominates everything below:

> **Tier-1 (AGENTS.md Safety): never run auth-generation commands.** `aws sso login`, `gh auth login`, `acli auth login`, OAuth device flows, and credential-provisioning scripts (`node scripts/mcp-auth.mjs`, `make e2e-auth`) are **user-only** actions. On any auth/expired-token error: stop, surface the `hint` verbatim, prompt the user. Falling back to `gh`/`acli`/raw `curl` does not work around a missing token — it masks the failure and pollutes the MCP gap audit.

<a id="legacy-sports-ci-local-write-path-auth-gap-ls-9234"></a>

### `legacy-sports-ci-local` write-path auth gap (LS-9234)

`legacy-sports-ci-local`'s token resolution (`tools/mcp/ci-server/src/github-api.ts`, shared with the hosted `legacy-sports-ci` connector) tries, in order: `GH_TOKEN`/`GITHUB_TOKEN` env → a GitHub App installation token minted from `AGENT_AUTHOR_APP_PRIVATE_KEY` → `gh auth token` CLI. Read-only tools (`ci_view_run`, `ci_get_logs`, `ci_list_runs`, …) and write tools (`ci_rerun`, `ci_cancel_run`, `ci_dispatch_workflow`) go through the **same** resolution — there is no read/write credential split by design. A CCR (Claude Code Remote) session that has none of those three sources set fails **every** `ci_*` tool call identically, not just write-path ones; if a session appeared to have only read tools working, that was other tools (e.g. `ci_audit_session_bash`) not needing a GitHub token at all, not a deliberate split.

If a `ci_*` call on this server fails with `No GitHub token available for the legacy-sports-ci-local server`, do **not** attempt to provision a token yourself (Tier-1 rule above) — use the built-in `mcp__github__*` tools instead, which authenticate independently via the platform's own token:

| Failed `legacy-sports-ci-local` tool          | Built-in substitute                                                                                                                                                                                                                                                   |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci_rerun` (failed jobs)                      | `mcp__github__actions_run_trigger({ method: "rerun_failed_jobs", owner, repo, run_id })`                                                                                                                                                                              |
| `ci_rerun` (full run)                         | `mcp__github__actions_run_trigger({ method: "rerun_workflow_run", owner, repo, run_id })`                                                                                                                                                                             |
| `ci_cancel_run`                               | `mcp__github__actions_run_trigger({ method: "cancel_workflow_run", owner, repo, run_id })`                                                                                                                                                                            |
| `ci_dispatch_workflow`                        | `mcp__github__actions_run_trigger({ method: "run_workflow", owner, repo, workflow_id, ref })`                                                                                                                                                                         |
| `ci_view_run` / `ci_list_runs` (read-only)    | `mcp__github__actions_list` / `mcp__github__actions_get` — save output to a temp file and extract fields with `jq`/`python3` rather than reading the full JSON inline; payloads run large (~400 KB at `per_page=15`)                                                  |
| `ci_get_playwright_test_result(source: "s3")` | No direct substitute for the structured pass/fail/flaky report (it needs the same run-id→commit-SHA GitHub API lookup as `ci_view_run`, so it fails identically) — use `mcp__legacy-sports-github__get_job_logs` to pull the failing job's raw logs instead (LS-8887) |

The error message thrown by `resolveToken()` names these substitutes directly (LS-9234, LS-8887) so an agent doesn't have to rediscover them. This does not fix the underlying credential gap — it is a documented fallback. Fixing the gap itself means getting `AGENT_AUTHOR_APP_PRIVATE_KEY` or `GH_TOKEN` set in the CCR environment's settings, which is a user action (Settings → Environment), not something an agent session can do for itself.

### Retired model — do not resurrect

Older docs (the pre-2026-07 `credentials` skill, anything mentioning `MCP_AUTH_TOKEN`) described per-session ~8 h Cognito ID tokens baked into `.mcp.json` URL-server headers, with 401 recovery = "run `node scripts/mcp-auth.mjs`, restart". That flow was **removed** (LS-5094; `scripts/mcp-auth.mjs` now purges the stale `MCP_AUTH_TOKEN*` keys on every run — LS-5219). The script itself still exists but is now the **user-run Track A provisioner** (machine credential + API URLs, needs AWS access) — an agent must never run it, and it is never the answer to a mid-session 401 in a connector session.

> **Multi-pattern alternation in Grep**: Use bare `|` (not POSIX `\|`) for alternation in Grep patterns — ripgrep syntax, not grep syntax. Example: `grep -n "ERROR\|WARN" file` becomes `Grep(pattern: "ERROR|WARN", path: "file", output_mode: "content")`. Drop the backslash from each `\|` when converting from a Bash grep command.

**`worktree_show_file` vs `worktree_show_remote`**: use `worktree_show_file` for local refs (HEAD, commit SHAs, local branch names, tags) and `worktree_show_remote` for remote branch refs (`origin/main:path`, `origin/<branch>:path`). They are different tools for different ref namespaces — `worktree_show_remote` is the MCP-first replacement for `git show origin/main:<path>` (which was previously unaddressed and caused agents to fall back to raw Bash). Note LS-2997 tracks `worktree_show_file` for local SHA reads; this distinction (LS-3024) specifically covers the remote-ref pattern.

**Glob limitation on Windows worktrees**: `Glob` with `path=` set to an absolute Windows worktree path may silently return empty results due to symlink traversal issues. Fall back to `worktree_ls_tree({ ref: "HEAD", path: "<dir>" })` (Git-tracked files only) or `worktree_run(command: "dir <dir>")`.

**Glob/ripgrep timeout on cloud/Linux sessions (LS-8420)**: the same symlink-traversal quirk shows up as a different symptom off Windows — `Glob` on a **single, exact, already-known file path** (e.g. `Glob(pattern: ".agents/skills/work-ticket/SKILL.md")`) can fail with `Ripgrep search timed out after 20 seconds`, even though the pattern is not a broad `**/*.ext` search. This repo's `node_modules/` (pool-linked, worktree `node_modules` is a directory symlink into `.modules-pool/<hash>/`) accounts for the vast majority of files on disk, and `.gitignore`/`.claudeignore`/`.rgignore` all exclude it — but that exclusion is not a substitute for avoiding the tree walk in the first place. **When the exact path is already known (not a pattern to discover), use `Read(file_path: "<path>")` directly instead of `Glob`** — `Read` opens the path without walking the tree, so it can't hit this budget. Reserve `Glob` for genuine pattern discovery (`**/*.ext`, `**/*name*`).

## Nx Targets

Prefer the `nx_run` MCP tool over `pnpm exec nx run <project>:<target>`. For affected targets, prefer `nx_run_affected` over `pnpm exec nx affected -t <target>`. Fall back to shell commands only when the MCP server is unavailable.

> **`passed: true` does not always mean tasks ran.** If the Nx Daemon fails to compute the project graph, the underlying process can still exit 0 with zero tasks executed. `nx_run`, `nx_run_affected`, and `nx_job_wait`/`nx_job_status` detect this and report `passed: false`, `isError: true`, `daemonError: true`, plus a `hint`. On `daemonError: true`, run `make clean-cache` (never `nx reset` — blocked repo-wide by `.claude/hooks/guard-risky-tools.mjs`, it corrupts the shared cache for other worktrees) and retry. (LS-8819)

> **Never invoke `node_modules/.bin/nx run …` or `jest` directly via Bash for test runs — including the `pnpm exec` prefixed forms (`pnpm exec jest …`, `pnpm exec prettier …`).** These bypass the MCP layer and fail when `node_modules/.bin/tsx` is missing (MCP server health-check warning at session start). Always use `nx_run` / `nx_run_affected` instead. Use `nx_show_projects` instead of `node_modules/.bin/nx show projects`. (LS-8078)

**Scoped feedback loops — what can and cannot be narrowed to a file list (LS-8735)**: reach for these instead of shelling out to `jest` / `eslint` / `tsc` while iterating on a couple of files.

- **jest → already scoped, via `args`, or via `nx_run_test` for config variants.** `nx_run({ project, target: "test", args: ["--testPathPatterns", "<pattern>"] })` — there is no `testPathPattern` parameter; pass the flag through `args`. The tool translates the deprecated `--testPathPattern` spelling, coalesces multiple values into one pipe-joined token on Windows, and auto-injects `--all` so a `--onlyChanged` baked into a package.json test script cannot silently swallow the pattern. For a project with config-scoped jest targets (e.g. `shared-components`'s `test:mobile` / `test:web`), prefer `nx_run_test({ project, config: "mobile"|"web", testPathPatterns: "<pattern>" })` (LS-8917) — a thin wrapper over `nx_run` that maps `config` to the `test:<config>` target so you don't need to know the colon-suffixed target naming convention.
- **eslint → `nx_run_eslint({ files, mode })`, but it is _not_ a speed win.** It narrows the _report_ to an explicit file list, not the _runtime_: every TS config in this repo enables type-aware rules via `parserOptions.project`, so ESLint builds a full TypeScript program before linting even one file. Measured in `lambdas/db`: **one file 4m40s vs the whole project 4m42s** — scoping saves ~2s of ~280s. That cost is per-run, so scoping does not shrink it. For a whole project prefer `nx_run({ project, target: "lint" })` — it is Nx-cached and returns instantly on a repeat run with unchanged inputs. The tool still runs from the nearest directory owning an `eslint.config.*` so the project's flat config actually applies (ESLint 9 resolves flat config from its cwd, not per file — from the repo root, `lambdas/db`'s `@nx/enforce-module-boundaries` allow-list is dropped and legitimate imports are reported as violations). A file list spanning two config roots is rejected; split it into one call per root. Since that ~280s floor routinely exceeds the ~60s MCP transport timeout, the tool now has the same job/jobId semantics as `nx_run`/`nx_run_test`/`nx_run_pc_chunk` (LS-9594): a run still going after ~45s returns `{ status: "running", jobId }` — poll with `nx_job_wait`/`nx_job_status` instead of falling back to raw Bash + `run_in_background`.
- **tsc → cannot be file-scoped; use project granularity.** `nx_run({ project, target: "typecheck" })` is the intended path. `tsc` refuses to combine `-p/--project` with explicit source files, and dropping `-p` discards the project's `compilerOptions`, path mappings, and include/exclude — so a "file-scoped typecheck" would emit errors that aren't real. This is a deliberate decision, not a missing tool; please don't re-file it as an MCP gap.

**`nx_run_e2e_specs` — targeted Playwright runs (LS-5988, LS-8252)**: use this instead of raw `npx playwright test …` for both hermetic and live-backend integration specs.

- **Hermetic mode** (default): forces `E2E_AUTH_MODE=ci`, auto-selects a free `E2E_PORT`, requires `dist/apps/web` first (`nx_run({ project: "web", target: "build" })`). Spec paths relative to `apps/web-e2e/src/tests/`.
- **Integration mode** (`integration: true`): runs `src/integration/tests/` specs against the live backend (`api.legacy-fantasy.com`) via `playwright.integration.config.ts`. Enforces `--workers=1`. Checks e2e JWT freshness (`~/.legacy-sports/e2e-token.json` — ask the user to run `make e2e-auth` if stale) and warns when `E2EPOOLPASSWORD` is missing (needed for premium-seat personas 3+). No `dist/apps/web` required.
- **Tracing** (`withTracing: true`, either mode — LS-9332): adds `--trace=on`; trace zip paths returned in `traceArtifacts`.
- Returns `{ success, mode, stats, failingTests[], output, traceArtifacts?, graphqlErrors?, preconditionWarnings? }` — `output` is the combined raw Playwright stdout/stderr (truncated to `MAX_OUTPUT_CHARS`), so `console.log`/debug output printed by a spec is already surfaced without a shell fallback.
- **Browser build drift (LS-8319)**: `apps/web-e2e`'s Playwright configs auto-resolve the pre-installed `/opt/pw-browsers` build regardless of version (see `apps/web-e2e/src/resolve-pw-browser.ts`), so a cloud image shipping an older Chromium build than the repo's pinned `@playwright/test` no longer fails at launch. If no usable build exists at all, the error result includes an actionable `hint` pointing at this remediation instead of a bare Playwright stack trace.
- **Zero-tests-matched is an error, not a silent pass (LS-9330)**: Playwright turns each spec arg into a regex with no escaping, and a raw Windows backslash path corrupts that regex into matching nothing — the tool used to report `success: true` / `stats.total: 0` for a run that never actually happened. Spec paths are now normalized to forward slashes before being forwarded to Playwright, and a run that still matches 0 tests for the requested specs/project/grep is now `isError: true` with an explanatory `error` — treat that result as "the request didn't match anything," not "nothing to test."

> **If you find yourself writing `pnpm exec nx` in a Bash tool call during a local session, treat this as a signal that the `legacy-sports-nx` MCP server is not connected.** Check server connectivity rather than falling back silently — `nx` lives in `node_modules/.bin` and will fail with a PATH error if the symlink is missing or broken. Verify the `node_modules` symlink exists (see [Tool Surfaces](#tool-surfaces)), then restart the session.

**Heavy targets are transport-safe by default (LS-8558, LS-8559).** Cloud Claude Code sessions enforce a ~60s MCP transport timeout on every tool call. `make_run` (and the job-backed nx tools `nx_run`, `nx_run_affected`, `nx_run_e2e_specs`, `nx_install_package`), plus `worktree_run` / `worktree_run_all` on the worktree server, now always run the underlying process as a background job with a ~45s bounded wait: fast targets return their result in one call, and anything slower returns `{ status: "running", jobId }` instead of blocking into the transport timeout. Never re-invoke the tool while its job runs — poll instead:

```
make_run({ target: "build-all" })   // fast → full result; slow → { jobId, status: "running" }
make_run_wait({ jobId })            // blocks ≤55s; re-call if it returns status: "running"
make_run_status({ jobId })          // non-blocking snapshot (status + log tail)
// nx tools poll with nx_job_wait({ jobId }) / nx_job_status({ jobId }) instead
// git-heavy github tools poll with github_job_wait({ jobId }) / github_job_status({ jobId }) instead
// worktree tools poll with worktree_job_wait({ jobId }) / worktree_job_status({ jobId });
// worktree_job_list recovers job handles after a server restart. worktree_run keeps its
// 120s process cap — long-running work still belongs in nx_run_pc_chunk / make_run / nx_run.
```

`make_run_wait` returns the full structured result (with `steps[]` for multi-step targets like `pre-commit`/`full-check`) once the job reaches `done`/`failed`; `nx_job_wait` likewise returns the originating tool's structured result (e.g. the playwright report for `nx_run_e2e_specs`). `runInBackground: true` still exists to skip the initial bounded wait and return the jobId immediately. (Validation routing is unchanged — see [Validation Routing](#validation-routing).)

The same contract covers the git-heavy github tools (LS-8562): `github_bulk_rebase` and `github_open_pr`'s push phase each run under a ~45s sync budget and may return `{ jobId, status: "running" }` — poll with `github_job_wait` / `github_job_status` **on the same server that returned the jobId** (job registries are per-process). `github_bulk_rebase` reports per-PR progress in `logTail`. These jobs are in-process and do not survive an MCP server restart — if a jobId is lost, verify the outcome (`github_view_pr`, `worktree_status`) instead of re-running. Only the stdio deployments are affected — the Lambda deployment has no `git` binary on its PATH, so `rebasePR`/`bulkRebase` route to a git-free GitHub API merge-style update there instead (`PUT /pulls/{number}/update-branch`) rather than the sync-budget/job path; this produces a merge commit, not a linear rebase (LS-7753).

The aws-server long-runners follow the same contract (LS-8560): `packer_build` always runs the build (including `packer init`) in the background with a 45s initial wait, returning either the finished result or `{ status: "running", buildId }`; `packer_build_wait` is capped at 55s per call and returns a non-error running snapshot with a re-arm hint; `aws_ssm_run_command` polls ≤55s per call and re-arms via `aws_ssm_run_command({ instanceId, commandId })` — never re-send the command while it is in progress.

The nx, make, and packer job runners share one engine — `@legacy-sports/mcp-jobs` in `lib/mcp-jobs` (LS-8564) — so make/packer jobs now also survive an MCP server restart (metadata persists on disk; a restarted server can still answer `make_run_status` / `packer_build_status` for jobs it did not spawn, reporting `orphaned` when the result was never recorded), and internal timeouts kill the whole process tree, not just the direct child. Internal timeouts are also success-aware for opted-in jobs (LS-8320): `nx_run_pc_chunk` gives the heavy full-monorepo chunks (`pc-lint`, `pc-test`) a longer process timeout than the other five, and if the timeout still fires after the chunk's nx success line is already in the log, the job is finalized as **passed** with `recoveredFromTimeout: true` (surfaced by `nx_run_pc_chunk` / `nx_job_wait` / `nx_job_status`) instead of the false `Process killed after Nms (internal timeout)` failure.

**`make_run` and `nx_run_pc_chunk` output are compact by default** (LS-7944, ported to `nx_run_pc_chunk` in LS-8423). The `output` field omits prettier per-file listings (collapsed to `[Formatting: N files checked, M changed]`) and truncates each step body to 20 lines with a `[N more lines — run step directly for full output]` note — the same truncation also caps non-prettier step bodies like `pc-lint`'s eslint output, since it works on line count, not content shape. Pass `verbose: true` only when you genuinely need the full raw output for debugging.

> **If you find yourself writing `make <target>` in a Bash tool call during a local session, treat this as a signal that the `legacy-sports-make` MCP server is not connected.** Check server connectivity rather than falling back silently — raw `make pc` will fail with `nx: not found` or similar PATH errors when `node_modules/.bin` is not in `$PATH`. Using `make_run` via MCP avoids this PATH resolution problem entirely. If `make pc` fails with `ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL Command "nx" not found`, the `node_modules` symlink is broken or missing — repair it with `worktree_install_recover()` (MCP-first), **not** `node scripts/modules-pool/link.mjs` via Bash. After recovery, restart the session so the MCP servers reconnect.

## Git Operations in Worktrees

Use `worktree_rebase_onto_main` instead of the fetch → rebase → push chain when syncing a branch with `main` (handles merge conflicts gracefully and pushes with `--force-with-lease`); pass `upstream` (the old base head) for the three-arg `git rebase --onto` form after a stacked PR's base squash-merges — see [worktree-workflow → rebase.md](../worktree-workflow/references/rebase.md#squash-merged-stacked-base-ls-8779) for the squash-detection recipe. Use `worktree_merge_main` instead of `git fetch origin main && git merge origin/main` when merge (not rebase) is the chosen conflict-resolution path — e.g. for the [PR state notices](../../../AGENTS.md#pr-state-notices) merge-conflict guidance that allows either merge or rebase. On conflict it leaves the merge in progress and returns the same structured conflict info as `worktree_conflict_info` (conflicted file list + marker locations); resolve, then `worktree_commit` + `worktree_push`, or `worktree_run(command: "git merge --abort")` to back out. On success it pushes with a plain `git push` (a merge commit doesn't rewrite history, so no `--force-with-lease` is needed). Use `worktree_commit` instead of `git add`/`git commit` via Bash — it handles staging and committing in one operation, refuses to stage likely credential/secret files (e.g., `.env`, `credentials.*`, `*.pem`, `*.key`), and supports `amend: true` to fix commit messages before push (pass `message` to replace, omit it to keep the existing message with `--no-edit`); add `resetAuthor: true` to also reset the commit author (e.g. after setting `git config user.email` in a cloud session). Use `worktree_checkout_file` instead of `git checkout [HEAD] -- <file>` to restore files to HEAD (discarding both staged and unstaged changes). Use `worktree_push` (supports `setUpstream`; auto-refreshes the remote-tracking ref before `--force-with-lease` via `fetchFirst`, default `true`, so a stale ref from a prior push no longer causes a spurious rejection — pass `fetchFirst: false` to skip) instead of `git push`, `worktree_rebase` (pass `disableRerere: true` if a stale rr-cache entry is causing conflict markers to be silently committed) instead of `git fetch origin && git rebase origin/main` (or `git fetch && twig rebase`), `worktree_rebase_continue` instead of `GIT_EDITOR=true git -C ... rebase --continue` (the tool suppresses the editor prompt internally — `GIT_EDITOR=true` is unnecessary), `worktree_fetch` instead of `git fetch origin`, `worktree_stash`/`worktree_stash_pop` instead of `git stash`/`git stash pop`, `worktree_unstage` instead of `git reset HEAD -- <files>`, `worktree_rm` instead of `git rm` or deleting files, `worktree_is_tracked` instead of `git ls-files`, and `worktree_check_ignore` instead of `git check-ignore`. Use `worktree_run` only as the **catch-all for git commands that have no dedicated tool** (e.g., `git merge-base`, `git cherry-pick`, `git tag`, `git add <file>` after manually resolving a merge conflict). These tools auto-resolve the worktree directory, refuse dangerous operations (pushing `main`, pushing during rebase), and require no manual `cd` or `-C` flags. Never use `git -C $wt <command>` via Bash when `worktree_run` can handle it.

**`worktree_run` shell on Windows**: uses Git Bash (`bash.exe` from Git for Windows) when available, falling back to `cmd.exe`. When Git Bash is used, common Unix shell idioms and utilities such as `&&`, `|`, `head`, and `grep` are available. When it falls back to `cmd.exe`, only cmd built-ins and operators like `&&` and `|` are supported — do not rely on Unix utilities (`head`, `grep`, etc.). Avoid PowerShell-specific syntax in `worktree_run` commands.

## File Size & Line Count

Use `worktree_file_info({ paths: [...] })` instead of `wc -l file1 file2 ...` via Bash to get byte sizes and, when available, line counts and approximate token counts for one or more files in a single round-trip. For files larger than 10MB, the tool returns only `bytes` (no `lines` or `approxTokens`); if `approxTokens` is omitted, fall back to `bytes` (dividing by 4 gives a rough token estimate) to decide whether `Read` will fit within its 10k-token limit or whether `offset`/`limit` chunking is needed. Accepts both relative paths (resolved against the worktree root) and absolute paths within the worktree root.

The label/check come from a deterministic `git merge` test and stay reliable while `mergeable` is `UNKNOWN`/stale after a base push — so a `MERGE_CONFLICT` verdict means rebase even if `mergeable` reads `MERGEABLE`. The dashboard's JSON rows expose this as `hasConflictSignal`; `CI_FAILING` verdicts carry a "conflicts cannot be ruled out yet" note while `mergeable` is `UNKNOWN`.

**Code-owner review is detected from outstanding review requests, not `reviewDecision`**: GraphQL's `reviewDecision` flips to `APPROVED` as soon as ANY required reviewer approves, so a CODEOWNERS catch-all (`*` → `@legacy-sports-review-bot`) satisfies it while a path-specific owner (e.g. `.github/workflows/**` → `@bkrupa`) has not approved — GitHub then keeps rejecting the merge with `405 … Waiting on code owner review from <owner>`. `github_pr_why_blocked` therefore returns `BLOCKED`/`AWAITING_CODE_OWNER_REVIEW` whenever a review request is still outstanding under a code-owner-required ruleset, whatever `reviewDecision` says, with the outstanding owner(s) in `details.pendingReviewers` (and `details.approvedByOtherReviewers: true` for the catch-all-approved case). Before LS-9379 this reported a false `READY`, which told driving agents the merge bot would finish the job and left PRs sitting indefinitely. `github_get_branch_protection` surfaces the same rule as `requireCodeOwnerReview` — note it can be `true` while `requiredReviewCount` is `0`, so the review count alone never proves a PR is unblocked.

**PR number parameter names**: as of LS-8678, every `legacy-sports-github` PR-number tool accepts both `number` and `prNumber` as interchangeable aliases (`prNumberField()` + `number ?? prNumber`, or the reverse where `prNumber` was the original primary — e.g. `github_pr_diff`, `github_finish_fix_round`), so passing either name works for single-PR tools: `github_view_pr`, `github_merge_pr`, `github_get_review_threads`, `github_get_check_runs`, `github_mark_pr_ready`, `github_pr_why_blocked`, `github_pr_diagnose`, `github_close_pr`, `github_list_reviews` (single-PR mode), `github_comment_pr`, `github_edit_pr`, `github_pr_commits`, `github_pr_timeline`, `github_set_commit_status`, `github_finish_fix_round`, `github_resolve_threads`, `github_pr_diff`. Two documented exceptions remain single-name by design: `github_manage_labels` and `github_request_review` take `prNumber` as an alias for their primary `prs` array — a third `number` name would add ambiguity, not remove it. Batch tools (`numbers`/`prs`/`items[].number`) are out of scope for this alias.

**GitHub auth-aware routing**: call `github_auth_status` at the start of any GitHub workflow. If `configured: true`, use our custom GitHub MCP tools. If `configured: false`, **stop and prompt the user** — do not silently fall back. Tell them their GitHub credentials are missing or expired, and direct them to set `GH_TOKEN`/`GITHUB_TOKEN`, run `gh auth login`, or configure `AGENT_AUTHOR_APP_PRIVATE_KEY` (see [cloud-agent-mode](../cloud-agent-mode/SKILL.md)). Only fall back to `gh` CLI after the user confirms their `gh` auth is working or explicitly asks you to try the CLI fallback. **In Lambda**: the `fallback` field in the `configured: false` response contains a Lambda-specific diagnosis (key missing vs. exchange failed); for operator remediation steps see `docs/dev-process/mcp-github-lambda-ops.md`.

> **`mcp__github__*` strips HTML comments out of every PR body it returns (LS-9463, LS-9279)**: `mcp__github__pull_request_read` **and** `mcp__github__list_pull_requests({ fields: ["body"] })` both remove `<!-- ... -->` content — including the `<!-- jira-link -->` marker — from the body. Verified on PR #7128 (LS-9453): the marker went in via `mcp__github__create_pull_request`, was missing from two `pull_request_read` calls, and was present in the stored body throughout — the Jira Link Check run echoed `PR_BODY` starting with the marker block and passed. To read linkage, use a channel the sanitizer does not touch: the PR title, the visible `**Jira:**` line, the `Jira Link Check` check-run conclusion, or its job log (`mcp__github__get_job_logs`, which prints `✅ Jira Link Check passed (primary: LS-####)`). Since LS-9279 that check also **repairs** a missing or malformed marker from the title key, so a marker you could not write is no longer a blocker — the title key is.
>
> The asymmetry that makes this look like a write-path bug: `mcp__github__add_issue_comment` round-trips the same literal `<!-- ... -->` text intact (observed on PR #6803, LS-9138), so probing the behaviour through comments points at the wrong layer.
>
> **Historical note — the earlier tickets read this the other way.** LS-9202 concluded the _write_ path sanitizes and that a marker therefore could not be written via the built-in tools at all; LS-8934 attributed the same observations to intermittency and prescribed a read-back-and-retry loop. LS-9227 and LS-9228 were both closed **Won't Do** on that basis, and LS-9279 repro'd it with steps that cannot distinguish the two cases — it was closed instead by making CI self-heal the marker rather than by settling which path strips. Whether the write path ever stripped is unresolved: those reports may have been accurate at the time, may have been this same misdiagnosis, or the platform may have changed since. Treat the paragraph above as current behaviour and PR #7128 as the checkable evidence. Prefer `github_open_pr`/`github_edit_pr` when the `legacy-sports-github` connector is present regardless — its create path injects a well-formed marker for you (LS-9043). See [pr-lifecycle create-pr.md § Seeing and fixing linkage on an open PR](../pr-lifecycle/references/create-pr.md#seeing-and-fixing-linkage-on-an-open-pr).

> **`mcp__github__subscribe_pr_activity` is a Claude Code built-in tool only** — it is NOT part of the custom `legacy-sports-github` MCP server and will not be available in cloud/headless environments (Copilot Coding Agent, CI). It is also absent from most current Claude Code sessions — PR events arrive automatically without it, so its absence is not a monitoring failure and never justifies polling. In those environments follow [Waiting on CI](#waiting-on-ci-no-polling-no-sleep) — `ci_dispatch_workflow({ waitForCompletion: true })` for dispatched runs, one-shot `github_view_pr`/`ci_view_run` lookups otherwise.

> **`mcp__github__search_pull_requests` / `mcp__github__search_commits` have no output-size limiting (LS-8410)**: unlike this server's own tools, neither exposes a `minimal_output`/compact param — every matched PR or commit is returned with its **full** body text (often multi-KB of markdown, including PR templates), so even a small result count can overflow the tool-result token limit on a broad query (a single `is:merged` keyword search or a wide commit-message `OR` chain has each overflowed past 100K chars). These tools belong to the officially-hosted GitHub MCP server (no `github` entry in this repo's `.mcp.json`; not vendored under `tools/mcp/`), so the overflow cannot be fixed at the tool level from this repo — mitigate at the call site instead:
>
> - **Searching this repo's PRs**: prefer `github_list_prs({ search: "...", state: "all" })` or `github_pr_scan` (hosted `legacy-sports-github` connector) — both are paginated and return compact summaries, not full bodies.
> - **Searching this repo's commit history**: prefer `git log --all --grep "LS-####"` / `worktree_log({ grep: "LS-####" })` for a ticket key (mind the shallow-clone graft window — see [failure-archaeology](../failure-archaeology/SKILL.md)) before reaching for `search_commits`.
> - **When `search_pull_requests`/`search_commits` are genuinely the only path** (cross-repo search, or history outside the graft): narrow the query as much as possible first — scope with `repo:owner/name`, drop wide keyword `OR` chains, add date/author filters — and pass a small `perPage` (5-10). A narrow query with few matches is not guaranteed to avoid overflow if any matched body is large, so treat this as risk-reduction, not a hard guarantee.

> **`mcp__github__actions_list({ method: "list_workflow_runs" })` has no `head_sha`/field filter (LS-8952)**: unlike this server's own tools, it returns every matched run with its full nested `repository`/`head_commit`/`pull_requests` payload and offers no way to restrict fields or filter server-side by commit — a branch with 20+ associated check-suite runs (bot reviewers, security scanning, Jira sync, CI orchestrator, etc.) can overflow 300-400KB per call. This tool belongs to the officially-hosted GitHub MCP server (no `github` entry in this repo's `.mcp.json`; not vendored under `tools/mcp/`), so the overflow cannot be fixed at the tool level from this repo — use the specialized tools instead:
>
> - **"Did CI finish for commit/PR X?"** — prefer `github_get_check_runs({ sha })` or `github_get_check_runs({ prNumber })` (`legacy-sports-github`, see [GitHub PR Operations](#github-pr-operations) below): scoped to one commit, deduped to the latest run per check name, and returned as a compact Markdown table (`name`, `status`, `conclusion`, `completedAt`, truncated `summary`) instead of raw nested JSON.
> - **"List recent runs on branch X"** — prefer `ci_list_runs({ branch: "X", commit?, limit? })` (`legacy-sports-ci`, see [CI Operations](#ci-operations) below): the `commit` param resolves an abbreviated SHA to its full SHA before mapping to `head_sha` server-side (LS-9589 — GitHub's own `head_sha` filter only matches an exact full SHA), `limit` bounds the result count (default 10), and each run is mapped to a small flat object (`id`, `conclusion`, `status`, `headSha`, `name`, `url`, …), not the full GitHub API run object.
> - **When `mcp__github__actions_list` is genuinely the only path** (neither hosted connector available): pass the narrowest `branch`/`event`/`status` filters it does support and keep `per_page` small — it still can't filter by commit, so treat this as risk-reduction, not a fix.
>
> **`mcp__github__actions_list({ method: "list_workflow_runs" })` can silently ignore `branch`/`workflow_id` entirely and return repo-wide noise (LS-9632)**: this is a stronger failure than the missing `head_sha` filter above — multiple sessions observed `branch` and/or `workflow_id` set (including the schema's own `workflow_id` param, not a made-up name) come back with `total_count` in the tens of thousands and a `workflow_runs` array spanning unrelated PRs, `main`, and dependabot branches, at 50-135K+ chars per call (routinely overflowing the tool-result token cap and forcing a save-to-file-and-slice workaround). Known triggers, none of which raise an error — the call always "succeeds" with the wrong scope:
>
> - Passing a workflow **display name** or a bare **numeric workflow ID** as `workflow_id` when the value doesn't resolve to a real workflow on the underlying REST route the tool builds (e.g. `ci.yml` typo'd against the actual filename) — GitHub's API itself 404s on an unknown `workflow_id` in the path, so a silent unfiltered fallback here means the tool is swallowing that error and re-issuing the unscoped `/actions/runs` list instead of surfacing it.
> - Combining `branch` with a second filter such as `event` — `branch` alone has been seen to filter correctly, but adding `event` alongside it has reproduced the repo-wide result on the same branch.
> - Passing an unrecognized top-level param (e.g. `workflow_ref` instead of the documented `workflow_id`, or `resource_id`) — the tool accepts it without a schema-validation error and silently drops back to the unfiltered list rather than failing fast.
>
> Same as LS-8952, this tool belongs to the officially-hosted GitHub MCP server (not vendored under `tools/mcp/`), so the silent-fallback behavior cannot be patched from this repo. Do not treat "I set `branch`/`workflow_id`" as proof the result is scoped — **always prefer `ci_list_runs({ branch, workflow, limit })` for a branch/workflow lookup** (`legacy-sports-ci`, see [CI Operations](#ci-operations) below): it builds the scoped `/actions/workflows/{workflow_id}/runs` REST path itself (resolving a display name/filename/numeric ID up front via `resolveWorkflowId`, throwing on an unresolvable one rather than silently falling back) and never issues the unscoped `/actions/runs` list unless no `workflow` filter was given. If `mcp__github__actions_list` is genuinely the only path available, treat any result back as unverified scope: check `total_count`/the number of distinct branches in `workflow_runs` before trusting it, and re-issue with `ci_list_runs` (or `github_get_check_runs` for a specific commit/PR) the moment either hosted connector becomes available instead of paging through the noise.

> **`mcp__github__get_job_logs` overflows even with `tail_lines` set (LS-9201)**: unlike this server's own `get_job_logs` (below), the built-in has no character-count cap — `tail_lines` bounds the number of _log lines_ returned, but GitHub Actions log lines from `pnpm`/`nx`/Playwright output are frequently multi-KB (embedded ANSI escape codes, JSON blobs, full stack traces), so even a modest `tail_lines` value (150-1500 all observed failing) can still return 200K+ characters and overflow the tool-result token limit. There is no `max_chars`/`strip_ansi` param to bound it independently of line count. This tool belongs to the officially-hosted GitHub MCP server (no `github` entry in this repo's `.mcp.json`; not vendored under `tools/mcp/`), so the overflow cannot be fixed at the tool level from this repo — prefer these instead:
>
> - **First choice**: `ci_get_logs({ runId or jobId, ... })` (`legacy-sports-ci`, see [CI Operations](#ci-operations) below) — enforces `maxChars`/`truncateLineLength` as hard caps.
> - **When only the `legacy-sports-github` hosted connector is available**: `get_job_logs({ job_id, max_chars, tail_lines, truncate_line_length, error_summary, grep_pattern })` — supports the same character-cap controls this ticket asked for (see the `gh run view JOB_ID --log` row below). `grep_pattern` (LS-9633) returns only lines containing a literal substring (e.g. a test name, `"1 failed"`) plus 2 lines of context instead of tailing — use it when the useful content isn't reliably within the last N lines (e.g. a live reporter that overwrites its own line with ANSI codes per test).
> - **When neither hosted connector is available** (only the built-in `mcp__github__get_job_logs`): pass the smallest `tail_lines` that could plausibly contain the failure (e.g. 50-100, not the default 500) and expect to still need the temp-file/slice workaround on verbose jobs — this is a genuine tool gap in the platform server, not something a smaller `tail_lines` reliably avoids.

> **`legacy-sports-github`'s own `get_job_logs` scopes to the failing step and flags truncation explicitly (LS-9644)**: when GitHub marks a step's `conclusion` as `"failure"`, the response is scoped to just that step's own output (`scopedToFailingStep: true` + `failingSteps: [...]`) before `tail_lines`/`max_chars` are applied — this avoids the historical failure mode where a plain tail landed inside an unrelated later step and looked like infra flake (e.g. the LS-8219 SIGINT-collision signature) while the real failure (a genuine test failure earlier in the log) went unseen. When truncation does occur, the response also includes `truncated: true`, `returnedLines`, and `returnedFrom: "tail"` so the caller knows the content is partial rather than assuming it's the whole log. Falls back to the previous whole-log behavior when no distinct failing step can be identified (plain-text log response, job cancelled at the job level, or missing step data) — a `truncated: true` response with `scopedToFailingStep: false` on a job with no obvious failing step is still worth cross-checking against `ci_search_logs`/`ci_get_logs` before diagnosing as flake.

> **Opaque `{"message":"Internal Server Error"}` 500s from `ci_get_logs`/`get_job_logs` (and any other hosted `legacy-sports-*` MCP tool) were a Lambda-handler gap, fixed at the transport layer (LS-9583)**: every hosted MCP Lambda (`ci`, `github`, `jira`, `rollbar`, `db-admin`) previously called `transport.handleRequest()` with no `try/catch` — an unhandled exception there (a transient upstream blip, an SDK bug, etc.) escaped the Lambda entirely and API Gateway/the Function URL returned its own generic 500 with zero diagnostic detail, forcing a `gh` CLI shell fallback. All five now route through a shared `runMcpTransport()` helper (`lib/mcp-bearer-auth`) that converts any such exception into a well-formed JSON-RPC 500 carrying the real error message. If a hosted tool call still returns a bare, detail-free 500 after this fix, treat it as a new bug (file a gap ticket) rather than assuming a `gh` CLI fallback is required — the tool should now say what actually failed.

## CI Operations

Use `ci_list_runs`, `ci_view_run`, `ci_get_logs`, `ci_search_logs`, `ci_rerun`, `ci_retry_runner_flake`, and `ci_cancel_run` instead of `gh run` commands via Bash. `ci_list_runs` accepts `limit` up to 100 (default 10). These tools parse and structure log output for agent consumption.

**`ci_list_runs` filter matching (LS-9589)**: `commit` accepts an abbreviated SHA (e.g. a 9-char prefix from `git log --oneline` / `worktree_commit`) — it's resolved to the full SHA via a commits lookup before filtering, since GitHub's `head_sha` param only matches a full SHA exactly. `workflow` already falls back to a case-insensitive substring match on the display name when an exact match fails, so a name copied from a check-run label without its emoji prefix (e.g. `"CI Pipeline"` for `"🚀 CI Pipeline"`) still resolves. When a `workflow` filter resolves to a real workflow but the combination with the other filters matches zero runs, the response names the workflow(s) the branch/commit's runs actually belong to instead of a bare "No workflow runs found." `ci_rerun`, `ci_cancel_run`, and `ci_view_run` are consolidated action/param-widened tools (LS-9714 — five overlapping rerun/retry tools and two scalar/batch splits were absorbed into these three; `ci_view_run_jobs` and `ci_retry_runner_flake` stayed separate, the latter because its `prNumber` input and shutdown-detection precondition give it a materially different schema, the documented escape hatch):

- **`ci_rerun({ runId, scope? })`** — `scope: "failed"` (default), `"job"` (+ `jobId`), or `"all"`. When the triage path is "this run failed → rerun the failed jobs", pass `withDiagnostics: true` (single-run, `scope: "failed"` only) for the semantic one-shot — it returns the failed-job list and an error-pattern snippet from the original logs in the same call (former `ci_retry_failed`). Pass `runIds` (1-50) instead of `runId` to rerun several runs independently in one call (former `ci_rerun_batch`); `scope: "job"` and `withDiagnostics` are single-run only.
- When a run was cancelled by the self-hosted-runner-shutdown flake specifically (`##[error]The runner has received a shutdown signal...`), prefer `ci_retry_runner_flake({ prNumber })` (LS-8404) over the manual diagnose-then-retry chain: it checks the PR for the repo's own `CI: Runner Flake` label + bot comment first, falling back (LS-9334) to scanning the PR's most recent run's failed/cancelled job logs directly for the same shutdown signature when both artifacts are absent (e.g. the orchestrator's own reporting job got skipped), and reruns in one call. Only when no layer finds a signal does it return a clear no-signal result (pointing at `ci_rerun({ runId, withDiagnostics: true })`).
- **`ci_cancel_run({ runId })`** — kill a single stale-SHA or no-longer-needed run instead of leaving it running. Pass `{ workflow, branch }` instead of `runId` to cancel every in-flight run of a workflow on a branch in one call (former `ci_cancel_runs`) — e.g. serializing expensive live-backend integration dispatches so a fresh run never races a stale one on the same branch (LS-7878).
- **`ci_view_run({ runId })`** — pass `runIds` (1-50) instead of `runId` to inspect several runs independently in one call (former `ci_view_run_batch`); `attempt` is single-run only.
- **Wedged `ci-orchestrator.yml` run** (a run stuck `pending` with 0 registered jobs, holding the `orchestrator-<PR#>` concurrency group so CI Gate never posts, LS-7752): use `ci_unwedge_orchestrator({ prNumber })` (LS-9587) instead of the manual `gh run list`/`gh api .../jobs`/`gh run view` cancel-then-relabel sequence — it finds the stale 0-job run for the PR's current head SHA, cancels it, polls for confirmed cancellation, then applies the `ci:run` label to redispatch. Bounded ~12s per call; an unconfirmed cancellation returns `{ status: "cancelling", runId, hint }` (never an error) — re-invoke with that `runId` to resume.

**`ci_get_logs` transient 502/503/504 errors**: the log-blob fetch path retries automatically (3 attempts, exponential backoff) as of LS-8218. If `ci_get_logs` still fails after retries, use `get_job_logs` via `legacy-sports-github` as a fallback (see table below).

**`ci_rerun` "already running" 403**: GitHub's workflow-run status (what the rerun endpoints gate on) can lag the per-job status `ci_view_run_jobs` reports, so a rerun can be rejected with a 403 "already running"/"already in progress" even after all jobs look complete. As of LS-8284 this is retried automatically (up to 3 attempts, ~10s/~20s backoff) instead of surfacing the error — no empty-commit workaround needed. If the tool still errors, the message states how many attempts were made; other 403s (e.g. permissions) still fail immediately, unchanged.

**`ci_rerun`/`ci_rerun_failed_jobs` raw "Service Unavailable" transport errors (LS-8704)**: a hanging rerun POST could previously consume the ci-server Lambda's remaining 30s timeout budget and get SIGKILLed mid-request, surfacing as an opaque, unparseable Streamable HTTP `"Service Unavailable"` error — this could happen even after the target run had reached a terminal state, sharing its root cause with LS-8429's `ci_wait_run` 503 symptom on a different endpoint. As of LS-8704 the underlying `githubPost` call is bounded to a 6s client-side timeout, so a hang now fails fast as a catchable error and `ci_rerun`/`ci_rerun_failed_jobs` surface an actionable "safe to retry" message instead of the raw transport error.

**`ci_rerun` (default `scope: "failed"`) and stranded `cancelled` downstream jobs (LS-9212)**: GitHub's `rerun-failed-jobs` endpoint only reschedules jobs with conclusion `failure` — a downstream required job that never ran because its dependency failed is left `cancelled`, not `failure`, so historically it was never rescheduled and just sat until the workflow's overall timeout, leaving `mergeable_state: blocked` with no visibly-failed check. As of LS-9212 the failed-only path detects this automatically and escalates to a full run rerun (`scope: "all"` semantics) whenever the run has any `cancelled` job — check the response `scope`/`message` for `"run (escalated from failed-jobs)"` to know when that happened. You should not need to manually fall back to a full rerun anymore, but if you ever see a run stuck `blocked` with jobs in state `cancelled` that a prior `ci_rerun` call didn't touch, `ci_rerun({ runId, scope: "all" })` is still the manual escape hatch.

**`ci_rerun`/`ci_rerun_failed_jobs` and stale merge-refs (LS-9638)**: GitHub's rerun/rerun-failed-jobs endpoints reschedule jobs against the run's already-checked-out ref, not a live recompute of `refs/pull/N/merge` — for a PR-triggered run, if the base branch has moved since the run first triggered, a rerun can silently replay the old merge snapshot and reproduce a since-fixed failure (or miss a since-introduced one). `ci_rerun` (and its `withDiagnostics` variant) now detects this and adds a `warning` field to the response when the run's `head_sha` no longer matches the PR's current `merge_commit_sha`. If you see that warning after a rerun reproduces an already-fixed failure, the fix is to force a real recompute — push a commit (e.g. merge/rebase the base branch into the PR branch) rather than rerunning again.

**`ci_get_logs` on a job that never started (LS-7910)**: a job that failed before any step executed (runner provisioning failure, hosted-runner billing/spending limit, or a GitHub Actions incident) has no log blob. `ci_get_logs` detects this and returns "Job failed before any step executed -- no logs exist..." instead of a raw Azure Blob Storage 404 — treat that message as the terminal signal (check the run/job conclusion and runner status) rather than retrying the log fetch.

**`ci_get_logs` / `ci_search_logs` on large `workflow_dispatch` runs (LS-8255)**: log fetches are capped at 10 jobs per call with a 20 s deadline. If the response includes `skippedJobs`, narrow scope using `jobName` or `jobId` to fetch specific job logs. Timeout errors include an actionable hint with the same guidance.

**`ci_get_logs`'s `jobName` disambiguates instead of silently guessing (LS-9578)**: job names in this repo overlap heavily by design (e.g. `"test"` is a substring of several distinct job names), so `jobName` prefers a case-insensitive exact full-name match and only falls back to substring matching when no exact match exists. If more than one job matches at either stage, the call errors listing every candidate job name + id instead of picking one — pass the exact name, `jobId`, or `exact: true` to disambiguate. When `jobName` does resolve to exactly one job, the response metadata echoes `resolvedJobName`/`resolvedJobId` so you can confirm which job actually answered the query.

`ci_get_logs` enforces `maxChars` and `truncateLineLength` as **hard caps** on the serialized response — always pass `maxChars` when individual log lines may be multi-KB (e.g. `maxChars: 80000, truncateLineLength: 300`) to prevent context overflow. When truncation occurs the response ends with `... [truncated at N chars]`.

**Paging past a `maxChars` cap (LS-9291)**: `ci_get_logs({ offset })` (like `Read`'s `offset`) skips that many lines from the start of the already-fetched (`maxLines`-bounded) window before `maxChars` truncation is applied — use it to reach content past the head of a large log instead of dumping to a file and slicing manually. The response `meta` includes `linesInWindow` and, when more lines remain, `linesRemainingInWindow` plus a `hint` naming the next `offset` to pass. `offset` is relative to this call's fetched window, not the full log — raise `maxLines` first if the window doesn't yet reach the target line.

**ANSI escape sequences are stripped (LS-9557)**: both `ci_get_logs` and `ci_search_logs` strip ANSI colour/cursor-movement codes from returned log text before `maxChars`/`truncateLineLength` are applied, so those caps budget real content and literal patterns (e.g. `"● FootballLeagueId"`) match without needing a wildcard around where escape codes used to sit.

**`errorSummary: true` scopes to the failing step (LS-9556)**: `ci_get_logs({ errorSummary: true })` now slices a job's log to the step GitHub itself marked `conclusion: "failure"` (via the Jobs API's per-step data) before scoring lines, instead of scanning the whole job log. This is a structural fix for a recurring defect (LS-8391/LS-8405/LS-8772) where runner-bootstrap noise, git-fetch spam, and other-tool-success chatter crowded out real failures; if you still see noise instead of the actual error, the job likely has no step marked `failure` (e.g. cancelled mid-step) — the scoping falls back to the whole log in that case rather than returning nothing.

**`ci_search_logs` (LS-8390)**: also accepts `maxChars` (default 50000) and `truncateLineLength` (applied to the matched line and every before/after context line, default 500/200) — pass these when `contextBefore`/`contextAfter` are non-trivial and log lines may be long, since per-match context can overflow the token limit in aggregate even when `limitMatches` bounds the match count. When the char cap forces trailing matches to be dropped, the response carries `charTruncated: true` and an adjusted `returnedMatches`.

**`ci_search_logs` zero-scope results (LS-8301)**: `failedOnly` defaults to `true`, so a run whose only relevant job actually succeeded (e.g. a successful merge-queue job) can be filtered out of scope entirely — the response still returns `totalMatches: 0`, but check `jobsSearched`/`jobsTotal` and a `scopeNote` field before concluding the pattern is genuinely absent. Separately, `|` in `pattern` is matched as a **literal** character unless `isRegex: true` is also set — alternation (`a|b|c`) silently does not work otherwise, a second way to get a false "0 matches".

**`ci_search_logs` partial job coverage on `workflow_call` orchestrator runs (LS-9389)**: `scopeNote` is not only-for-total-exclusion — it now fires any time `jobsSearched < jobsTotal`, including when `failedOnly` (default `true`) excludes _some but not all_ jobs (e.g. a passing job that actually holds the pattern) or the per-call `MAX_LOG_JOBS` cap trims the searched set. In that case `truncated: true` is also set. Treat any `jobsSearched < jobsTotal` — not just a `scopeNote`-present, zero-searched case — as "this 0-match result is not authoritative"; retry with `failedOnly: false` and/or `jobName`/`jobId` to cover the rest before concluding the pattern is absent from the run.

When acting on **several runs at once** (unblocking or re-validating multiple PRs), pass `runIds` instead of `runId` over a per-run loop: `ci_rerun({ runIds: [...] })` reruns up to 50 runs and `ci_view_run({ runIds: [...] })` inspects up to 50, each returning the shared partial-failure shape `{ success, total, succeeded, failed }` so one run erroring never fails the whole call. `runId` remains for one-off use. (`ci_get_logs` already accepts `runIds` for batch log fetches.)

## Jira Operations

**Auth-aware routing and fallback order**: call `jira_auth_status` before any Jira operation when the `legacy-sports-jira` tools are exposed. If `configured: true`, use `jira_*` MCP tools. If `configured: false` or they fail, use the Atlassian plugin. Fallback chain: `jira_*` MCP tools → Atlassian plugin (`mcp__claude_ai_Atlassian__*`) → `acli` CLI (last resort, local-only).

**When `jira_*` tools are absent from the session** (the `legacy-sports-jira` hosted connector is not connected — availability is per-session consent, see [Auth Model](#auth-model)): do NOT fall back to `acli`. Use the Atlassian plugin directly: `mcp__claude_ai_Atlassian__transitionJiraIssue`, `mcp__claude_ai_Atlassian__getJiraIssue`, etc. (cloud ID `fb294606-6c8f-4b52-9a41-11fe45b77528`). `acli` is only for local sessions where both the connector and the Atlassian plugin are confirmed unavailable.

**Description fields accept Markdown**: `description`, `context`, `risk`, and `planningNotes` params on `jira_create_ticket`, `jira_bulk_create_tickets`, and `jira_edit_ticket` all parse Markdown to ADF before sending to Jira. Bullet lists (`-`/`*`/`+`), numbered lists, fenced code blocks, ATX headings, **bold**, _italic_, and `inline code` all render correctly in the Jira UI. Plain text is unchanged — no migration needed for existing calls.

**`jira_create_ticket` hints on an invalid Story parent**: a `Bug`/`Task` cannot parent to a `Story` — only an Epic can (see [plan-ticket's Hierarchy section](../plan-ticket/references/create.md#hierarchy)). If this 400s (`"Please select valid parent issue"`), the error response includes a `hint` field naming the epic-parent + `jira_link_issues(..., linkType: "Relates")` workaround (LS-8481) — read it instead of retrying blind.

Use `jira_list_children` instead of `searchJiraIssuesUsingJql` with `parent = LS-####` to list children of an epic or story. Raw JQL returns verbose markdown-formatted output that can overflow the MCP context limit (~192K chars for 50 results); `jira_list_children` returns compact structured JSON with pagination support. Pass `paginate: true` to fetch **all** children in a single call — the tool paginates internally and returns `{ parent, total, children: [{key, summary, status}], truncated? }` (hard-capped at 500 items; `truncated: true` when the cap is hit). Use `paginate: true` whenever the parent is an epic or bucket with potentially 100+ children to avoid manual `pageToken` threading.

For any other JQL query, use `jira_search` instead of `searchJiraIssuesUsingJql`. The Atlassian plugin's tool returns ~3.8 KB per issue (~190 KB for 50 results) due to metadata envelope overhead (expand URLs, self links, avatar URLs, statusCategory objects) even when minimal fields are requested. Use `compact: true` for large result sets to get `{ issues: [{key, summary, status}], nextPageToken? }` (~2 KB for 50 issues). When the response includes `nextPageToken`, pass it as `pageToken` to fetch the next page.

**LS-8983 — `searchJiraIssuesUsingJql`'s `fields` param is non-functional**: passing `fields: ["summary", "status"]` (or any other narrow field list) to the Atlassian plugin's `searchJiraIssuesUsingJql` does not restrict the response — every issue still comes back with the full nested `project`, `issuetype` (with `avatarUrls`), `assignee`, `statusCategory`, and other objects, exactly as if `fields` had been omitted. A 15-issue response can exceed 64,500 characters this way. This is the root cause behind the ~3.8 KB/issue overhead described above — `fields` cannot be used to work around it. **Do not pass `fields` to `searchJiraIssuesUsingJql` expecting it to shrink the response.** Use `jira_search(jql: "...", compact: true)` or `jira_list_children` instead (see the routing table above); if only the raw plugin tool is available, redirect the output to a file and extract with `jq`/`Grep` rather than reading the full response inline.

**LS-9233 — always pass an explicit `maxResults` to `searchJiraIssuesUsingJql`**: the Atlassian plugin's tool has no safe implicit default — omitting `maxResults` (or passing a broad one like 50) on a JQL query with many matches overflows the MCP tool-result token cap, because each issue costs ~3.8 KB regardless of the `fields` requested (see the LS-8983 note above). **Never call `searchJiraIssuesUsingJql` without an explicit `maxResults`.** Use `maxResults: 1` for single-issue lookups (`key = LS-####`); for broader queries, prefer `jira_search(jql: "...", compact: true)` or `jira_list_children` (see the routing table above) instead of raising `maxResults` on the plugin tool.

**LS-9237 — `jira_search` supports a working `fields` param**: unlike the Atlassian plugin's `searchJiraIssuesUsingJql`, the custom `jira_search` tool's `fields` param is honored — pass `fields: ["summary", "status", ...]` to restrict both the underlying JQL request and the rendered table to exactly those Jira field names (plus `key`), overriding the default/compact column set. Nested `{ name }` / `{ displayName }` / `{ value }` shapes (e.g. `status`, `assignee`) are flattened to their scalar automatically. Prefer `compact: true` for the common summary/status case; reach for `fields` only when you need a specific field neither default set includes.

**LS-9509 — never loop `jira_check_blockers`, and never hand a blocker sweep to a subagent**: Jira returns `issuelinks` inside the same search response as `summary` and `status`, so blocker state is free to carry. Pass `includeBlockers: true` to `jira_search` or `jira_list_children` and every row gains a `blocked` column (`yes` when a blocker is neither Done nor In Review) and a `blockers` column listing non-Done blockers as `LS-123(Status)` — at zero additional Jira requests. `jira_get_all_descendants` already annotates `blocked` / `blockers[]` unconditionally. Read blocker state off the listing you already made; a row with `blocked=no` that still names an `LS-x(In Review)` blocker is the signal to base the branch off `LS-x` rather than `main`. Only when you hold bare keys with no listing should you call `jira_check_blockers` — and then pass `keys: [...]` (1-50, resolved in one JQL call), not N single-key calls. A single `key` still returns the original flat `{ canProceed, blockers, recommendation }`.

**Batch variants (call once instead of N times in a loop)**: when operating on multiple tickets, prefer the `*_batch` / `bulk_*` tools over looping the single-item tool. Each accepts an array (max 50) and isolates per-item failures so one bad input never fails the whole call. Two distinct response shapes are in use today:

- **Operation-style** `{ total, succeeded, failed }` — used by tools that perform writes or where per-item identity is naturally a list: `jira_transition({ keys: [...] })` (multi-key status change; `jira_bulk_transition` is a deprecated alias), `jira_bulk_create_tickets`, `jira_bulk_edit` (summary/description/type/sprint/parent across N tickets), `jira_bulk_link_issues` (N issue links; same inward/outward contract as `jira_link_issues`), and `jira_bulk_list_children` (children of N parents in one call — returns the first page per parent; a parent's `nextPageToken`, when present, signals truncation, so page that parent with single-item `jira_list_children`).
- **Read-style** `{ <items>: { [key]: ... }, missing: [key, ...] }` — used by reads where the natural answer is a key→record map: `jira_view({ keys: [...] })` returns `{ tickets: { [key]: ticket }, missing: [key, ...] }`. Pass `include: ['comments']` or `include: ['transitions']` to fetch sub-resources in the same call (replaces the former `jira_get_comments` / `jira_get_transitions` tools).

Single-item tools are retained for one-off use.

**Claim mode assignee resolution (LS-7891, precedence fixed in LS-8302, email unblocked in LS-9513)** — applies to `jira_transition({ ..., action: "claim" })` and `jira_start_work`: on a successful claim the ticket is assigned using the first available of: `assigneeAccountId` param → `assignee` email param → `JIRA_ASSIGNEE_ACCOUNT_ID` env var → `JIRA_ASSIGNEE_EMAIL` env var → `GET /rest/api/3/myself`. accountId paths come first because they need no lookup at all.

Email resolution is two-stage. `/rest/api/3/user/search` is tried first and works in local basic-auth sessions; on the **hosted Lambda** it 401s ("Unauthorized; scope does not match") because the service account's client-credentials token carries only `read:jira-work write:jira-work`. It then falls back to a JQL lookup — `assignee = "<email>"`, reading `fields.assignee.accountId` off the first match — which **is** permitted under `read:jira-work`. Two things to know about that fallback: it only finds users who already have at least one issue assigned somewhere (a brand-new user's first claim still comes back unassigned with a warning), and the resolution is memoised per Lambda container.

`read:jira-user` is not simply unrequested — it is not grantable to the service app today: asking for it at the token endpoint returns `invalid_scope`. Enabling `/myself` and `/user/search` on the Lambda would take an Atlassian developer-console change, which is why the JQL route exists. The `/myself` last resort therefore remains local-only.

**An In Progress ticket with no assignee gets repaired, not skipped (LS-9513).** Both `claim` (which returns `ALREADY_CLAIMED`) and `jira_start_work` (which returns `idempotent: true`) used to return before the assignment step, so a ticket left unowned by an earlier failed claim could never be fixed by re-running either tool. They now fill in the missing assignee — without re-transitioning or re-claiming — and say so in `warnings`. A ticket that already has an assignee is left untouched.

**The env vars are Lambda-wide, not per-session — always prefer the explicit param.** The hosted Lambda is shared across every caller's session, so `JIRA_ASSIGNEE_ACCOUNT_ID`/`JIRA_ASSIGNEE_EMAIL` cannot identify which session is claiming a given ticket; falling back to them attributes every claim that omits an explicit `assignee`/`assigneeAccountId` param to the same fixed account. Per [work-ticket leaf-mode](../work-ticket/references/leaf-mode.md) step 1, resolve the assignee from **this session's own** `JIRA_ASSIGNEE_EMAIL` env var (`echo "$JIRA_ASSIGNEE_EMAIL"`) and pass it explicitly as the `assignee` param on every claim call — do not rely on the Lambda picking it up itself. When a call does fall through to the env-var default (no explicit param passed), the tool surfaces a loud warning (logged + returned in `warnings`) rather than assigning silently, so misattribution is visible instead of assumed correct. The Lambda's own default comes from the `jira_assignee_email` / `jira_assignee_account_id` terraform variables; `jira_assignee_email` is fed from the `JIRA_ASSIGNEE_EMAIL` repo variable by `lambda-terraform-apply.yml` (LS-9513) — before that both were empty strings, so every param-less claim fell straight through to the 401ing `/myself`.

**Standalone assignment with no transition (LS-9607)** — `jira_edit_ticket` and `jira_bulk_edit` also accept `assignee`/`assigneeAccountId`, reusing the same `resolveAndAssign` machinery (and precedence) described above, but **without** any status transition — use these when a ticket just needs to change hands (e.g. backfilling unassigned tickets) and `jira_transition({ action: "claim" })` / `jira_start_work`'s In Progress side effect and Done/In Review guard are unwanted. Passing both params as `null`/`""` (or omitting one while the other is empty) unassigns the ticket. `jira_bulk_edit` applies this per-ticket across the batch.

**Claim duplicate-work guard (LS-9289)** — `jira_transition({ ..., action: "claim" })` accepts an optional `openPrs` param: PRs the caller already found referencing the ticket key (e.g. `github_pr_dashboard(state: "open")` filtered by key). The jira server has no GitHub credentials of its own and cannot check this itself, so the guard only fires when the caller supplies it — when `openPrs` is non-empty, claim returns `action: "PR_EXISTS"` instead of `PROCEED` and does not transition or assign the ticket. See `.agents/skills/work-ticket/references/leaf-mode.md` step 1 for when to run the lookup.

**LS-3810 caveat — `transitionJiraIssue` response body bug**: the Atlassian plugin's `transitionJiraIssue` response body returns data for a different issue — the returned `key`/`id` will not match the requested issue key (sometimes off-by-one in the key sequence). The transition itself succeeds, but always re-verify: call `searchJiraIssuesUsingJql(cloudId: "fb294606-6c8f-4b52-9a41-11fe45b77528", jql: "key = LS-XXXX", maxResults: 1, fields: ["status"])`, confirm `issues[0].key` matches the requested key, and check `issues[0].fields.status.name` to confirm the transition. The custom `jira_transition` MCP tool is not affected by this bug.

**LS-3715 — `getJiraIssue` returns parent epic's children instead of the requested issue**: the Atlassian plugin's `getJiraIssue` tool returns the parent epic's children list instead of the requested single issue. **Never use `mcp__*__getJiraIssue` to fetch a single ticket.** Use `searchJiraIssuesUsingJql(cloudId: "fb294606-6c8f-4b52-9a41-11fe45b77528", jql: "key = LS-XXXX", maxResults: 1)` instead, or the custom `jira_view` MCP tool (unaffected by this bug).

**LS-3771 — `transitionJiraIssue`/`createJiraIssue` cold-start encoding bug**: both Atlassian plugin tools reject nested object parameters (`transition: { id }` and `additional_fields`) with "expected object, received string" during a cold-start window. **Mitigation for transitions**: retry once after any other successful plugin call; if that still fails — in a local session fall through to `acli jira workitem transition --key LS-#### --status "<Status>" --yes`; in a cloud session use `jira_transition` from the custom MCP server if available, otherwise transition manually in the Jira UI. **Mitigation for creates with parent**: use `jira_create_ticket({ summary: "...", parent: "LS-####" })` (custom server, unaffected) when available. If the custom server is unavailable, create the ticket without parent then set it via `editJiraIssue({ cloudId: "fb294606-6c8f-4b52-9a41-11fe45b77528", issueIdOrKey: "LS-CHILD", fields: { parent: { key: "LS-PARENT" } } })`.

## AWS Operations

Use `aws_logs_tail` instead of `aws logs tail` via Bash, and `aws_sso_status` to check credentials before any AWS operation. If `aws_sso_status` returns expired or unconfigured, **stop immediately and prompt the user to run `aws sso login`** — do not retry the failing command. See `.agents/skills/infrastructure/references/aws-sso-login.md` for the exact prompt pattern.

In a **Claude Code Remote (CCR) session**, the `legacy-sports-aws` stdio server may connect but every `aws_*`/`packer_*` tool call still fails, because there is no `aws`/`terraform` binary on PATH there (LS-9537). This surfaces as an actionable error naming the missing binary and the CCR limitation — not the raw `spawn aws ENOENT` Node throws by default — but the underlying capability gap is real: AWS-side verification (live Lambda config, CloudWatch logs, etc.) is simply unavailable from a CCR session. Fall back to what the deploy/CI run itself reports (e.g. a Terraform apply output in the GitHub Actions log) instead of retrying `aws_*` tools.

`aws_logs_tail` defaults to markdown (extracted `### Errors` from `ERROR`/`WARN`/`Exception`/`Error:` lines + their stack frames, followed by a `### Recent` code-block with the last 50 lines). Pass `format: 'json'` only when you need the structured payload (e.g. piping into another tool). Pass `functions: string[]` (1-10) for batch mode — per-function blocks fetched concurrently (cap 5). For historical incident forensics, pass `startTime` + `endTime` (ISO-8601, e.g. `2025-06-01T00:00:00Z`) to pin an exact absolute window instead of the rolling `since` lookback; `maxLines` cap still applies.

For searching arbitrary log groups (including `/aws/apigateway/...` access logs) or scoping to a precise time window, use `aws_logs_filter` instead. It accepts any `logGroup` (leading-slash names handled natively — no `MSYS_NO_PATHCONV` needed), an optional `filterPattern`, and `startTime`/`endTime` as epoch milliseconds. Output is hard-capped at 50 events or 20 000 chars (`truncated: true` when hit).

## Browser Operations

Use `browser_dev_start` to start a dev server, `browser_navigate` + `browser_screenshot` to capture UI state, and `browser_screenshot_upload` to get GitHub-hosted image URLs for PR bodies. `browser_dev_start` waits at most 45s for readiness and never blocks into the ~60s MCP transport limit (LS-8561): on a slow startup it returns `ready: false` with the pid/port — poll `browser_dev_status` until the port shows `listening: true` before navigating. It defaults to `nx serve web` but accepts a `target` param (nx `"project:target"`, e.g. `"shared-components:storybook"`) to start any other nx dev server instead (LS-8665) — never fall back to a manual `Bash`+`curl`+sleep-poll loop for this. Always call `browser_cleanup` before ending a workflow. See `.agents/skills/pr-lifecycle/references/agent-screenshots.md` for the full workflow.

`browser_navigate` on a bare non-HTML document (a `.svg`/`.xml` `file://` URL rendered natively, whose root has no `<head>`) skips the post-navigation stabilization-CSS injection instead of throwing, and does not emit the dev-server remedy hint for `file://` navigation failures (LS-9393) — no dev server is involved in a `file://` load. Use this path to verify hand-authored SVG diagrams (`.agents/skills/**/diagrams/*.svg`) render correctly: `browser_navigate` straight to the `file://` path, then `browser_screenshot`.

For a route that requires an authenticated session, use `browser_dev_login({ port })` instead of typing a real password into the sign-in form or trying to set the `ls_jwt` HttpOnly cookie via page-context JS (`document.cookie` can't see or set httpOnly cookies — this is exactly the gap that blocked LS-9208's AC1). It reads the cached e2e JWT from `~/.legacy-sports/e2e-token.json` (minted interactively by the human via `make e2e-auth` — agents cannot complete the device-flow handshake) server-side and applies it via Playwright's `context.addCookies` plus `page.evaluate` for the matching localStorage keys, mirroring `apps/web-e2e/src/integration/fixtures/ui.ts`'s `buildIntegrationStorageState`; the JWT itself is never included in the tool result (LS-9437). Fails with a `make e2e-auth` remedy if no valid cached token exists.
